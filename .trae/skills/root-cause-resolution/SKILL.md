# 根因排查与解决

## 概述

随机修复浪费时间并制造新 Bug。快速补丁掩盖根本问题。

**核心原则：** 在尝试修复之前，必须先找到根因。只治标不治本 = 失败。

**阶段：** 0（调查）→ 1（路径）→ 2（修复）→ 3（验证）→ 4（收尾）

## 铁律

```
未完成根因调查之前，禁止任何修复
```

---

## 进度追踪

在整个排查过程中，维护一份**进度文件**追踪所有问题、任务及其解决状态。

### 文件管理

- **目录**：`docs/root-cause-resolution/`（不存在则创建）
- **文件名**：`progress-YYYY-MM-DD-HHmmss.md`（精确到秒，避免重复）
- **状态值**：`待处理` → `进行中` → `已完成`（仅在用户确认后）

### 文件格式

```markdown
# 进度 — 2026-07-20 14:35:27

文件：docs/root-cause-resolution/progress-2026-07-20-143527.md

## [ ] 事项 1：[问题/任务的简要描述]
- 状态：待处理
- 根因：
- 修复：
- 验证：

## [ ] 事项 2：[简要描述]
- 状态：进行中
- 备注：正在排查…
```

### 更新规则

| 时机 | 操作 |
|------|------|
| 工作开始前 | 创建文件，列出所有问题/任务，初始状态 `待处理` |
| 开始处理某事项 | 状态设为 `进行中` |
| 调查/修复过程中 | 追加过程记录（根因发现、修复尝试、验证步骤） |
| 用户确认解决 | 标记 `已完成`，记录确认时间戳 |
| 用户提出新任务（任何时候） | 立即追加新事项，告知用户 |
| 进入 Phase 4 前 | 检查所有事项，未完成的先与用户确认 |

### 新任务处理

用户在任何阶段提出新任务时：
1. 立即追加到进度文件，状态 `待处理`
2. 告知用户："已记录新任务：[描述]"
3. 继续当前工作，除非用户明确重新排定优先级
4. 若重新排定优先级，前一个事项备注"已暂停 — 重新排定至 [新事项]"

### 核心规则

- 即使是"简单"问题也必须创建进度文件
- 每次重要事件后立即更新，不要"稍后"
- 进度文件是活跃工作的唯一真实来源，不要依赖记忆
- Phase 4 前必须读取文件确认所有事项状态

## Phase 0：根因调查

在尝试任何修复之前，必须完成以下所有步骤。

### 第 1 步：仔细阅读错误信息

- 完整阅读堆栈跟踪，注意行号、文件路径、错误码
- 不要跳过任何错误或警告
- 错误信息通常包含精确的解决方案

### 第 2 步：稳定复现

- 能否稳定触发？确切步骤是什么？
- 如果无法复现：
  - 在疑似触发点添加日志埋点（见[根因追踪](#根因追踪)）
  - 检查环境问题（操作系统、Node 版本、配置差异）
  - 查看调试日志（Tauri：`debug-logs.txt`，浏览器：`debug-logs-browser.txt`）
  - **不要猜测** — 收集更多数据直到能复现或隔离触发条件

### 第 3 步：检查近期变更

- Git diff、近期提交 — 什么改动可能导致此问题？
- 新依赖、配置变更、环境差异

### 第 4 步：收集多组件证据

当系统包含多个组件时，在提出修复方案前先添加诊断埋点：
- 记录数据进出每个组件边界时的状态
- 验证环境/配置的传播
- 运行一次收集证据，确定**在哪里**出问题，再深入调查

### 第 5 步：数据流追踪

当错误位于调用栈深处时，向后追踪找到原始触发点：
- 错误值从何处产生？
- 是谁用错误值调用了当前函数？
- 持续向上追踪直到找到源头
- 在源头修复，而非在表象处

详见[根因追踪](#根因追踪)。

### 第 6 步：模式分析

- 查找可工作的示例 — 什么相似的功能是正常的？
- 对比参考实现，列出正常与异常之间的每一个差异
- 理解依赖关系 — 此功能需要哪些组件、配置、环境？

### 第 7 步：假设与验证（科学方法）

1. 形成单一假设："我认为 X 是根因，因为 Y" — 要具体
2. 最小化验证 — 做**最小**可能的改动，一次只改一个变量
3. 验证后继续 — 有效则继续，无效则形成**新**假设，不在已有改动上叠加

**不知道时：** 说"我不理解 X"，触发[外部调研](#外部调研)查阅资料。不要假装知道。

## Phase 1：确定路径

### 路径 A：已确认根因

**条件（必须全部满足）：**
- 能够解释导致问题的确切机制
- 能够从触发点到表象追踪数据/控制流
- 修改已确认的根因能修复问题且无副作用

→ 进入 Phase 2A（直接修复）。

### 路径 B：未确认根因

**只有在以下所有条件都满足时**才能得出"未找到根因"的结论：
- 已穷尽所有调查手段（完整调用栈、组件边界、Git 历史、稳定复现）
- 已确认问题属于环境层面或已知的第三方依赖限制且无升级路径
- 已记录所调查的内容以及每条路径为何行不通

**未满足条件 → 返回 Phase 0。** 不要过早进入路径 B。

→ 进入 Phase 2B（预防性措施）。

## 外部调研

当遇到以下任一情况时，必须触发外部调研，不得闷头硬试：

| 触发场景 | 说明 |
|---------|------|
| 没有候选方案 | 所有方案评估后均不可行 |
| 完全不知道如何解决 | 缺乏相关知识或经验，无从下手 |
| 遇到特别顽固的问题 | 多次尝试后问题依然存在 |
| 多次修复失败 | 第 1-2 次修复无效重新分析后仍无解 |
| 技术方案有根本性分歧 | 现有知识无法判断哪种方案正确 |
| 怀疑有更好的做法但不知道 | 直觉感到当前方案不够好 |

**调研步骤：**
1. 搜索网络（`WebSearch`），了解类似产品如何处理相同问题
2. 查阅相关库/框架的官方文档
3. 搜索社区讨论（GitHub Issues、Stack Overflow）
4. 使用相同框架评估外部方案
5. 结合项目上下文调整，不要盲目复制

**查询模板：**
```
"[技术/库] [问题描述] 最佳实践"
"[错误信息或症状] 解决方案 site:github.com"
```

## Phase 2A：直接修复（已知根因）

1. **创建失败测试用例** — 优先使用自动化测试，没有则用一次性脚本
2. **设计修复方案** — 在根因源头修复，一次只改**一处**，不要"顺手"做额外改进
3. **检查同类问题** — 代码库中是否还有其他地方存在相同根因模式？
4. **添加验证日志** — 格式见[日志规范](#日志规范)
5. **[进度] 更新进度文件** — 记录根因、修复方案和发现的同类问题
6. **进入 Phase 3**

**如果修复无效：**

| 失败次数 | 操作 |
|---------|------|
| 第 1 次 | 返回 Phase 0 重新分析；或触发[外部调研](#外部调研) |
| 第 2 次 | 返回 Phase 0 或触发[外部调研](#外部调研)；记录失败尝试 |
| 第 3 次及以上 | **停止。** 触发[外部调研](#外部调研) + 质疑架构（见[3 次以上失败](#3-次以上修复失败质疑架构)） |

---

## Phase 2B：预防性措施（无根因）

### 第 1 步：设计候选方案

对每个候选方案按以下框架评估：

| 维度 | 评估问题 |
|------|---------|
| 覆盖范围 | 能处理哪些场景？遗漏了哪些？ |
| 复杂度 | 需要多少代码？新依赖？新概念？ |
| 副作用风险 | 可能破坏什么？性能影响？ |
| 可维护性 | 后续开发者能理解吗？易于调试吗？ |
| 误判风险 | 会不会阻止正常行为？ |
| 可逆性 | 如果引发问题，撤销的难度如何？ |

### 第 2 步：向用户展示选项

当存在多个可行方案时，使用 `AskUserQuestion`：
- 为每个选项提供简短标签
- 描述中总结：做什么、优缺点、推荐理由
- 推荐选项标记为"(推荐)"
- 等待用户决策后再实施

### 第 3 步：实施并继续

方案确定后实施。**[进度] 更新进度文件** — 记录预防性方案及其理由。进入 Phase 3。

## Phase 3：验证

### 第 1 步：添加验证日志

如果 Phase 2A 中尚未添加，在关键位置添加诊断日志。格式见[日志规范](#日志规范)。

**需要记录：** 修复点的进入/退出及状态、数据转换前后的值、错误路径、修复所依赖的假设

### 第 2 步：用户测试

1. 告知用户需要测试什么以及注意观察什么
2. 等待用户确认测试完成
3. **不要事先宣布成功**
4. **[进度] 更新进度文件** — 标注用户测试已完成

### 第 3 步：日志分析

用户确认测试完成后，分析日志文件。注意 `.adl-logs/` 位于 `.gitignore` 中：

| 工具 | 可用？ | 说明 |
|------|--------|------|
| `LS` / `Read`（绝对路径） | 是 | 绕过 `.gitignore` |
| `RunCommand` | 是 | Shell 不遵守 `.gitignore` |
| `Glob` / `Grep` / `SearchCodebase` | **否** | 遵守 `.gitignore`，会遗漏日志 |

**也检查运行时调试日志：** `debug-logs.txt`（Tauri）和 `debug-logs-browser.txt`（浏览器）

**检查要点：** 预期日志条目 → 确认修复生效；错误条目 → 边界情况；缺失条目 → 代码路径未触发；意外模式 → 与假设不符

### 第 4 步：处理结果

| 结果 | 操作 |
|------|------|
| 日志确认有效，用户确认解决 | **[进度] 标记已完成**，记录验证摘要 → Phase 4 |
| 修复部分有效但存在缺口 | 识别缺口，记录分析，返回 Phase 2A/2B 完善 |
| 修复完全无效 | 记录失败尝试，重新检查方案/代码/方法/架构 |
| 引入回归 | 回滚或调整修复；记录回归；重新评估副作用 |
| 用户说"问题还是没有解决" | 记录"用户报告修复无效"，进入[失败迭代](#失败迭代) |

### 失败迭代

当用户报告问题仍然存在：
1. 重新检查方案 → 假设错了？修复的是表象而非根因？
2. 重新检查代码 → 实现是否正确？边界情况？
3. 重新检查方法 → 技术策略是否合理？
4. 重新检查架构 → 是否是系统性问题？
5. 仍然卡住 → 触发[外部调研](#外部调研)

**经过 3 次失败的迭代后，停止。** 向用户升级报告每轮尝试、学到什么、未解决的架构问题。不要尝试第 4 轮。

### 3 次以上修复失败：质疑架构

**表明架构问题的模式：**
- 每次修复在不同位置暴露新问题
- 修复需要"大规模重构"
- 每次修复在其他地方产生新症状

**停止并质疑：** 这个模式是否从根本上不合理？是否应该重构架构而非修修补补？

**在尝试更多修复前与用户讨论，同时配合[外部调研](#外部调研)。**

### 触发检测

进入 Phase 4 的触发条件是用户表示问题已解决的任何消息。检测模式：

| 中文 | 英文 |
|------|------|
| "问题已解决"、"已解决"、"搞定了"、"没问题了"、"可以了"、"好了"、"解决了" | "it's fixed"、"problem resolved"、"solved"、"done"、"works now"、"resolved"、"fixed" |

**第 1 步 — 更新进度文件：** 将对应事项标记为 `已完成`，记录确认时间戳。

**第 2 步 — 进度关卡：** 读取进度文件，检查未确认事项：
- 全部已完成 → 进入 Phase 4
- 有未完成事项 → 询问用户每个未确认事项，更新后进入 Phase 4

**模糊触发：** 如果消息可能另有含义（如"好了"可能只是示意停止），询问一次："确认问题已解决，可以开始收尾归档了吗？"

## Phase 4：收尾归档

### 入口关卡

读取 `docs/root-cause-resolution/` 下最新进度文件：
- 所有事项已完成 → 进入第 1 步
- 存在未完成事项 → 返回[触发检测 — 第 2 步](#触发检测)先解决

### 第 1 步：根因验证与代码清理（子代理工作流）

**只读报告循环：** 子代理只生成报告，主代理实施修复。循环直到报告无问题。

```
子代理（只读报告）→ 主代理审查 → 有问题 → 主代理修复 → 子代理重新审查
                                         → 无问题 → 继续
```

**规则：**
| 规则 | 说明 |
|------|------|
| 子代理类型 | 始终使用 `subagent_type: "search"`（只读） |
| 禁止修改代码 | 子代理不得写入、编辑或删除任何文件 |
| 强制重新审查 | 主代理修复后，必须重新调度同一子代理审查 |
| 预存问题必须修复 | 包括此前已存在的代码问题 |
| 逐问题循环 | 每个问题使用独立子代理循环 |

#### 子代理 A：根因验证

对每个问题，调度只读子代理审查变更：

```
分析为修复 [问题描述] 所做的变更。进行全面审查：

1. 根因与正确性：是否识别并修复了真正的根因？遗漏了边界情况？
2. 技术方案与设计质量：方案是否合适？命名、职责、耦合、架构一致性
3. 副作用与安全性：是否引入回归？性能影响？影响共享状态？
4. 预存问题：审查范围内是否存在此前已存在的代码问题？

审查所有变更文件的 git diff。对每个问题包含严重性（严重/高/中/低）和建议修复方案。
```

#### 子代理 B：死代码与冗余清理

对每个通过根因验证的问题，调度只读子代理：

```
审查为 [问题描述] 所做的所有变更。识别并报告：

1. 死代码 — 不可达的代码（未使用的导入、函数、变量、永不执行的条件分支）
2. 冗余检查 — 同一条件的多重守卫、重复验证
3. 不必要的预防措施 — 根因修复后不再需要的防御性代码
4. 诊断日志 — 应删除或降级为 trace 级别的调试日志

不要标记：有正当用途的错误处理、系统边界验证、生产调试用的 warn/error 日志

对每个项目指定：文件路径、行号、要删除的内容、为何可安全删除。
```

#### 最终验证

所有清理完成后：
1. 运行验收流程（ESLint/Prettier/Clippy/rustfmt + 类型检查 + 测试）
2. 验证所有修复在清理后仍然完整

### 第 2 步：标记所有事项为已完成

确认进度文件中所有事项已标记 `已完成`。保留全部过程记录，不得删除或修改。

### 第 3 步：更新 README.md

更新 `docs/root-cause-resolution/README.md`：
1. 读取当前内容
2. 追加记录（如尚未存在）：
   ```
   - [progress-YYYY-MM-DD-HHmmss.md](./progress-YYYY-MM-DD-HHmmss.md) — 事项1标题, 事项2标题, 事项3标题
   ```
3. 确保链接按时间顺序排列（最新在最后）

## 日志规范

### 日志目录

- `.adl-logs/` — 项目调试日志（`.gitignore` 保护），使用 `LS`/`Read` 绝对路径访问
- `debug-logs.txt` — Tauri 桌面模式
- `debug-logs-browser.txt` — 浏览器预览模式

### 日志格式

```
[时间戳] [级别] [组件::函数] 消息 — 键=值, 键=值
```

示例：
```
[2026-07-14T15:30:00.123Z] [DEBUG] [WorkspaceStore::openWorkspace] 进入 — path="E:/test", workspaceId="abc-123"
[2026-07-14T15:30:00.789Z] [ERROR] [WorkspaceStore::openWorkspace] 加载失败 — error="ENOENT: no such file"
```

### 日志级别

| 级别 | 使用场景 |
|------|---------|
| `DEBUG` | 追踪修复执行、验证代码路径 |
| `INFO` | 状态转换、成功操作 |
| `WARN` | 预期但异常的情况 |
| `ERROR` | 意外的失败、异常 |

### 日志规则

- 始终包含上下文（组件、函数、相关 ID/值）
- 在关键操作前后都记录，不仅仅在操作之后
- 记录错误路径，不要只记录正常路径
- 如果修复依赖某个假设，在该假设被违反时记录

## 根因追踪

Bug 通常出现在调用栈深处。在错误表象处修复只是在治标。

**核心原则：** 沿调用链向后追踪直到找到原始触发点，在源头修复。

### 追踪过程

1. **观察表象** — 错误表现是什么？
2. **查找直接原因** — 哪段代码直接导致此错误？
3. **向上追踪** — 谁调用了出错的函数？谁传递了参数？
4. **持续追踪** — 查找错误值是在哪里进入调用链的
5. **找到原始触发点** — 错误值首次被引入的地方，在**此处**修复

### 添加堆栈追踪

当无法手动追踪时：

```typescript
const stack = new Error().stack;
console.error('DEBUG 操作:', { directory, cwd, stack });
```

**要点：** 在测试中使用 `console.error()`（日志器可能被抑制）；在危险操作之前记录，而非失败之后；包含上下文和堆栈。

## 决策树

```
Bug / 意外行为
  │
  ├─ [进度] 创建进度文件，列出所有事项
  │
  ├─ Phase 0：根因调查（7 步）
  │     ├─ 🤷 不知道？ → [外部调研]
  │     ├─ 根因已确认 → Phase 1 → Phase 2A → Phase 3
  │     └─ 未确认 → 已穷尽手段？ 是 → Phase 2B
  │                             否 → 返回 Phase 0
  │
  ├─ Phase 2A 修复无效？
  │     ├─ 第 1-2 次失败 → 返回 Phase 0 / [外部调研]
  │     └─ 第 3 次以上 → [外部调研] + 质疑架构
  │
  ├─ Phase 3 → 已修复？ → 标记已完成 → 进度关卡 → Phase 4
  │     └─ 否 → 失败迭代（最多 3 轮）→ 仍卡住 → [外部调研]
  │
  └─ 任何阶段：用户新任务 → 立即追加进度文件
```

## 红旗警示

| 如果发现自己… | 应该… |
|-------------|------|
| "先快速修复，以后再调查" | 从一开始就做对 |
| "试试改 X 看看能不能行" | 返回 Phase 0，不要猜测 |
| "我没完全理解，但可能有效" | 停止，理解清楚再修复 |
| 一次性做多处改动 | 一次只改一个变量 |
| 跳过验证日志 / 失败测试 | 没有证据就是盲人摸象 |
| 在追踪数据流之前就提出方案 | 你不知道根因 |
| 再试一次修复（2 次以上失败后） | 3 次以上失败 = 架构问题 |
| 未穷尽根因调查就添加预防性措施 | 返回 Phase 0 |
| 使用 `Glob`/`Grep` 读取 `.gitignore` 保护的日志 | 使用 `LS` + `Read` 绝对路径 |
| 跳过创建进度文件 / 忘记更新 | 进度文件是唯一真实来源 |
| 未通过进度关卡就进入 Phase 4 | 必须先检查未确认事项 |
| 没有头绪时硬试而非触发外部调研 | 搜索和学习是调试的一部分 |
| 多次修复失败后仍不寻求外部信息 | 第 3 次失败时必须触发外部调研 |
| 子代理修改代码 | 始终使用 `subagent_type: "search"`，只读 |
| Phase 4 完成后忘记更新 README.md | 每次收尾后必须追加记录 |

**以上任何情况（最后一条除外）意味着：停止，返回 Phase 0。**

## 速查表

| 阶段 | 关键活动 | 成功标准 |
|------|---------|---------|
| **进度** | 创建进度文件，列出事项，每次事件后更新 | 所有事项已追踪且状态准确 |
| **0. 调查** | 阅读错误，稳定复现，检查变更，收集证据，追踪数据，模式分析，假设验证 | 理解是什么和为什么 |
| **1. 路径** | 确定根因是否已知 | 明确选择路径 A 或 B |
| **2A. 直接修复** | 失败测试，设计方案，检查同类，添加日志 | 修复针对根因 |
| **2B. 预防性** | 设计方案，展示选项，触发外部调研 | 方案已确定并实施 |
| **3. 验证** | 日志，用户测试，日志分析 | 问题已确认解决 |
| **关卡 → 4** | 标记已完成，检查未确认事项，询问用户 | 所有事项已确认 |
| **4. 收尾归档** | 子代理验证+清理 → 标记已完成 → 更新 README | 代码已清理，进度已标记，README 已更新 |
