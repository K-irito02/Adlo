# Documentation Organizer

整理项目中的所有文档性质文件，建立规范、合理、清晰的层级结构，确保文档不再散乱无章。

## 触发条件

当用户提出以下需求时调用此技能：

- 整理文档 / 组织文档结构
- 文档太乱了，帮我规整一下
- 建立文档规范 / 文档目录规范
- 把散落的文档归类
- 重构文档目录结构

## 执行流程

### 阶段 1：盘点与诊断（Inventory & Diagnosis）

**1.1 全量扫描**

扫描项目中所有文档性质的文件（`.md`、`.txt`、`.rst`、`.adoc` 等），排除以下目录：

- `node_modules/`、`.git/`、`target/`、`dist/`、`build/`
- `.worktrees/`、`test-artifacts/`
- 技能系统内部文档（`.trae/skills/`、`.agents/skills/`、`.opencode/skills/` 的 SKILL.md 及附属文件）
- `references/` 外部参考项目

**1.2 问题诊断清单**

扫描后，按以下维度诊断问题：

| 问题类型 | 诊断标准 | 示例 |
|----------|----------|------|
| 根目录散落 | 项目根目录存在超过 5 个 `.md` 文件 | `AGENTS.md`、`CONTEXT.md`、`SECURITY.md` 等散落根目录 |
| 层级过深 | 单条路径超过 4 级目录嵌套 | `docs/a/b/c/d/e/file.md` |
| 层级过浅 | 单个目录下超过 20 个文件无子目录分组 | `docs/` 下 30+ 个文件直接平铺 |
| 命名不一致 | 混用中文/英文/下划线/连字符/日期前缀 | `知识沉淀/` 与 `development/` 混用 |
| 空目录/孤儿文件 | 目录为空或只有一个无关联文件 | 空目录无 README.md |
| 重复/过期内容 | 多个文件内容高度重叠，或日期过期的临时文档 | 同一主题的 `-v1.md`、`-v2.md`、`-final.md` |
| 缺少索引 | 目录下无 README.md 作为入口 | 3 级子目录没有 README.md |
| 跨引用断裂 | 文档中的链接指向已移动/删除的文件 | `[详见](../old-path/file.md)` 指向不存在的路径 |

**1.3 输出诊断报告**

将诊断结果以表格形式呈现给用户，标注严重程度和影响范围，**等待用户确认后再进入阶段 2**。

### 阶段 2：方案设计（Proposal）

**2.1 文档分类体系（动态调整）**

> **重要**：以下分类体系是**起始参考模板**，不是固定不变的。每次执行整理时，必须根据阶段 1 的诊断结果和项目的实际文档特征，**动态调整**分类体系——可以新增类别、合并冗余目录、删除不必要的目录、调整子目录划分。

**动态调整规则**：

| 操作 | 触发条件 | 示例 |
|------|----------|------|
| 新增类别 | 诊断发现某类文档数量 >= 5 且无现有目录可归入 | 项目有大量 API 文档 → 新增 `api/` |
| 合并目录 | 两个目录下的文档总数 < 5 且主题相近 | `setup/` + `workflows/` → 合并为 `guides/` |
| 删除空目录 | 诊断确认某目录在当前项目中无对应文档 | 无设计系统 → 删除 `design-system/` |
| 调整子目录 | 子目录下文件过多或过少 | `browser/` 下 30+ 文件 → 按子主题拆分 |
| 重命名目录 | 原名称不够准确或不符合命名规范 | `operations/` → `user-guides/` |

**调整流程**：

1. 基于阶段 1 诊断报告，列出当前项目的文档类型分布
2. 对照参考模板，识别需要调整的部分
3. 生成调整后的分类树（标注与模板的差异），提交用户确认
4. 确认后以此作为阶段 3 的执行蓝图

**2.1.1 整理完成后同步更新技能文件**

全部整理完成后（阶段 4 验证通过），必须将**实际采用的新分类体系**回写到本技能文件（即此 `SKILL.md`），替换"参考模板"中的分类树，确保技能文件始终反映当前项目的真实文档结构。同步更新规则：

- 仅更新 `2.1` 节中的分类树代码块
- 保留 `...` 占位符表示可按需扩展
- 不修改其他章节内容（除非命名规范等也发生了变更）

**根目录保留文件（最小化原则）**：

根目录仅保留以下项目级文档，其余全部移入 `docs/`：

| 文件 | 说明 |
|------|------|
| `README.md` | 项目总览入口 |
| `AGENTS.md` | AI Agent 治理规则总入口 |
| `CONTRIBUTING.md` | 贡献指南 |
| `SECURITY.md` | 安全策略 |
| `CONTEXT.md` | 领域术语表 |
| `FUTURE-ROADMAP.md` | 远期路线图 |
| `LICENSE` | 许可证 |
| `CHANGELOG.md` | 变更日志（如有） |

**2.2 命名规范**

| 规则 | 说明 | 示例 |
|------|------|------|
| 目录名 | 英文 kebab-case | `knowledge-base/`、`ui-manual/` |
| 文件名 | 英文 kebab-case，描述性 | `browser-tab-audio-control.md` |
| 日期前缀 | `YYYY-MM-DD-` 格式，仅用于时序性文档 | `2026-07-15-startup-overlay.md` |
| 索引文件 | 每个目录下必须有 `README.md` | `docs/architecture/README.md` |
| 禁止项 | 目录名不使用中文、空格、下划线、大写字母 | ❌ `知识沉淀/`、`UI_Manual/`、`My Docs/` |

**2.3 变更影响评估**

设计方案时必须评估每项变更的影响范围：

- 哪些文件包含了指向被移动/重命名文件的链接？
- 哪些 CI/CD 配置、脚本、代码引用了文档路径？
- 哪些 AGENTS.md / rules 文件中引用了被移动的文档？
- 是否需要更新 `.gitignore`？

**2.4 用户确认**

将完整方案（包括文件移动清单、重命名清单、新增/删除清单）以表格形式呈现，**必须获得用户明确批准后才能进入阶段 3**。

### 阶段 3：执行（Execution）

**3.1 安全前置**

执行前必须：

1. **提醒用户**：建议先 `git commit` 保存当前状态，以便回滚
2. **确认 git 状态**：检查是否有未提交的变更，如有则提醒用户
3. **逐项执行**：按以下顺序操作，每步完成后验证

**3.2 操作顺序**

```
1. 创建新目录结构（mkdir）
2. 移动文件（git mv，保留 git 历史）
3. 重命名文件/目录（git mv）
4. 删除空目录/过期文件（需用户确认）
5. 创建/更新 README.md 索引文件
6. 扫描并更新所有交叉引用
7. 更新相关配置文件
```

**3.3 并行子Agent执行模式（大型文档库）**

当文档库规模较大时（满足以下任一条件），使用并行子 Agent 分工执行，提升效率：

| 触发条件 | 阈值 |
|----------|------|
| 文档文件总数 | >= 100 个 `.md` 文件 |
| 独立领域数 | >= 5 个互不重叠的文档域 |
| 用户明确要求 | 用户说"并行整理"、"分头执行"等 |

**3.3.1 分区策略**

将文档按领域/模块划分为独立分区，每个分区分配给一个子 Agent：

```
分区原则：
├─ 每个分区内的文档不跨分区引用（或跨区引用极少）
├─ 分区之间无共享状态，互不依赖
├─ 每个分区规模适中（10-50 个文件）
└─ 分区边界清晰（按目录或主题划分）

示例分区（基于本项目）：
├─ 分区 A：docs/architecture/ + docs/design-system/ + docs/development/
├─ 分区 B：docs/analysis/ + docs/knowledge-base/
├─ 分区 C：docs/plans/ + docs/specs/
├─ 分区 D：docs/reports/
├─ 分区 E：根目录散落文件 + UIOperationManual/
└─ 分区 F：docs/superpowers/
```

**3.3.2 子Agent任务模板**

每个子 Agent 使用 `Task` 工具（`subagent_type: general_purpose_task`）派遣，任务描述必须包含：

```markdown
## 任务：整理文档分区 [分区名称]

### 分区范围
- 目标目录：[绝对路径列表]
- 涉及文件数：[N] 个

### 具体要求
1. 按以下目标结构整理文件：
   [该分区对应的目标目录树]
2. 使用 `git mv` 移动/重命名文件，保留版本历史
3. 为每个目录创建/更新 README.md 索引
4. 不要修改文件内容（仅移动和重命名）
5. 不要执行阶段 4 验证（留待主 Agent 统一验证）

### 排除范围
- 不触碰技能目录（.trae/skills/、.agents/skills/、.opencode/skills/）
- 不触碰 references/ 外部参考项目
- 不触碰其他分区范围的目录

### 命名规范
- 目录名：英文 kebab-case
- 文件名：英文 kebab-case
- 禁止中文、空格、下划线、大写字母出现在目录名中
```

**3.3.3 主Agent调度流程**

```
1. 根据方案设计中的分类树，划分分区
2. 并行派遣所有子 Agent（一次 `Task` 调用中发送多个子 Agent）
3. 等待所有子 Agent 完成
4. 主 Agent 逐一检查每个分区的执行结果
5. 发现问题 → 主 Agent 直接修复（或重新派遣子 Agent）
6. 执行跨分区操作：
   ├── 更新跨分区交叉引用（子 Agent 不会处理跨区引用）
   ├── 创建/更新 docs/README.md 总入口
   └── 更新根目录 AGENTS.md 等文件
7. 进入阶段 4 统一验证
```

**3.3.4 主Agent验证与修复**

子 Agent 完成后，主 Agent 必须执行以下检查：

| 检查项 | 方法 | 发现问题时的处理 |
|--------|------|------------------|
| 文件是否全部到位 | 对比方案清单与实际文件列表 | 补充遗漏的移动操作 |
| 目录结构是否正确 | 对比方案中的目标树 | 调整目录结构 |
| 命名是否规范 | 检查目录名/文件名 | 重命名不符合规范的文件 |
| README.md 是否完整 | 检查每个目录的索引文件 | 补充或修正 README.md |
| 跨分区引用是否断裂 | Grep 搜索跨分区链接 | 更新跨分区引用路径 |
| 是否有越界操作 | 检查子 Agent 是否修改了排除范围 | 回滚越界变更 |

**注意事项**：
- 子 Agent 不处理跨分区交叉引用，统一由主 Agent 在汇总阶段处理
- 子 Agent 不执行阶段 4 验证，统一由主 Agent 执行
- 如果某个子 Agent 失败，主 Agent 可重新派遣或自行接管该分区
- 并行模式下，阶段 4 验证尤为重要——因为子 Agent 之间缺乏协调，可能产生不一致

**3.4 交叉引用更新**

文件移动/重命名后，必须扫描以下位置并更新引用：

| 扫描范围 | 扫描内容 |
|----------|----------|
| 所有 `.md` 文件 | Markdown 链接 `[text](path)` |
| `AGENTS.md` | 指向被移动文档的链接 |
| `.trae/rules/*.md` | 规则文件中的 "相关文件" 链接 |
| `.agents/rules/*.md` | 同上 |
| `docs/README.md` | 文档总入口的链接 |
| `.github/workflows/*.yml` | CI 配置中的文档路径引用 |
| `package.json` | 脚本中的文档路径（如有） |

**交叉引用更新规则**：

- 使用 `Grep` 搜索旧路径，用 `Edit` 逐个替换为新路径
- 相对路径需要根据新旧位置重新计算
- 更新后列出所有被修改的文件供用户审查

**3.5 README.md 索引模板**

每个目录的 `README.md` 使用以下模板：

```markdown
# <目录名称>

<一句话描述此目录的文档范围>

## 目录

- [文件1](./file-1.md) — 描述
- [文件2](./file-2.md) — 描述

## 子目录

- [子目录1](./subdir-1/) — 描述
```

### 阶段 4：验证（Validation）

执行完成后，自动进行以下验证：

**4.1 链接有效性检查**

- 扫描所有 `.md` 文件中的相对链接 `[text](./path)` 和 `[text](../path)`
- 验证每个链接指向的文件/目录是否存在
- 报告所有断链

**4.2 结构完整性检查**

- 每个非叶子目录是否有 `README.md`？
- 是否有空目录残留？
- 是否有文件未被任何索引引用？

**4.3 命名规范检查**

- 所有目录名是否符合 kebab-case？
- 是否还有中文目录名残留？
- 文件名是否符合规范？

**4.4 输出验证报告**

以表格形式输出验证结果，标注通过/失败项。

## 关键原则

### 最小变更原则

- 只移动/重命名确实需要整理的文件，不动已经结构良好的部分
- 不删除任何内容，除非用户明确要求
- 优先使用 `git mv` 保留版本历史

### 渐进式整理

- 对于大型文档库，可分批次整理（按领域/模块分批）
- 每批整理完成后验证再继续下一批

### 用户主导

- 诊断报告和方案设计阶段必须获得用户批准
- 任何不确定的操作（删除、合并）必须询问用户
- 不擅自决定文档归属，分类不明确时列出选项让用户选择

### 不越界

- 不修改文档内容本身（仅更新交叉引用路径）
- 不修改代码文件（除非代码中硬编码了文档路径）
- 不修改技能系统文件（`.trae/skills/`、`.agents/skills/`、`.opencode/skills/`）
- 不修改 `references/` 外部参考项目

## 常见场景指南

### 场景 1：根目录散落大量 .md 文件

1. 列出根目录所有 `.md` 文件
2. 对照"根目录保留文件"清单，标记需要移入 `docs/` 的文件
3. 为每个文件确定目标位置
4. 移动后更新 `docs/README.md` 和根目录 `AGENTS.md`

### 场景 2：中文目录名不规范

1. 扫描所有中文目录名
2. 翻译为英文 kebab-case（如 `知识沉淀/` → `knowledge-base/`）
3. 使用 `git mv` 重命名
4. 更新所有引用旧路径的链接

### 场景 3：单个目录下文件过多

1. 识别目录中超过 20 个文件的目录
2. 按主题/时间/模块分组
3. 创建子目录并移动文件
4. 为每个子目录创建 README.md 索引

### 场景 4：重复/过期文档清理

1. 识别命名相似的文件（如 `*-v1.md`、`*-v2.md`、`*-final.md`）
2. 识别日期超过 6 个月的临时报告
3. 列出候选文件，让用户决定保留/归档/删除
4. 如保留多个版本，移入 `archive/` 子目录

## 禁止行为

- 未经用户确认直接移动/删除文件
- 修改文档内容（仅允许更新交叉引用路径）
- 在技能目录（`.trae/skills/` 等）中执行整理操作
- 修改 `references/` 外部参考项目
- 创建空的占位文件
- 移动 `.gitignore` 中已排除的文件
- 忽略 `git mv` 使用普通 `mv` 导致丢失版本历史
