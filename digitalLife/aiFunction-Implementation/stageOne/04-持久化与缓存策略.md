# 持久化与缓存策略实施计划

## 模块概述

**包名**: `@ai-digital-life/storage`

**优先级**: P0

**目标**: 为桌面应用提供可靠的本地数据存储、缓存、检查点元数据、敏感信息保护和版本演进基础。

第一阶段的存储系统必须服务三件事：

1. 恢复运行状态。
2. 支撑索引、任务、审批和日志等基础能力。
3. 不让敏感信息和脏数据成为未来架构债务。

## 修订结论

相较原方案，第一阶段应做以下收敛：

- 不把缓存当成真实数据源。
- 不使用 `safeStorage + localStorage` 作为“系统密钥链”方案。
- 不让数据库表结构与工作区 / 会话 / 任务 / 审批文档各写各的。
- 检查点在 Phase 0 只要求支撑恢复和审计，不要求提前承担完整变更引擎职责。

## 存储分层

### 1. 强一致持久化数据

必须可靠落盘，重启后可恢复：

- 工作区元数据
- 会话摘要
- 任务与审批记录
- 索引元数据
- 用户配置
- 数据库迁移状态

### 2. 可重建缓存数据

可删除、可失效、可重算：

- 文件树缓存
- 符号索引缓存
- 仓库地图缓存
- 搜索结果缓存

### 3. 敏感数据

必须与普通配置和缓存分层：

- API Key
- Token
- 凭据
- 未来的远端服务认证材料

### 4. 临时数据

仅服务运行过程，不作为长期状态：

- 临时索引分片
- 运行态健康快照
- 调试级缓存

## 本地目录约定

建议统一使用应用数据目录：

```text
data/
├─ app.db
├─ cache/
│  ├─ retrieval/
│  └─ temp/
├─ checkpoints/
├─ logs/
├─ backups/
└─ state/
```

要求：

- SQLite 只存结构化元数据
- 大体积缓存文件走文件目录
- 检查点与备份独立于普通缓存

## 存储策略表

| 数据类型 | 介质 | 生命周期 | 说明 |
|----------|------|----------|------|
| 工作区、会话、任务、审批 | SQLite | 长期 | 核心业务元数据 |
| 索引元数据 | SQLite | 中期 | 用于校验和恢复增量索引 |
| 文件树、符号索引缓存 | SQLite/文件 | 可重建 | 删除后可重算 |
| 仓库地图摘要 | 文件 | 短中期 | 模型消费型缓存 |
| 检查点元数据 | SQLite | 中期 | 记录恢复点和关联资源 |
| 检查点内容 | 文件 | 中期 | 独立文件存储，便于清理 |
| 凭据与密钥 | 系统凭据存储 | 长期 | 不进入普通配置或缓存 |

## 数据库 Schema 基线

第一阶段建议统一以下表结构，避免各模块文档不一致：

```sql
CREATE TABLE IF NOT EXISTS workspaces (
  id TEXT PRIMARY KEY,
  path TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  type TEXT NOT NULL,
  status TEXT NOT NULL,
  config_json TEXT NOT NULL,
  git_snapshot_json TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  last_opened_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS sessions (
  id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL,
  status TEXT NOT NULL,
  approval_mode TEXT NOT NULL,
  current_task_json TEXT,
  summary_json TEXT,
  checkpoint_id TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  FOREIGN KEY (workspace_id) REFERENCES workspaces(id)
);

CREATE TABLE IF NOT EXISTS retrieval_indexes (
  workspace_id TEXT PRIMARY KEY,
  version TEXT NOT NULL,
  status TEXT NOT NULL,
  file_count INTEGER NOT NULL,
  symbol_count INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  FOREIGN KEY (workspace_id) REFERENCES workspaces(id)
);

CREATE TABLE IF NOT EXISTS tasks (
  id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL,
  session_id TEXT NOT NULL,
  parent_id TEXT,
  type TEXT NOT NULL,
  status TEXT NOT NULL,
  priority TEXT NOT NULL,
  description TEXT NOT NULL,
  operations_json TEXT NOT NULL,
  result_json TEXT,
  error_json TEXT,
  approval_id TEXT,
  checkpoint_id TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  started_at INTEGER,
  completed_at INTEGER
);

CREATE TABLE IF NOT EXISTS approvals (
  id TEXT PRIMARY KEY,
  task_id TEXT NOT NULL,
  workspace_id TEXT NOT NULL,
  risk_level TEXT NOT NULL,
  decision TEXT,
  request_json TEXT NOT NULL,
  reason TEXT,
  approved_by TEXT,
  created_at INTEGER NOT NULL,
  decided_at INTEGER,
  expires_at INTEGER
);

CREATE TABLE IF NOT EXISTS checkpoints (
  id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL,
  workspace_id TEXT NOT NULL,
  type TEXT NOT NULL,
  description TEXT,
  manifest_json TEXT NOT NULL,
  storage_path TEXT,
  created_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS migrations (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  applied_at INTEGER NOT NULL
);
```

## 检查点策略

第一阶段不建议直接做“全量项目快照”。成本高、清理难、恢复慢。

Phase 0 的检查点应该采用：

- 元数据记录 + 关联文件清单
- 小范围目标文件快照
- 高风险操作前的 Git 状态记录
- 可选的压缩归档文件

适用场景：

- 工作区打开前后状态标记
- 索引前的工作区快照元信息
- 任务执行前的恢复点
- 审批通过后操作前的安全点

## 缓存策略

### 内存缓存

适合：

- 高频短生命周期查询
- UI 状态衍生数据
- 最近一次索引状态

要求：

- TTL
- 最大容量
- LRU 或近似 LRU 淘汰

### 文件缓存

适合：

- 仓库地图摘要
- 搜索结果缓存
- 大对象序列化结果

要求：

- TTL
- 版本戳
- 清理任务

## 敏感数据策略

### 结论

第一阶段应采用：

- **首选**: `keytar` 或系统凭据管理器
- **可选回退**: Electron `safeStorage` 加密后写入受控文件

不建议：

- 使用 `localStorage`
- 将密钥混入普通 YAML / JSON 配置
- 将敏感信息写进日志或错误报告

### 日志脱敏

日志与错误报告至少应脱敏：

- 密钥字段
- Token 字段
- 认证头
- 用户绝对路径
- 未来可能包含凭据的命令参数

## 与其它模块的边界

- `storage` 提供持久化与缓存能力，不负责任务编排
- `workspace` 负责决定何时创建检查点
- `task` 负责决定哪些任务需要关联检查点
- `retrieval` 负责索引内容生成，`storage` 只负责存取

## 验收标准

- [ ] 重启应用后能恢复最近工作区与必要会话摘要
- [ ] 数据库 Schema 与工作区、会话、任务、审批文档一致
- [ ] 缓存删除或失效后不会影响正确性
- [ ] 检查点可为高风险操作提供恢复依据
- [ ] 敏感数据不会以明文落盘
- [ ] 数据目录结构清晰，可迁移、可清理、可备份

## 延后实现

- 内容寻址 Blob 存储
- 分层缓存 L1/L2
- 全量仓库快照
- 远端同步与跨设备备份
