# 系统架构与工程基线

## 文档定位

这份文档定义第一阶段的总边界。`stageOne` 不再只是“基础模块清单”，而是 **Phase 0：可运行的桌面应用底座**。

第一阶段必须同时满足三件事：

1. 有清晰的系统分层和依赖规则。
2. 有最小可运行的桌面壳层和安全边界。
3. 有足够稳健的基础设施，能够支撑 Phase 1 的核心闭环实现。

## 第一阶段目标

第一阶段的目标不是实现完整 AI 编程闭环，而是建立后续闭环赖以成立的运行环境：

`启动应用 → 打开工作区 → 持久化状态 → 构建索引 → 展示健康状态/日志/审批壳层 → 安全退出与恢复`

做到这一步，后续的模型接入、Patch 预览、命令执行、验证与回滚才有稳定承载面。

## 第一阶段正式交付物

### 必须交付

- 最小可运行桌面壳层
- 主进程 / Preload / Renderer / Worker 的进程边界
- 类型化 IPC 通道与权限白名单
- Monorepo 工程骨架与包边界
- 配置、日志、错误恢复、持久化、工作区、索引、任务审批、迁移升级
- 启动恢复、崩溃恢复、健康检查、审计基础能力

### 只做骨架，不做完整能力

- 模型接入与路由
- Prompt 工程
- 命令执行与终端交互
- Patch / Diff 应用引擎
- 智能体任务规划

这些能力不是第一阶段的核心交付物，但第一阶段必须为它们预留清晰的位置和接口。

## 分层架构

### 1. 桌面壳层

负责窗口、布局、页面路由、状态展示和用户交互。

不负责：

- 业务规则
- 权限判定
- 直接文件系统访问
- 直接进程管理

### 2. 应用服务层

负责工作区、会话、索引、任务、审批、配置等应用级服务编排。

特点：

- 面向用例组织
- 依赖基础设施接口
- 不依赖具体 UI

### 3. 执行与系统接入层

负责 Git、文件系统、子进程、文件监听、系统目录、密钥存储等系统能力适配。

要求：

- 所有高风险动作可审计
- 默认不可直接暴露给 Renderer
- 统一通过主进程或受控 Worker 访问

### 4. 基础设施层

负责配置、日志、错误、存储、迁移、事件总线、健康检查等通用能力。

要求：

- 稳定
- 可测试
- 尽量无业务语义

## 进程拓扑

### Main

职责：

- 应用启动与退出
- BrowserWindow 生命周期
- IPC 注册与权限校验
- 本地数据目录管理
- 原生能力封装
- Worker 拉起与监管

### Preload

职责：

- 提供最小、安全、类型化桥接
- 暴露白名单 API
- 屏蔽 Node/Electron 原始能力

### Renderer

职责：

- 页面、交互、状态展示
- 编辑器与面板渲染
- 健康状态、日志、审批与工作区信息呈现

限制：

- 不直接访问 Node API
- 不直接访问数据库、文件系统、命令执行接口

### Worker

职责：

- 索引
- 搜索
- 仓库地图构建
- 长时任务
- 可中断的后台处理

## 推荐工程骨架

```text
ai-digital-life/
├─ apps/
│  └─ desktop/
│     ├─ main/
│     ├─ preload/
│     └─ renderer/
├─ workers/
│  └─ indexer/
├─ packages/
│  ├─ kernel/
│  ├─ events/
│  ├─ config/
│  ├─ logger/
│  ├─ errors/
│  ├─ storage/
│  ├─ workspace/
│  ├─ retrieval/
│  ├─ task/
│  └─ migration/
├─ configs/
├─ scripts/
├─ tests/
├─ docs/
└─ package.json
```

第一阶段不建议一开始就引入过多“未来包”。未进入实现范围的能力，先用接口目录或占位文档表达，不要在代码树中提前做大量空包。

## 依赖规则

1. `apps/desktop` 可以依赖 `packages/*`，但 `packages/*` 不能反向依赖 `apps/*`。
2. `kernel` 不依赖任何业务包。
3. `events`、`config`、`logger`、`errors`、`storage` 属于 Phase 0 基础设施内核。
4. `workspace`、`retrieval`、`task` 只能依赖基础设施层和系统适配接口，不能直接依赖 UI。
5. 任何系统调用能力都不能从 Renderer 直接触发，必须经过 Main 注册的受控 IPC。
6. 禁止循环依赖，禁止“低层依赖高层”。

## 第一阶段最小运行路径

第一阶段完成后，至少要能稳定演示以下路径：

1. 启动桌面应用。
2. 读取全局配置并初始化日志系统。
3. 选择并打开工作区。
4. 识别项目根、检测 Git 状态、恢复最近会话摘要。
5. 后台建立基础索引并回传进度。
6. 展示日志、健康状态、任务列表和审批壳层。
7. 异常退出后恢复上次工作区和必要状态。

## 第一阶段不应做的事

- 不把完整模型执行链路硬塞进 Phase 0
- 不提前做多智能体编排
- 不提前做插件市场
- 不提前做复杂团队协作
- 不为远期能力做过度抽象

## 非功能基线

### 架构基线

- 模块边界明确
- 无循环依赖
- IPC 接口类型化
- 系统权限最小化

### 可靠性基线

- 关键状态可恢复
- 崩溃后不丢失必要元数据
- 高风险操作有审计记录
- Worker 崩溃可被主进程感知和重启

### 可扩展性基线

- UI、应用服务、系统接入、基础设施分层清晰
- 检索、工作区、任务中心互相通过接口协作
- 后续新增模型、工具执行、变更引擎时无需推翻 Phase 0 架构

### 工程基线

- Node.js LTS 作为统一运行时
- pnpm workspace 作为包管理与 monorepo 基础
- TypeScript 严格模式
- ESLint + Prettier + Vitest + Playwright

## 结论

第一阶段的本质不是“先做一些工具模块”，而是 **建立一个能承载后续 AI 桌面代理能力的可运行、可恢复、可治理的系统底座**。所有 Phase 0 文档都应服从这个目标。
