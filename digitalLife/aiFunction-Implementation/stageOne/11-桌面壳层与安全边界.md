# 桌面壳层与安全边界

## 模块定位

这个模块是第一阶段新增的正式交付物，用于补足现有 `stageOne` 中缺失的运行容器与安全边界。

它的目标不是实现复杂 UI，而是提供一个 **最小可运行、权限可控、进程职责明确** 的桌面应用外壳。

## 第一阶段目标

第一阶段的桌面壳层至少要做到：

1. 应用可启动、可关闭、可恢复最近工作区。
2. Renderer 不直接获得 Node/Electron 高危能力。
3. 所有敏感系统能力通过 Main 统一注册和授权。
4. 后台长任务与 UI 解耦。
5. 崩溃、异常和健康状态可观察。

## 首批薄切片实现约束

首批实现应优先交付一条最小但真实的运行路径，而不是先铺多个占位模块：

- 启动桌面壳层
- 读取配置并初始化日志
- 拉起 Retrieval Worker
- 通过 Preload 暴露 `app.getInfo`、`app.getHealth`、`workspace.listRecent`、`workspace.open`
- 展示最近工作区、健康状态、检索状态和日志摘要
- 重启后恢复最近工作区与基础窗口状态

首批不要求：

- 文件系统浏览器式复杂交互
- 多窗口与复杂布局
- 终端、命令执行或高风险操作入口

## 进程职责

### Main

负责：

- 应用生命周期
- 窗口创建与恢复
- 安全配置
- IPC 白名单注册
- Worker 生命周期管理
- 本地数据目录初始化
- 原生能力适配

### Preload

负责：

- 用 `contextBridge` 暴露有限 API
- 参数校验
- 将 IPC 细节隐藏在受控接口后面

禁止：

- 暴露 `ipcRenderer.send`
- 暴露任意执行接口
- 暴露文件系统原语

### Renderer

负责：

- 工作区选择页
- 首页 / 健康状态页
- 日志查看页
- 审批中心壳层
- 设置页

### Worker

负责：

- 索引构建
- 搜索
- 文件监听后的增量计算
- 长时后台任务

## IPC 设计原则

### 白名单通道

只允许暴露明确的能力接口，例如：

- `app.getInfo`
- `app.getHealth`
- `workspace.open`
- `workspace.listRecent`
- `index.start`
- `index.getStatus`
- `task.list`
- `approval.listPending`
- `log.tail`

### 输入输出类型化

每个 IPC 通道都必须：

- 有明确请求类型
- 有明确响应类型
- 有失败返回结构

建议统一返回：

```ts
type IpcResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: { code: string; message: string } };
```

### 禁止透传高危能力

禁止从 Renderer 直接触达：

- 任意命令执行
- 任意路径读写
- 任意进程启动
- 任意网络请求代理
- 任意数据库语句执行

## 安全基线

### BrowserWindow

- `contextIsolation: true`
- `sandbox: true`
- `nodeIntegration: false`
- `enableRemoteModule: false`
- 禁止在 Renderer 中直接使用 Electron/Node 全局对象

### 路径边界

第一阶段要明确三类目录：

- 应用目录
- 用户数据目录
- 当前工作区目录

任何写入动作都必须声明写入目标属于哪一类目录。

### 权限边界

第一阶段至少区分：

- 只读操作
- 低风险写操作
- 高风险系统操作

高风险系统操作默认不开放给桌面壳层，只保留接口与审批入口。

## 推荐目录结构

```text
apps/desktop/
├─ main/
│  ├─ bootstrap/
│  ├─ ipc/
│  ├─ security/
│  ├─ workers/
│  └─ index.ts
├─ preload/
│  ├─ api/
│  ├─ validators/
│  └─ index.ts
└─ renderer/
   ├─ app/
   ├─ pages/
   ├─ stores/
   ├─ components/
   └─ index.tsx
```

## 启动流程

1. Main 初始化数据目录、配置、日志。
2. Main 拉起 Worker 管理器。
3. Main 创建窗口并装载 Preload。
4. Renderer 请求应用健康信息与最近工作区列表。
5. 用户打开工作区后，Main 调用工作区服务与索引服务。
6. Worker 回传索引进度，Renderer 仅做展示。

## 恢复与健康检查

第一阶段建议具备以下机制：

- 启动时检查上次异常退出标记
- Worker 心跳或状态上报
- 索引中断后可重试
- 关键依赖初始化失败时给出可读错误页

## 第一阶段验收标准

- [ ] 应用可以正常启动并打开主窗口
- [ ] Renderer 无 Node 直连能力
- [ ] 受控 IPC 通道具备统一错误返回格式
- [ ] 可以打开工作区并展示最近工作区列表
- [ ] 可以显示索引状态、系统健康状态和日志摘要
- [ ] Worker 异常退出后主进程可感知
- [ ] 应用重启后可恢复最近工作区与基础状态

## 延后实现

- 终端面板
- 实时补全编辑器深度集成
- 复杂多窗口布局
- 自动化浏览器控制
- 完整沙箱执行

第一阶段的重点不是“桌面功能很多”，而是“桌面外壳足够稳，权限边界足够硬”。
