# Agent 执行循环

## 目标

将计划、工具调用、变更预览、审批、验证、回滚串成一个可恢复、可审计、可解释的单 Agent 执行闭环。

## 设计原则

- **单 Agent**：只有一个执行主体，不引入多代理协商
- **Patch First**：默认产出补丁提案，不直接落盘
- **Tool Governed**：所有副作用通过工具协议进入统一执行面
- **Human in the Loop**：高风险步骤暂停审批
- **Resumable**：执行过程具备恢复语义

## 状态机

```
draft → planning → ready → executing
  executing → waiting-approval → executing
  executing → applying → verifying → succeeded
  executing → failed → rolled-back
  任意状态 → aborted
```

### 状态规则


| 状态               | 允许的操作                  |
| ---------------- | ---------------------- |
| planning         | 读上下文、调用模型生成计划，不允许副作用工具 |
| executing        | 只读工具 + 低风险提案型工具        |
| waiting-approval | 仅等待用户决策                |
| applying         | 仅通过变更管理模块落盘            |
| verifying        | 仅执行允许的验证命令             |
| failed           | 可重试、降级或回滚              |


## 执行流程

### 1. 计划生成

用户发送任务后，Agent 先生成结构化计划：

- 目标摘要
- 执行步骤列表
- 每步的风险等级
- 验证动作
- 预期的成功/失败出口

### 2. 工具执行

步骤通过统一工具网关执行，不允许模型直接调用底层模块。

必备工具域：

- 文件读取与搜索
- 编辑计划生成
- 终端命令执行
- 变更预览与应用
- 回滚

### 3. 审批暂停

以下场景进入 `waiting-approval`：

- 删除文件
- 覆盖多文件修改
- 安装依赖
- 运行未知脚本
- 高风险命令

### 4. 变更应用

模型产出修改后：

- 先形成 PatchSet 进入 diff 预览
- 用户按文件/按块接受
- 全部接受后进入 applying 状态

### 5. 验证与总结

应用成功后自动运行验证命令，验证结果结构化回传到对话与编辑器，输出最终执行总结。

## 失败处理


| 策略  | 适用场景                      |
| --- | ------------------------- |
| 重试  | 网络抖动、流式中断、临时锁冲突           |
| 降级  | 计划质量低→建议模式，自动上下文失败→显式引用模式 |
| 回滚  | 补丁应用失败、验证失败、状态不一致         |


## 持久化

执行状态必须持久化到数据库，至少包括：

- Agent 运行记录（runs）
- 执行计划（plans）
- 执行步骤（steps）
- 工具调用记录（tool_invocations）
- 恢复标记（recovery_markers）

恢复时区分：未落盘的计划、已生成未应用的 Patch、已应用未验证、验证失败待处理。

## 多 Agent 扩展点

- 状态机预留 `delegated` 状态，未来可将子任务分发给子 Agent
- 工具调用记录可标记来源 Agent ID
- 计划步骤可标记 `assignee`（当前固定为主 Agent）

## 验收标准

- 执行前生成清晰计划
- 步骤按状态机推进
- 高风险步骤暂停审批
- 所有工具调用有记录
- Patch 应用与验证在同一运行时链路
- 失败可重试、降级或回滚
- 中断后可恢复或安全中止
- 输出结构化执行总结
