# 变更管理

## 目标

将所有 Agent 生成的修改统一收束为可审查、可局部接受、可验证、可回滚的 PatchSet。

## Patch First 原则

Agent 默认生成 PatchSet 提案，不直接落盘。流程：

1. Agent 产出修改 → 构建 PatchSet
2. 用户在 diff 视图中审查
3. 用户按文件或按 hunk 接受/拒绝
4. 创建检查点
5. 原子写入已接受的变更
6. 运行验证
7. 失败则回滚到检查点

## PatchSet 模型

一个 PatchSet 包含：

- 唯一 ID，关联到执行 Run
- 描述与风险等级
- 多个 FilePatch（每个文件的变更）
- 每个 FilePatch 包含多个 Hunk（独立的修改块）
- 状态：draft → pending-review → approved → applied → validated / rolled-back

## 应用流程

1. 原始内容哈希校验（确保文件未被外部修改）
2. 冲突检测：编辑器脏文件、外部修改、内容漂移
3. 基于已接受 hunk 重建目标内容
4. 创建检查点（快照原始文件）
5. 原子写入
6. 写入审计记录

## 冲突检测

至少检测：

- 编辑器中未保存的修改
- 外部程序对文件的修改
- Patch 生成后到应用前的文件内容变化

冲突时不静默覆盖，必须提示用户。

## 检查点

- 记录原始文件内容的快照
- 关联到 PatchSet ID 和 Run ID
- 支持全量恢复和按文件恢复
- 应用崩溃后可从检查点恢复

## 验证协同

变更管理模块不执行验证命令本身，但负责：

- 传递推荐验证命令（构建、测试、lint）
- 记录验证结果
- 失败时提供回滚选项

## 审计记录

每次变更至少记录：

- 触发来源（哪个 Run / Step）
- 用户接受了哪些 hunk
- 是否执行验证
- 验证结果
- 是否回滚

## 延后实现

- unified diff 导入导出
- 三方合并界面
- 多候选补丁投票

## 验收标准

- 所有 AI 修改默认先进入 PatchSet
- 用户可按文件或按块接受
- 应用前创建检查点
- 冲突被检测和提示
- 失败可回滚
- 全流程可审计
