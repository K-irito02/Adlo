# 第二阶段：交互式 MVP 与单 Agent 工作流（Phase 1）

## 复核结论

在审视 `stageTwo`、`expectedFunctionality` 和当前 `ai-digital-life` 代码仓后，可以得出一个明确结论：

- 现有 `stageTwo` 已覆盖第二阶段的大部分模块能力
- 但它 **还不足以直接支撑“单 Agent 完整工作流”**
- 主要缺口不是又少了几个工具，而是 **缺少统一的执行编排层**

原方案的问题主要集中在五点：

1. 8 个模块基本是并列关系，缺少一个把计划、工具调用、审批、补丁、验证、回滚串起来的中枢。
2. 对 `expectedFunctionality/02-AI智能体引擎` 中“工具调用协议、任务规划与执行控制、命令闭环反馈”的最小必要切片没有前置吸收。
3. 多处设计仍偏“模块能力清单”，没有形成面向当前 monorepo 的真实落地边界。
4. Patch、命令、审批、检查点、审计虽然分别出现，但跨模块契约不统一。
5. Phase 1 与 Phase 2 的边界不够锋利，容易在开发时把“单 Agent 可控闭环”做成“多 Agent 平台预演”。

本次更新后的第二阶段定义为：

> 在 Phase 0 稳定底座之上，交付一个 **桌面优先、工作区优先、Patch First、Human in the Loop** 的单 Agent 编程闭环。

## 当前阶段目标

第二阶段必须让用户能够稳定完成这条主链路：

`打开工作区 -> 发起任务 -> Agent 生成计划 -> 收集上下文 -> 调用工具 -> 产出补丁 -> 预览审批 -> 应用修改 -> 运行验证 -> 总结结果 -> 必要时回滚`

这里的“单 Agent”不是多角色多代理编排，而是一个受治理的执行运行时，内部可以有：

- `planning`
- `executing`
- `waiting-approval`
- `applying`
- `verifying`
- `summarizing`

这些阶段状态，但 **不引入 Phase 2 的多代理自治网络**。

## 当前实现状态

当前代码仓已经实现了这条主链路的大部分核心节点：

- `React + Zustand` 工作区主界面
- `DeepSeek -> MiniMax` 真实 provider 路由与健康检查
- 非敏感 provider 设置持久化与桌面端修改入口
- 计划生成、Patch 预览、hunk 决策、应用、验证、自动回滚
- 一轮保守自动修复预览
- 命令审批、执行、失败重试与恢复
- 外部文件修改检测与冲突提示
- Monaco 编辑器、诊断定位、选区发送
- Playwright 验收覆盖

当前仍未完全交付的能力主要是：

- 真正的流式模型请求和取消
- Prompt 版本管理与回滚
- 更完整的上下文摘要与缓存层
- unified diff 导入导出
- 更强的自动修复多轮循环
- 更完整的命令输出可视化和终端交互

## 现代 AI 编程产品能力基线（2026-04 调研）

结合当前主流产品的官方文档与产品页，第二阶段应主动吸收的共识能力包括：

- 明确区分 `chat / plan / code / verify` 等执行模式，而不是所有请求共用一条模糊通道
- 持久规则与记忆层，保证项目约束可重复注入
- 代码库理解、搜索、引用、工具调用是 Agent 主路径的一部分，不是外挂能力
- 命令执行、补丁应用、代码审查都要经过可见、可控的中间层
- 检查点、审批、Hooks/规则、结构化 Slash 命令，已经成为现代 AI 编程软件的标配治理面

这意味着本项目第二阶段不应只追求“能对话、能改文件”，而应至少达到：

- 有计划
- 有规则
- 有工具协议
- 有补丁中间层
- 有验证闭环
- 有恢复与审计

但同时必须控制范围，不把“后台自治、多 Agent、云执行网络”提前塞进当前阶段。

## 单 Agent 边界

### 第二阶段必须交付

- 单 Agent 计划生成与顺序执行
- 工具调用统一入口与执行记录
- 高风险动作暂停审批
- Patch First 变更提案与局部接受
- 应用后自动验证与失败回滚
- 结构化执行总结与结果可追溯

### 第二阶段明确不做

- 多 Agent 并行自治
- 长时间后台自治任务网络
- 通用插件市场
- 云端浏览器/远程沙箱编排
- 复杂 DAG 工作流引擎

## 最小可运行薄切片

### Slice A：可用对话闭环

- 模型接入
- 流式对话
- `@file` 引用
- 工作区级上下文注入

### Slice B：可控代码修改

- Agent 计划
- 文件读取与搜索
- 生成 PatchSet
- diff 预览
- 局部接受

### Slice C：验证与恢复

- 命令审批
- 构建/测试执行
- 结果结构化回传
- 检查点回滚

只有三条 Slice 都打通，第二阶段才算完成。

## 实施顺序

| 顺序 | 交付重点 |
|------|----------|
| 1 | `model-gateway` + `conversation` 跑通单轮流式 |
| 2 | `prompt-engine` + `context-engine` 建立稳定请求构造 |
| 3 | `fs-ops` + `change-engine` 打通 Patch First 链路 |
| 4 | `terminal` + `task` 接入审批、验证、审计 |
| 5 | `agent-runtime` 将计划、执行、应用、验证串成状态机 |
| 6 | `editor` 把 diff、诊断、选择发送与补丁应用接入桌面 UI |
| 7 | 集成测试与恢复测试补齐 |

## 总体验收标准

### 单 Agent 工作流

- [ ] 用户输入任务后，系统先生成结构化计划
- [ ] Agent 可按步骤调用文件、搜索、命令、补丁等工具
- [ ] 高风险步骤会进入审批暂停态
- [ ] 代码修改默认以 PatchSet 方式呈现，不直接盲写
- [ ] 用户可按文件或按块接受修改
- [ ] 应用后可自动执行验证命令并收集结构化结果
- [ ] 验证失败时可回滚到检查点
- [ ] 最终能输出结构化执行总结

### 工程质量

- [ ] 所有 Phase 1 包保持低耦合、高内聚
- [ ] Renderer 不新增越权能力
- [ ] 审批、检查点、审计记录持久化
- [ ] 关键链路具备单测与集成测试
- [ ] 关闭应用后重启可恢复未完成执行状态或明确降级

## 进入 Phase 2 的门槛

只有当以下条件满足时，才应该进入完整智能体框架阶段：

1. 单 Agent 闭环稳定，主路径可重复成功。
2. 计划、工具调用、审批、补丁、验证、回滚具备统一状态机。
3. 关键高风险动作均可审计与恢复。
4. 当前阶段不再依赖“人工兜底脚本”才能完成核心流程。

## 结论

更新后的 `stageTwo` 不再只是“8 个模块的实施计划集合”，而是一个明确面向当前代码仓的、可在 Phase 1 落地的 **单 Agent 编程工作流方案**。这既覆盖了 `expectedFunctionality` 中第二阶段真正需要的能力，又避免提前滑向 Phase 2 的多智能体复杂度。
