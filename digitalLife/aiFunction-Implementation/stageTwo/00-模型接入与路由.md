# 模型接入与路由实施计划

## 模块概述

**包名**: `@ai-digital-life/model-gateway`

**优先级**: P0

**目标**: 为第二阶段提供统一、可流式、可降级、可追踪的模型调用面，并把模型能力差异显式化，而不是让上层模块直接感知各家 API 细节。

## 在单 Agent 工作流中的职责

该模块不负责“自主规划”，它只负责：

- 管理 provider 适配器
- 提供统一 `chat` / `chatStream` 能力
- 维护模型能力注册表
- 根据阶段与任务类型进行路由
- 提供中断、重试、故障转移和用量追踪

它是 `conversation`、`prompt-engine`、`agent-runtime` 的基础依赖。

## Phase 1 必须交付

- 至少接入 2 个模型提供商
- 统一非流式与流式请求接口
- 能力注册表：上下文长度、工具调用、流式、JSON 输出、成本等级
- 基于任务阶段的路由：`chat` / `plan` / `edit` / `verify`
- 请求级取消
- 故障转移、熔断、超时控制
- Token 与成本用量记录
- 路由决策追踪

## Phase 1 不做

- 多模型竞速
- 自动模型评分学习
- 多模态协议
- 远程 Agent 集群调度

## 当前代码仓映射

推荐新增位置：

```text
ai-digital-life/packages/model-gateway/
```

与现有仓库的关系：

| 当前模块 | 关系 |
|----------|------|
| `config` | 读取 API 配置、默认模型、路由策略 |
| `logger` | 记录调用、失败、熔断、降级 |
| `storage` | 保存用量统计、最近健康状态 |
| `task` | 为高成本或特殊模型请求预留审批策略接入点 |
| `apps/desktop` | 暴露模型配置与状态给 UI |

当前已落地的最小阶段二实现补充：

- 非敏感 provider 元数据通过 `config/config.json` 持久化
- 当前支持 `DeepSeek / MiniMax` 的启用开关、优先级、默认模型 ID
- `Main` 在配置变更后重建 `ModelGateway` 与 `AgentRuntimeService`
- `Renderer` 只通过受控 IPC 读写设置并触发健康检查，不直接请求模型

## 核心设计

### 1. Provider 适配层

每个提供商实现统一接口：

```typescript
export interface ModelProvider {
  id: string;
  models: ModelDescriptor[];
  healthcheck(): Promise<ProviderHealth>;
  chat(request: UnifiedChatRequest): Promise<UnifiedChatResponse>;
  chatStream(
    request: UnifiedChatRequest
  ): AsyncIterable<UnifiedStreamEvent>;
}
```

### 2. 模型能力注册表

```typescript
export interface ModelDescriptor {
  id: string;
  providerId: string;
  displayName: string;
  maxInputTokens: number;
  maxOutputTokens: number;
  supportsStreaming: boolean;
  supportsToolCalls: boolean;
  supportsJsonMode: boolean;
  costTier: 'low' | 'medium' | 'high';
  latencyTier: 'fast' | 'standard' | 'slow';
  recommendedFor: Array<'chat' | 'plan' | 'edit' | 'verify'>;
}
```

### 3. 路由输入维度

路由不能只看“任务类型”，还必须看当前执行阶段：

| 维度 | 示例 |
|------|------|
| 对话场景 | 普通问答、代码解释、补丁生成 |
| 执行阶段 | `planning`、`executing`、`verifying` |
| 成本策略 | 默认、节省、质量优先 |
| 响应形式 | 流式、非流式、结构化 JSON |
| 工具需求 | 是否需要 tool calling |

### 4. 路由策略

默认优先级建议：

`手动指定 > 阶段策略 > 能力匹配 > 成本/延迟策略 > 故障转移`

示例：

- `planning` 优先推理强、结构化输出稳定的模型
- `chat` 优先低延迟流式模型
- `edit` 优先代码可靠性更高、支持工具调用的模型
- `verify-summary` 可降级到更便宜模型

当前代码已支持的最小路由控制：

- 按 provider `enabled` 过滤
- 按 `priority` 升序路由
- 按 provider 配置覆盖默认 `modelId`
- 所有 provider 都失败后才降级到 synthetic fallback

### 5. 流式与取消

必须具备：

- 首包超时
- 全流程超时
- 会话级取消
- 解析异常降级为完整响应或明确错误

### 6. 可观测性

每次调用至少记录：

- `requestId`
- `sessionId`
- `runId`
- `phase`
- `provider`
- `model`
- `latencyMs`
- `promptTokens`
- `completionTokens`
- `routeReason`
- `fallbackUsed`

## 与单 Agent 的接口契约

`agent-runtime` 调用时必须显式传入：

```typescript
export interface UnifiedChatRequest {
  messages: UnifiedMessage[];
  phase: 'chat' | 'plan' | 'edit' | 'verify';
  modelPreference?: string;
  requireToolCalls?: boolean;
  responseFormat?: 'text' | 'json';
  maxOutputTokens?: number;
  metadata: {
    sessionId: string;
    workspaceId: string;
    runId?: string;
    stepId?: string;
  };
}
```

这样路由层才能区分“普通聊天”和“执行步骤中的结构化规划”。

## 实施顺序

1. Provider 抽象与类型统一
2. OpenAI / Claude 双 provider 接入
3. 注册表与路由决策
4. 流式解析与取消
5. 熔断、故障转移、健康状态
6. 用量统计与桌面设置集成

当前桌面设置集成已完成的最小闭环：

- 模型健康状态展示
- provider 开关
- provider 优先级调整
- provider 默认模型 ID 调整
- 手动触发健康检查

## 测试计划

### 单元测试

- provider 请求格式转换正确
- 手动指定模型时跳过自动路由
- 阶段路由能根据 `phase` 正确选择模型
- 熔断器状态切换正确
- 取消请求后流式迭代正确结束

### 集成测试

- 双 provider 流式请求跑通
- 主模型失败后自动切换备选模型
- 同一会话多次请求用量统计准确

## 验收标准

- [ ] 至少接入 2 个模型提供商
- [ ] 对话、规划、编辑、验证四类请求可统一调用
- [ ] 流式响应可逐步回传并支持取消
- [ ] 路由决策可解释且可记录
- [ ] provider 故障时能自动降级
- [ ] Token 与成本统计准确
- [ ] 不同执行阶段能选择合适模型

## 风险与约束

- API Key 只允许通过受控秘密存储读取，不落盘到普通配置
- 不允许把 provider 原始协议泄漏到上层业务
- 不允许由 Renderer 直接发模型请求

## 结论

第二阶段的模型层不应只是“多模型接入”，而应是一个面向单 Agent 工作流的统一模型网关。
