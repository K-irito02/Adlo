# 变更预览与应用实施计划

## 模块概述

**包名**: `@ai-digital-life/change-engine`

**优先级**: P0

**目标**: 把所有 AI 生成的修改统一收束为可审查、可局部接受、可验证、可回滚的 PatchSet，并将其安全地落到工作区。

## 在单 Agent 工作流中的职责

该模块是第二阶段的用户信任核心，负责：

- 构建 PatchSet
- 计算 diff / hunk
- 局部接受与拒绝
- 创建检查点
- 应用补丁
- 冲突检测
- 应用后验证协同
- 回滚

## Phase 1 必须交付

- PatchSet / FilePatch / Hunk 统一模型
- unified diff 导入与导出
- 按文件 / 按块接受
- 应用前创建检查点
- 应用前脏文件与外部变更检测
- 应用后验证协同
- 失败回滚
- 审计日志

## Phase 1 不做

- 三方合并界面
- 高级 Git 工作树操作
- 多候选补丁投票
- 团队审批流

## 核心设计

### 1. 统一变更模型

```typescript
export interface PatchSet {
  id: string;
  runId?: string;
  description: string;
  riskLevel: 'low' | 'medium' | 'high';
  filePatches: FilePatch[];
  checkpointId?: string;
  status:
    | 'draft'
    | 'pending-review'
    | 'partially-accepted'
    | 'approved'
    | 'applied'
    | 'validated'
    | 'rolled-back'
    | 'failed';
}
```

### 2. Patch First 落地规则

第二阶段必须明确：

- Agent 先生成 PatchSet
- 用户先审查
- 再创建检查点
- 最后应用

不允许把“整文件覆盖写入”作为默认主路径。

### 3. 应用语义

补丁应用必须基于真实接受状态重建内容，不能出现“只要有 pending 就直接用新内容”的模糊逻辑。

建议流程：

1. 原始内容哈希校验
2. 冲突检测
3. 基于已接受 hunk 重建目标内容
4. 创建检查点
5. 原子写入
6. 写入审计

### 4. 冲突检测

最少检测：

- 编辑器脏文件
- 外部修改
- Patch 生成后文件内容漂移

### 5. 检查点

检查点必须支持：

- 全量恢复
- 按文件恢复
- 关联到 patchSetId / runId
- 应用崩溃后恢复

### 6. 验证协同

该模块不负责执行验证命令本身，但要与 `terminal` 协作：

- 传递推荐验证命令
- 记录验证结果
- 失败时驱动回滚选项

## 实施要点

### 补丁来源统一

无论补丁来自：

- 对话文本
- 结构化工具调用
- 编辑器中的建议

都先归一为 PatchSet，再走统一流程。

### 风险评级

风险评级至少考虑：

- 删除文件
- 修改配置 / 迁移 / 构建脚本
- 影响文件数量
- 是否新增依赖

### 审计内容

至少记录：

- 谁触发了 patch
- patch 来源 run / step
- 用户接受了哪些 hunk
- 是否执行验证
- 是否回滚

## 测试计划

### 单元测试

- PatchSet 构建正确
- hunk 接受/拒绝逻辑正确
- 基于接受状态重建文件内容正确
- 冲突检测正确
- 回滚后文件恢复正确

### 集成测试

- Agent 生成补丁 -> 用户部分接受 -> 应用成功
- 应用后验证失败 -> 自动回滚
- 文件在补丁应用前被外部修改 -> 冲突被拦截

## 验收标准

- [ ] 所有 AI 修改默认先进入 PatchSet
- [ ] 用户可按文件或按块接受
- [ ] 应用前会创建检查点
- [ ] 冲突会被检测和提示
- [ ] 应用后可触发验证
- [ ] 失败时可回滚
- [ ] 全流程可审计

## 结论

第二阶段的变更引擎应成为用户信任的中间层，让 Agent 的每次修改都可见、可控、可恢复。
