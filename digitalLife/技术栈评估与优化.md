## 二、架构亮点

### 2.1 Crate 模块化（共 20 个 Crate）

良好的关注点分离，按领域拆分：

| Crate | 职责 |
|-------|------|
| `kernel` | 共享类型与常量（serde）|
| `errors` | `thiserror` 错误类型 |
| `storage` / `migration` | SQLite 连接池与迁移 |
| `config` | 配置分层与持久化 |
| `logger` | tracing 初始化 |
| `events` | 跨 crate 事件总线 |
| `workspace` | 文件系统 / Git / 大纲解析 |
| `outline` | 16+ 语言大纲解析 |
| `context` | 上下文选择 |
| `command` | 命令执行与治理 |
| `pty` | PTY 进程管理（portable-pty）|
| `fs-ops` | notify 监听、原子写 |
| `task` | 任务状态机、审批 |
| `conversation` | 会话管理 |
| `agent-runtime` | 单 Agent 顺序规划 |
| `model-gateway` | 模型路由与流式 |
| `change-engine` | Patch 预览/应用/回滚 |
| `terminal` | 终端流式输出 |
| `browser` | Tauri 子 WebView 生命周期 |
| `src-tauri` | 二进制入口、Tauri Command、capabilities |

**评价**：模块化程度高，边界清晰，便于独立演化。

### 2.2 前端架构亮点

- **Zustand 切片合并模式** — 12 个切片 + 11 个 action 模块，避免 Redux 式样板代码
- **双端一致性机制** — `isTauriShell()` 运行时检测 + `DigitalLifeBridge` 三层桥接（tauri/preview/mock）
- **四维代码质量门禁** — clippy + rustfmt + tsc + eslint
- **CSS 设计 Token** — 亮暗主题通过 CSS 自定义属性统一
- **调试日志收起器** — 统一拦截 console 输出，自动写入文件

### 2.3 架构设计中值得认可的决策

| 决策 | 为什么好 |
|------|----------|
| `IpcErrorCode → AppError → IpcResult` 统一错误通道 | 错误类型化，前端可精确匹配处理 |
| 低层 crate 不依赖高层 crate | 防止循环依赖，保持架构整洁 |
| `capabilities/default.json` 拒绝 `"*"` 通配权限 | 最小权限原则，安全最佳实践 |
| 双端一致性机制（3 桥接） | Tauri + 浏览器 + 测试三端覆盖，架构弹性强 |
| 39 轮迭代重构积累 | 架构经过实际打磨，非纸上谈兵 |

## 三、缺陷与薄弱之处

### 🔴 高风险

#### 3.1 IPC 契约手写：两端类型无共享

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| Rust `AppCommand` ⇄ `ipc.ts` 之间无 Schema 共享 | 🔴 **高** | 每新增一个 IPC 方法需要同时修改 Rust 端和 TypeScript 端，且无编译期一致性保障。随着 IPC 方法增加（当前 18 个命令文件），不匹配风险线性增长 |

**根因**：当前 `DigitalLifeBridge` 三层桥接实现正确，但 Rust struct 的定义与 TypeScript 接口之间完全靠人工同步，没有任何校验机制。

#### 3.2 双 Markdown 渲染器冗余

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| `markdown-it` + `react-markdown` 同时存在 | 🔴 **高** | 两份渲染逻辑、两份 bug、双倍维护成本。在 529 个 i18n key 的场景下，任何渲染行为的不一致都会导致显示问题 |

---

### 🟡 中风险

#### 3.3 数据库层

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| **SQLite 类型安全缺失** | 🟡 中 | 纯 SQL 拼接缺少编译期类型检查，手写 SQL 易出错 |
| **慢查询监控缺失** | 🟡 中 | 无慢查询日志，性能问题只能靠人工发现 |

**关于 SQLite 并发**：当前文档将 SQLite 并发限制列为「中」风险，但在**单用户桌面应用**场景下，rusqlite 的并发能力完全足够。r2d2 连接池在此场景下已经过剩。此风险应降级。

#### 3.4 前端依赖体积

| 依赖 | 体积影响 | 说明 |
|------|----------|------|
| `pdfjs-dist` | 🔴 **~5MB** | 全量导入，影响首屏加载 |
| `mammoth` | 🟡 ~500KB | 仅 docx 预览使用 |
| `@codemirror/*` 多语言包 | 🟡 累积较大 | 16+ 个语言包同时加载 |
| `highlight.js` | 🟡 中 | 可按需加载语言 |

#### 3.5 自定义 i18n 系统维护成本

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| 自建 i18n，缺少 ICU 消息格式、复数规则 | 🟡 中 | 当前 529 keys、zh-CN/en-US，规模尚可控。但随着功能扩展，缺失 ICU 消息格式、复数规则、locale 热切换等能力会逐渐暴露 |
| 翻译覆盖度无自动化检查 | 🟡 中 | 新增 key 时可能遗漏翻译 |

#### 3.6 密钥存储 Linux 兼容性

| 问题 | 说明 |
|------|------|
| **Linux D-Bus 依赖** | keyring 在 Linux 上依赖 D-Bus/gnome-keyring，无头环境或最小发行版可能不可用 |
| **无降级策略** | 检测失败时没有降级方案（如加密文件存储） |

#### 3.7 无 CI/CD 流水线

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| 四维门禁仅在本地运行 | 🟡 **中** | 无法防止合入坏代码；无法自动执行测试套件 |

#### 3.8 CSS 纯 Token 系统长期维护成本

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| 无 utility classes，无设计系统强制执行 | 🟡 中 | 随着组件数增加到 32+，重复样式会逐渐膨胀；亮暗主题手动管理，缺少 dark mode 的自动化工具链 |

---

### 🟢 低风险

#### 3.9 Rust 依赖冗余

| 问题 | 说明 |
|------|------|
| `tokio features = "full"` | full 特性包含所有运行时组件，但实际只用部分，可精简以减小二进制体积 |
| `rustls-tls` 静态链接 | 增加编译时间和二进制体积 ~5MB，但跨平台一致性好，当前保留合理 |

#### 3.10 portable-pty 跨平台差异

| 问题 | 说明 |
|------|------|
| Windows PTY 行为偏差 | portable-pty 在不同平台上的 PTY 语义（行尾、编码、退出信号）有微妙差异，需针对 Windows 增加专项测试 |

#### 3.11 React 19 生态就绪度

| 问题 | 说明 |
|------|------|
| React 19 于 2024-12 月正式发布，已稳定 ~6 个月 | 第三方库（`@uiw/react-codemirror`、`react-markdown` 等）已知兼容，此风险已基本解除 |

## 四、推荐优化方案

### 4.1 【核心新增】IPC 类型安全：引入 ts-rs

**方案**：在 `adl-kernel` 或 `adl-errors` crate 中引入 `ts-rs`，从 Rust struct 自动生成 TypeScript 类型定义。

```toml
# crates/kernel/Cargo.toml
[dependencies]
ts-rs = "10"
```

```rust
// 示例：Rust 端标注
use ts_rs::TS;

#[derive(serde::Serialize, TS)]
#[ts(export, export_to = "../../frontend/src/shared/ipc-types.ts")]
pub struct WorkspaceInfo {
    pub id: String,
    pub name: String,
    pub path: String,
}
```

然后作为 `build.rs` 步骤或 CI 步骤生成 `ipc-types.ts`，`ipc.ts` 直接 import 该文件。

| 评估维度 | 评分 | 说明 |
|----------|------|------|
| 跨平台 | ✅ | 纯编译期工具，不影响运行时 |
| 性能 | ✅ | 零运行时开销 |
| 轻量 | ✅ | 仅开发依赖，不增加二进制体积 |
| 实施成本 | 低 | 仅需标注 `#[derive(TS)]` + 一次 CI 配置 |
| 收益 | **高** | 彻底消除 Rust ⇄ TypeScript 类型不匹配 |

**注意事项**：
- `ts-rs` 对复杂泛型、生命周期参数的支持有限，需要时可用 `#[ts(type = "...")]` 手动覆盖
- 每次 Rust 端修改类型后需要重新生成 `.ts` 文件（建议集成到 `build.rs` 或 CI pre-check）
- commit hook 中应加入生成文件一致性检查

### 4.2 【核心新增】统一 Markdown 渲染器

**方案**：放弃 `markdown-it`，统一使用 `react-markdown` + `rehype-*` 插件生态。

```bash
# 移除
pnpm remove markdown-it @types/markdown-it
# react-markdown 和 remark-gfm 已在依赖中 ✅
```

| 评估维度 | 评分 | 说明 |
|----------|------|------|
| 跨平台 | ✅ | 纯前端变更 |
| 性能 | ✅ | react-markdown 基于 unified 生态，tree-shaken 后更小 |
| 轻量 | ✅ | 减少一个渲染器约 15KB+gzip |
| 实施成本 | 中 | 需要重构所有使用 markdown-it 的调用点 |
| 收益 | 高 | 减少维护成本，避免渲染行为不一致 |

**注意事项**：
- 检查 `markdown-it` 是否有独特插件被使用（如自定义 markdown 扩展），`react-markdown` 可能需要 `rehype-` 或 `remark-` 替代
- 迁移后需要对比渲染结果，确保视觉一致

### 4.3 数据库层优化

#### 方案 A：保持 rusqlite → **不做变更（推荐）**

| 维度 | 评分 |
|------|------|
| 改动量 | 无 |
| 跨平台 | ✅ 已验证 |
| 性能 | ✅ 单用户足够 |
| 风险 | 极低 |

**理由**：单用户桌面应用场景下，rusqlite bundled SQLite 已绰绰有余。引入 diesel/sea-orm 会增加编译时间、二进制体积和复杂性，与「轻量」约束相悖。

**改进建议**：
- 为频繁读取路径添加适当索引优化（已有 `init_indexes.sql` ✅）
- 可考虑在 `crates/storage` 中封装 Repository 模式将 SQL 集中管理，但不改变底层库

#### 方案 B：渐进式 Repository 模式封装

在 `crates/storage` 内将 SQL 集中到 Repository 方法中：

```rust
// 示例：Repository 模式
pub struct WorkspaceRepository {
    pool: r2d2::Pool<SqliteConnectionManager>,
}

impl WorkspaceRepository {
    pub fn list_workspaces(&self) -> Result<Vec<Workspace>, StorageError> {
        // SQL 集中在此处，而非散落在调用方
    }
}
```

| 优点 | 缺点 |
|------|------|
| SQL 集中管理，可审查性强 | 需要重构现有代码 |
| 为未来可能的 ORM 切换做准备 | 初期投入 |

#### 方案 C：diesel/sea-orm（**不推荐**）

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **diesel** | 编译期类型安全 | 编译慢 ~30%、同步 API、学习曲线陡 | ⭐⭐ |
| **sea-orm** | 异步支持 | 依赖多、二进制增大、SQLite 支持非一等公民 | ⭐ |

**结论**：**方案 A（保持）+ 方案 B（Repository 模式）** 为最佳路径。保持零额外依赖，仅优化代码组织。

### 4.5 密钥存储优化

#### 方案：保持 keyring + 添加降级策略（P1）

```rust
// 在 adl-config 或独立 crate 中实现双层存储策略

pub enum CredentialStorage {
    Keyring(keyring::Entry),
    EncryptedFile(PathBuf),
}

impl CredentialStorage {
    pub fn new(service: &str, account: &str) -> Result<Self> {
        // 先尝试 keyring，失败降级到加密文件
        match keyring::Entry::new(service, account) {
            Ok(entry) => Ok(CredentialStorage::Keyring(entry)),
            Err(_) => Ok(CredentialStorage::EncryptedFile(
                get_encrypted_file_path()
            )),
        }
    }
}
```

| 评估维度 | 评分 | 说明 |
|----------|------|------|
| 跨平台 | ✅ 增强 | 解决 Linux 无 D-Bus 场景 |
| 性能 | ✅ | 加密文件方案仅在 keyring 不可用时触发 |
| 轻量 | ✅ | 不对无问题用户增加任何开销 |

### 4.6 Rust 二进制体积优化

#### 方案 A：tokio features 精简（P0）

**当前**：`features = ["full"]`

**建议**：根据实际使用按需启用：

```toml
# Cargo.toml (workspace dependencies)
tokio = { version = "1", features = ["rt-multi-thread", "macros", "fs", "io-util", "net", "time", "signal"] }
```

**各 crate 实际使用的 tokio 特性**（需审计后确认）：

| Crate | 实际使用特性 |
|--------|----------------|
| `model-gateway` | rt, macros, net, time, io-util |
| `pty` | rt, process, fs |
| `fs-ops` | rt, fs, time |

**预期收益**：release binary 减小 ~5-10%

#### 方案 B：cargo-bloat 定期分析（P2）

```bash
cargo install cargo-bloat
cargo bloat --release --crates
```

定期检查最大的 crate 依赖，识别可移除或替换为更小的替代。

#### 关于 opt-level 的谨慎说明

**之前的建议 `opt-level = "z"` —— 不推荐**：

| 选项 | 二进制体积 | 运行时性能 | 推荐 |
|------|-----------|-----------|------|
| `opt-level = 3`（当前） | 较大 | 最快 | ✅ |
| `opt-level = "z"` | 最小 | 略降 | ❌ |
| `opt-level = "s"` | 较小 | 略降 | ❌ |

在 **AI 数字生命** 这样一个涉及 PTY 实时处理、文件系统 watch、流式 AI 推理的桌面应用中，运行时性能优先级应高于二进制体积优化。当前 `opt-level = 3` 是正确选择，不应为了节省 ~2-3MB 而降低 PTY 和模型网关的响应速度。

**仅推荐**：`lto = true` + `codegen-units = 1` + `strip = true`（检查是否已启用，未经过度优化）。

### 4.8 CSS 系统评估（P2 观察项）

## 五、跨平台方案完整对比

在「跨平台 + 高性能 + 轻量」约束下的所有可行桌面框架对比：

| 方案 | 二进制体积 | 内存占用 | 运行时性能 | 跨平台覆盖 | 推荐度 | 核心优劣 |
|------|-----------|----------|-----------|-----------|--------|----------|
| **Tauri 2.x（当前）** | **~5-10 MB** | **~80-150 MB** | **⭐⭐⭐⭐⭐** | Win/Mac/Linux + Android/iOS | **🏆 首选** | Rust 零成本抽象 + WebView UI 灵活 |
| Wails 3 (Go) | ~15-25 MB | ~100-200 MB | ⭐⭐⭐⭐ | Win/Mac/Linux | 备选 | Go 更简单，但 GC 导致 PTY 响应有延迟毛刺；Tauri 已有 39 轮重构积累 |
| Electron | ~150-250 MB | ~300-600 MB | ⭐⭐⭐ | Win/Mac/Linux | ❌ 不推荐 | 轻量需求下直接出局 |
| Flutter Desktop | ~20-40 MB | ~150-250 MB | ⭐⭐⭐⭐ | Win/Mac/Linux + 移动端 | 值得观察 | 自绘引擎 UI 一致性最佳；Dart ⇄ Rust FFI 维护成本高 |
| Qt 6 + QML | ~30-50 MB | ~120-200 MB | ⭐⭐⭐⭐⭐ | 全平台 | ❌ 不推荐 | C++ 复杂、LGPL 许可限制 |
| Avalonia (.NET) | ~80-150 MB | ~200-350 MB | ⭐⭐⭐ | Win/Mac/Linux | ❌ 不推荐 | .NET 运行时依赖，轻量要求不符 |

**为什么 Tauri 2.x 在当前约束下是天花板**：

1. **性能**：Rust 零成本抽象 + tokio 协程。PTY 输出、文件系统 watch、流式 AI 推理，这些场景下任何 GC 语言（Go/Dart/C#/Java）都有 latency spike
2. **轻量**：Tauri + SQLite 打包后 <10MB；Electron 起步 150MB+
3. **跨平台**：Tauri 2.x 已支持 Android/iOS（今年 2026 年可评估扩展）
4. **存量资产**：16 个 Rust crate + 完整前端 + 39 轮重构，迁移成本远大于收益

### 8.1 总体评价

**当前技术栈整体合理且优秀**，在「跨平台 + 性能 + 轻量」三角约束下已经做到当前时间点的最优解。

| 安全性 | 双端一致架构 + `IpcErrorCode` 统一错误通道 + 最小权限 | ✅ |

3. **🔵 P2 项持续观察** — i18n 迁移、CSS 优化、测试增强、bundle 定期分析
4. **⚪ 无需大改** — 数据库层、状态管理层、前端框架层当前均为最优选择
