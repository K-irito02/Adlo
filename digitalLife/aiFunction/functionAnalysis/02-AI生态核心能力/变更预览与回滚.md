# 变更预览与回滚

## 功能定位

变更预览与回滚负责把 AI 的输出从“直接写入文件”转变为“可审查、可验证、可撤销的变更集”。

这是现代 AI 编程软件最关键的人机信任机制之一。

## 为什么它比“生成代码”更重要

用户真正信任的不是 AI 会写代码，而是：

- AI 改了哪里
- 为什么这样改
- 我能不能只接受其中一部分
- 如果改坏了能不能回去

没有预览和回滚，自动编辑能力越强，风险越高。

## 关键分析

### 现代产品常见的变更形态

- 单文件 patch
- 多文件 diff
- 分块 hunk 接受/拒绝
- 新文件创建预览
- 命令执行后的自动修改回放

### 一个合格的变更链路应包含

1. 生成修改建议
2. 形成结构化 diff/patch
3. 标记影响文件与风险
4. 支持全部或部分应用
5. 应用前后留检查点
6. 验证失败时支持回滚

### 回滚不只是 Git revert

在 AI 编程场景里，回滚常见有三种：

- 会话级撤销：撤回刚应用的 patch
- 检查点恢复：回到任务开始前状态
- Git 级回退：对已提交变更做恢复

## 与相邻模块的边界

- 它不负责编辑器渲染本身，但需要被编辑器消费。
- 它不负责测试执行，但应在验证失败后接收结果并触发回滚。
- 它不负责 Git 提交，但与版本控制模块高度协同。

## MVP 判断

必须进入 MVP。

因为只要产品支持多文件修改和命令执行，就必须支持：

- 明确展示改动
- 精细控制应用范围
- 出问题时恢复

否则无法建立用户信任。

## 设计要点

- 优先支持 patch-first，而不是 write-first。
- 变更集要带上来源任务和上下文说明。
- 部分接受能力很重要，尤其是大模型一次给出多处修改时。
- 应用 patch 前后都要留检查点。

## 对自研产品的建议

第一版就应支持：

- 统一 diff 视图
- 分文件/分块接受
- 撤销最近一次 AI 修改
- 基础检查点恢复

后续再补：

- 三方合并
- 与 Git 工作树联动的可视化回退
- 自动回滚策略
