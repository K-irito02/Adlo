# AI 编程软件功能分析

## 文档定位

`functionAnalysis` 用来回答两个问题：

1. 现代化 AI 编程软件到底由哪些能力构成。
2. 哪些能力必须进入 MVP，哪些能力应该延后。

它不是实现规格书，也不是功能宣传页，而是后续 `expectedFunctionality` 的分析输入。

## 本轮修正重点

相较于上一版，本轮重点修正了四类问题：

- 原有分类偏重“功能罗列”，缺少“是否属于 MVP”与“模块边界”的判断。
- 基础工程底座不完整，缺少配置/环境、工作区/会话、索引检索、日志恢复等底层能力分析。
- 核心 AI 能力里缺少任务规划、审批控制、变更预览与回滚这类现代工具的关键闭环。
- 一些能力原先被单纯当作功能点描述，本轮改为按照“运行时基础设施 -> 人机协作闭环 -> 智能体自动化 -> 扩展生态”的层次来理解。

## 现代 AI 编程软件的稳定核心

结合近年的主流产品形态，可以把现代 AI 编程软件的核心抽象成一条稳定主链：

`工作区与会话 -> 索引与检索 -> 上下文装配 -> 对话/任务 -> 工具调用 -> 变更预览 -> 执行验证 -> 提交与审计`

在这条主链上，真正决定产品差异的通常不是“能不能生成代码”，而是下面这些能力是否足够成熟：

- 是否能稳定理解整个代码库，而不是只看当前文件。
- 是否有可控的命令执行、审批、沙箱和回滚机制。
- 是否能把 AI 的输出转成可审查、可验证、可恢复的变更。
- 是否能把团队规则、项目规则、记忆与长期上下文稳定沉淀下来。
- 是否能以任务为中心，而不是只以聊天为中心。

## 分层分析框架

建议用四层来理解本目录中的能力：

### L0 基础运行时

负责“系统能稳定运行”：

- 配置管理与环境隔离
- 日志、可观测性与错误恢复
- 工作区与会话管理
- 文件系统、索引与检索
- 终端、事件总线

### L1 人机协作核心闭环

负责“用户能稳定完成一次开发任务”：

- 对话交互引擎
- 上下文管理
- 模型接入与路由
- 代码生成与重构
- 变更预览与应用
- 终端执行与结果回流
- Git 与测试验证

### L2 智能体自动化

负责“让系统从助手升级为代理”：

- 任务规划与执行控制
- 智能体配置与工作流
- Hooks
- 子代理与多智能体
- 沙箱执行

### L3 生态、治理与规模化

负责“让产品可扩展、可协作、可治理”：

- MCP、Skills、插件生态
- 安全治理
- 团队协作
- 质量保障
- 云服务、浏览器、多模态、CI/CD 等高级集成

## MVP 判断

### 必须进入 MVP

- 工作区与会话管理
- 配置管理与环境隔离
- 日志可观测性与错误恢复
- 文件系统操作
- 索引与检索引擎
- 对话交互引擎
- 模型接入与管理
- 上下文管理
- 终端与命令行集成
- 终端命令自动执行
- 变更预览与回滚
- 版本控制集成
- 基础测试自动化
- 基础权限/审计/隐私边界

### 应在 V1-V2 实现

- 任务规划与执行控制
- 智能体配置与工作流
- 沙箱隔离与安全执行
- 代码质量分析
- 代码安全扫描
- Skills、Hooks、MCP
- 本地记忆与知识库

### 可以明显后置

- 浏览器集成
- 云服务集成
- 实时协作编辑
- 插件市场与分发
- 多模态输入
- 大规模多智能体协作

## 如何使用本目录

推荐阅读顺序：

1. 先看 [00-能力分层与MVP边界](./00-能力分层与MVP边界.md)
2. 再看 `01-基础工程功能`
3. 再看 `02-AI生态核心能力`
4. 最后根据产品路线按需阅读 `03-06`

如果目标是做一款真正可落地的现代 AI 编程软件，不建议从“插件市场、多模态、多人协作”开始，而应该先把以下闭环做扎实：

`可理解代码库 -> 可生成变更 -> 可预览变更 -> 可执行验证 -> 可回滚 -> 可审计`

## 与 expectedFunctionality 的关系

两者的分工如下：

| 目录 | 作用 |
|------|------|
| `functionAnalysis` | 分析“现代产品应该有什么、为什么重要、是否适合进入 MVP” |
| `expectedFunctionality` | 规定“本项目准备怎么实现、如何分阶段落地、目录结构和工程基线如何设计” |
