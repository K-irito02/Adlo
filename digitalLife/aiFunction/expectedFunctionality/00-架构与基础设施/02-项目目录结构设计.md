# 项目目录结构设计

## 目标

项目目录结构要服务三件事：
1. 让模块边界天然清晰
2. 让MVP能快速落地，而不是一开始就被工程复杂度拖死
3. 让后续多代理、扩展生态和团队协作有可持续扩展空间

## 推荐形态

建议采用桌面应用+模块化包的monorepo结构：

```
ai-digital-life/
├─ apps/
│  ├─ desktop/          # Electron/Tauri桌面应用
│  │  ├─ main/          # 主进程壳层
│  │  ├─ preload/       # 安全桥接层
│  │  └─ renderer/      # UI、编辑器、对话面板
│  └─ worker/           # 后台索引、解析、任务执行
├─ packages/
│  ├─ kernel/           # 类型、错误、事件、常量、通用协议
│  ├─ config/           # 配置加载、校验、作用域合并
│  ├─ workspace/        # 工作区、会话、检查点、快照
│  ├─ retrieval/        # 索引、搜索、仓库地图、上下文装配
│  ├─ model-gateway/    # 模型接入、路由、计费与容错
│  ├─ conversation/     # 对话状态、消息流、命令与引用
│  ├─ prompt-engine/    # 提示词模板、版本管理、动态组装
│  ├─ tool-runtime/     # 文件、终端、Git、测试等工具执行层
│  ├─ change-engine/    # patch、diff、应用、回滚
│  ├─ agent-runtime/    # 任务规划、执行控制、状态机
│  ├─ security/         # 审批、沙箱、审计、权限
│  ├─ quality/          # 测试、质量分析、文档、依赖治理
│  ├─ extensions/       # MCP、Skills、Hooks、插件
│  └─ ui-kit/           # 共享UI组件与设计令牌
├─ configs/             # 默认配置、schema、环境模板
├─ scripts/             # 开发、构建、发布、迁移脚本
├─ tests/               # 测试目录
├─ docs/                # 文档目录
├─ data/                # 本地开发数据目录
└─ package.json
```

## 模块职责边界

### apps

只负责"把能力装配成产品"，不承载核心业务规则。

- `apps/desktop`：窗口、布局、编辑器、对话和用户交互
- `apps/worker`：后台索引、解析、批量任务和可并行计算

### packages/kernel

内核层必须保持最稳定、最少依赖：
- 基础类型
- 错误定义
- 事件协议
- 通用结果对象
- 常量与枚举

任何业务模块都可以依赖它，但它不能反向依赖业务模块。

### packages/workspace与packages/retrieval

这两个包决定"系统理解代码库的方式"：
- `workspace`负责项目边界、会话和检查点
- `retrieval`负责索引、搜索、仓库地图和上下文装配

它们必须分开，避免"工作区状态管理"和"代码检索算法"缠在一起。

### packages/tool-runtime与packages/change-engine

- `tool-runtime`负责调用工具
- `change-engine`负责描述和应用变更

不要让文件系统、Git、终端直接跳过change engine写入业务状态，否则难以统一回滚与预览。

### packages/agent-runtime

负责任务分解、步骤状态和执行控制，不应直接持有UI状态或存储实现细节。

## 依赖规则

1. `apps/*`可以依赖`packages/*`，但`packages/*`不得依赖`apps/*`
2. `kernel`不得依赖任何业务包
3. `agent-runtime`通过接口依赖`workspace/retrieval/model-gateway/tool-runtime/change-engine/security`
4. `extensions`不得直接改写UI或存储，只能通过受控接口扩展能力
5. `security`可依赖`kernel`和`config`，审批与审计结果通过事件发布

## MVP建议

MVP阶段可以只落地下面这些包：
- `kernel`
- `config`
- `workspace`
- `retrieval`
- `model-gateway`
- `conversation`
- `prompt-engine`
- `tool-runtime`
- `change-engine`
- `security`

`agent-runtime`、`quality`、`extensions`可以先做最小骨架，逐步补实。

## 结论

目录结构的目标不是"看起来大而全"，而是让未来的复杂能力自然有位置可放，同时保证当前MVP的核心链路最短、最稳、最好测。
