# 系统架构总览

> 历史说明：本页保留早期规划讨论价值，但其中技术选型与进程拓扑仍含 Electron 时代设定。当前实现已切换到 **Rust + Tauri 2.x**；架构真源请优先参考 [docs/architecture/system-overview.md](../../../../docs/architecture/system-overview.md)、[tech-stack-alignment.md](../../../../docs/architecture/tech-stack-alignment.md) 与根 [AGENTS.md](../../../../AGENTS.md)。

## 项目愿景

**AI数字生命的最终形态**：

本项目旨在构建一个真正的"AI数字生命"——一个能够自动操作电脑上任何内容的智能体。用户只需通过自然语言与它交流，它就能：
- 理解用户意图，自主规划和执行复杂任务
- 操作电脑上的任何应用程序、文件和系统资源
- 组织和管理Agent团队，协同完成大型项目
- 持续学习和进化，越来越懂用户的需求和习惯

**为什么从AI编程开始**：

现代化AI编程能力是AI数字生命的基石：
1. **代码是精确的语言**：编程任务有明确的成功标准，便于验证AI能力
2. **工具链成熟**：编辑器、终端、Git、测试框架等工具链完善
3. **能力可迁移**：理解代码、修改文件、执行命令、验证结果的能力可迁移到其他场景
4. **即时反馈**：代码修改的效果可以立即验证

**演进路径**：

```
AI编程助手 → 文件管理助手 → 浏览器操作助手 → 应用控制助手 → 完整AI数字生命
     ↓              ↓              ↓              ↓              ↓
  代码闭环      文件操作闭环    网页交互闭环    应用操作闭环    全域操作闭环
```

当前阶段聚焦于AI编程助手，建立稳定可靠的核心能力闭环。

## 架构结论

本项目的系统架构围绕一条稳定主链展开：

`用户输入 → 工作区/检索 → 模型 → patch → 预览审批 → 执行验证 → 回滚或提交`

这意味着：
- UI只是壳层，不承载核心业务规则
- 工作区、检索、工具执行、变更应用、智能体运行时必须分层
- 任何改动工作区状态的动作都必须经过变更预览、审批和检查点

### 桌面壳层

- 编辑器

### 基础设施层

- 配置
- 事件

- 错误恢复
- 存储与缓存

## MVP实施边界

**MVP只需要把以下能力做稳：**
- 单工作区
- 本地索引与仓库地图
- 单主代理
- patch预览与应用
- 命令执行与验证
- 审批、日志、回滚
- Prompt版本管理与效果评估

**MVP不应优先追求：**
- 多代理编排
- 插件市场
- 多模态输入
- 浏览器运行时
- 实时协作

## 建议进程拓扑

- **主进程**：窗口、安全边界、原生桥接
- **渲染进程**：UI、编辑器、对话展示
- **后台进程**：索引、解析、长任务

MVP阶段可以保持轻量，不要为了"看起来先进"过早引入复杂的跨进程编排。

## 技术选型

| 决策项 | 选型 | 理由 |
|--------|------|------|
| 应用框架 | Electron 28+ | 成熟的跨平台桌面应用方案，丰富的原生API |
| 开发语言 | TypeScript 5.3+ | 类型安全、IDE友好、与Electron深度集成 |
| 构建工具 | Vite + electron-builder | Vite极速HMR，electron-builder成熟打包 |
| 状态管理 | Zustand | 轻量、TypeScript友好、无模板代码 |
| 包管理 | pnpm | 严格依赖隔离，monorepo友好 |
| IPC通信 | Electron IPC + 类型安全封装 | 原生IPC性能最优，自封装提供类型安全 |
| 进程管理 | Electron UtilityProcess | 官方推荐子进程方案，比child_process更安全 |
| 日志框架 | pino | Node.js生态性能最优的结构化日志库 |
| 配置格式 | YAML（主）+ JSON（兼容） | YAML可读性好支持注释，JSON兼容性广 |

## 依赖规则

1. `apps/*`可以依赖`packages/*`，但`packages/*`不得依赖`apps/*`
2. `kernel`不得依赖任何业务包
3. `agent-runtime`通过接口依赖`workspace/retrieval/model-gateway/tool-runtime/change-engine/security`
4. `extensions`不得直接改写UI或存储，只能通过受控接口扩展能力
5. `security`可依赖`kernel`和`config`，审批与审计结果通过事件发布
6. 禁止反向依赖（低层不得依赖高层），禁止同层循环依赖
