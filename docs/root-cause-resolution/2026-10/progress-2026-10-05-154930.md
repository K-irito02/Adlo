### Phase 0（2026-10-05 15:49 完成）
- **根因（已实测确认）**：
  `crates/dsh-version/src/lib.rs::detect_running_dsh` 在 `async` 上下文里调用 **`reqwest::blocking`**。reqwest 0.13.4 的 `blocking::wait::enter()`（`reqwest-0.13.4/src/blocking/wait.rs:80`，`#[cfg(debug_assertions)]`）会 `Builder::new_current_thread().build().enter()` 构建一个 shell runtime，该 runtime 在语句结束时于**异步上下文内被 drop** → tokio 抛 panic：
  `Cannot drop a runtime in a context where blocking is not allowed. This happens when a runtime is dropped from within an asynchronous context.`（`tokio-1.53.0/src/runtime/blocking/shutdown.rs:51`）。
  该 panic 使 `/dsh/open` 的 axum handler task 崩溃、连接被重置 → 前端 `httpBridge.call` 的 `fetch` reject → `NetworkError: Failed to fetch` → `captureError` → 全局错误卡片。ad-server 进程本身存活（仅该 task 崩溃）。
- **触发条件**：只要 ad-server 的异步上下文调用 `detect_running_dsh`，且 3080 端口**确实有进程在监听**（TCP connect 成功，才会走到 reqwest 分支）→ 必 panic。
  - 首次打开走 `dsh_state` 快速路径，不调用检测 → 正常。
  - 关闭后 `dsh_state` 清空 → 第二次 `run_open` 走 `select_dsh_source` → `detect_running_dsh` → panic。
  - `get_source_status_inner`（`/dsh/source-status`）也直接调用 `detect_running_dsh`（同根因，即 2026-09-26 那次「进 DSH 组弹 Network error」的真实根因）。
- **验证证据**：新建临时集成测试 `crates/dsh-version/tests/probe_blocking.rs`，在 `#[tokio::test]` 内起本地 TCP 假服务器并调用 `detect_running_dsh(port)` → panic，backtrace 第 5 帧 `reqwest::blocking::wait::enter`、第 9 帧 `adl_dsh_version::detect_running_dsh`。
- **数据流**：`CenterEntryPage.handleOpenDsh` → `openDsh` → `window.digitalLife.dsh.open()` → httpBridge POST `/dsh/open` → `handlers/dsh.rs::run_open` → `select_dsh_source` → `detect_running_dsh`（阻塞 reqwest）→ panic。
- **修复方向（Path A）**：把 dsh 来源检测链路改为 **async**：`detect_running_dsh` 用异步 `reqwest::Client` + `tokio::net::TcpStream`；`detect_system_dsh` 用 `tokio::process::Command`；`select_dsh_source` 改 async；`run_open` / `get_source_status_inner` 调用处 `.await`。彻底移除异步上下文中的 `reqwest::blocking`。
- **下一步**：Phase 2A 实施 + 回归测试（同根因：`/dsh/source-status` 也应一并修复）。
