## [x] 事项 3：图片复制后粘贴出现异常高亮荧光层（且颜色随重复复制次数变化）
- 类型：解决类型 → 本技能流程
- 状态：已完成（2026-10-10 04:21 用户确认）
- 现象：从剪贴板历史复制图片条目（`write_image_to_clipboard`）后，在他处粘贴得到的图片出现异常彩色高亮/荧光叠加层；剪贴板历史里重复出现的新记录同样异常，且叠加颜色随重复次数不同。
- 根因（Phase 0 已确认）：
  - `crates/clipboard/src/read.rs::write_image_to_clipboard` 用 `image` crate 将 PNG 编码为 BMP。`image` 0.25.10 的 BMP 编码器对 `Rgba8` 输出 **108 字节 BITMAPV4HEADER + biCompression=3 (BI_BITFIELDS) + 含 alpha 掩码的 BGRA32**（见 `image-0.25.10/src/codecs/bmp/encoder.rs:140-160,320-330`）。
  - `clipboard-win` 5.4.1 的 `raw::set_bitmap_inner` **只拷贝 40 字节 BITMAPINFOHEADER**（`ptr::copy_nonoverlapping(data+14, info_header, 40)`），丢弃 V4 头其余部分；随后以 `biCompression=BI_BITFIELDS` 调用 `CreateDIBitmap`，而 BI_BITFIELDS 要求头部后紧跟 R/G/B(/A) 掩码——这些掩码落在**未初始化的栈内存**上被当作掩码读取。
  - 结果：颜色通道被错误的掩码重映射 → 产生彩色叠加；掩码来源为栈垃圾 → 每次调用不同 → **叠加颜色随复制次数变化**（与现象完全吻合）。
  - 放大效应：每次从历史复制都会触发监听器回读 → 重新落盘新 PNG（`insert_or_bump` 因 digest 因污染而每次不同 → 无法去重）→ 新记录持续累积且各自带不同色层。
- 修复：写回图片改用**经典 24 位 BI_RGB BMP**（新增 `pub(crate) fn png_to_bmp24`，透明像素按 `((c·a) + 255·(255−a))/255` 合成到白底），不再触发 `image` crate 的 V4/BI_BITFIELDS 头；`write_image_to_clipboard` 改调该函数。文件：`crates/clipboard/src/read.rs`。
- 验证：单测 `png_to_bmp24_is_classic_24bit_birgb` 断言 BMP 头（`"BM"`、DIB=40、24bpp、压缩=0）并**解码回读**断言合成像素（全透明→白 `[255,255,255,255]`；半透明红 `[255,0,0,128]`→`[255,127,127,255]`）；真机粘贴无荧光层由用户确认。

## [x] 事项 4：先复制文本、再复制图片后粘贴，竟同时粘贴「文本 + 图片」（追加式复制）
- 类型：解决类型 → 本技能流程
- 状态：已完成（2026-10-10 04:21 用户确认）
- 现象：先复制文本（CF_UNICODETEXT），再复制图片，在目标处粘贴得到文本+图片混合内容。
- 根因（Phase 0 已确认）：
  - `clipboard-win` 5.4.1 `raw::set_bitmap` 显式使用 `options::NoClear::EMPTY_FN`（空操作），**不调用 `EmptyClipboard`**，源码注释亦称 bitmap 格式「不可能与其它格式重叠、保持向后兼容」（见 `clipboard-win-5.4.1/src/raw.rs:787-792,805-843`；`options.rs`）。
  - `write_image_to_clipboard` 直接 `set_clipboard(formats::Bitmap, &bmp)` → 只 `SetClipboardData(CF_BITMAP)`，先前剪贴板残留的 CF_UNICODETEXT 等格式**原样保留** → 粘贴时按格式优先级/多格式输出得到「文本 + 图片」。
- 修复：新增**统一写回入口** `crates/clipboard/src/write.rs::write_item_to_clipboard`：打开剪贴板后先调用 `clipboard_win::empty()`（`EmptyClipboard`）**清空一次**，再以全格式 **`NoClear` 变体**逐个写入（`raw::set_string_with`/`set_html_with`/`set_without_clear`/`set_bitmap_with`；否则默认变体的 `EmptyClipboard` 会抹掉循环中先前写入的格式）。旧 `read::write_image_to_clipboard` 与其 `set_clipboard` 导入被删除；HTTP 路由 `POST /clipboard/write` 取代 `POST /clipboard/write-image`；前端 `ClipboardBridge.write` 取代 `writeImage`。
- 验证：`plan_formats` 纯逻辑单测（含 html/rtf 无载荷降级、空文本不写、image 无载荷为空）；Rust `adl-clipboard`/`adl-server` 测试 0 失败；真机「先文后图粘贴只得到图片、先图后文只得到文本」由用户确认。

## [x] 事项 5：在别处复制内容后，剪贴板历史刷新「有点慢」
- 类型：解决/优化/调整类型 → 本技能流程
- 状态：已完成（2026-10-10 04:21 用户确认）
- 现象：在系统其它应用复制内容后，左侧边栏「剪贴板历史」需要一段时间才出现新条目。
- 根因（Phase 0 已确认）：
  - `ClipboardHistoryList.tsx` 以 **固定 2000 ms 轮询** `fetchClipboardHistory(true)` 刷新（`REFRESH_INTERVAL_MS = 2000`），无任何推送；即平均 ~1 s、最坏 ~2 s 才可见，且 Tauri 与浏览器两种模式都一样慢。
  - 推送能力其实**已存在但未接线**：`ClipboardMonitor` 变化时通过 `broadcast` 发送 `Some(id)`（`crates/clipboard/src/monitor.rs:76-91`），但 `crates/server/src/engine.rs:251` 只 `spawn` 了监听、**无人订阅该 broadcast**；kernel 里 `AppEvent::ClipboardChanged(String)`（`crates/kernel/src/events.rs:52`）**定义了但从未 emit**。
  - 已有可复用的推送通道：`/ws/workspace` WebSocket（`crates/server/src/ws_workspace.rs`）推送 `AppEvent::FilesChanged`，前端共享客户端 `frontend/src/shared/ipc/workspace-events-ws.ts`（按 `kind` 分帧）。
- 方案（已在 spec §14 定稿）：监听广播 → `AppEvent::ClipboardChanged`（改为无负载变体）→ `ws_workspace` 新增 `{kind:"clipboard-changed"}` 帧 → 前端共享 WS 客户端分派 → 列表立即重拉（~100 ms 节流）；轮询 `2000 → 10000 ms` 降级为断线兜底。
- 用户决策：方案 A（WS 推送 + 轮询兜底）；并入现有 spec（批次 E）。
- 修复：接线推送链 —— `ClipboardMonitor` broadcast → `crates/server/src/engine.rs` 专用线程（`blocking_recv`；`Lagged` 记 `tracing::warn!` 后**继续**，`Closed` 才退出，避免静默失效）→ `AppEvent::ClipboardChanged`（改为无负载变体，`kind()` 不变）→ `crates/server/src/ws_workspace.rs` 新增 `clipboard_changed_frame()`（`{"kind":"clipboard-changed"}`，复用 `try_send_frame`）→ 前端 `shared/ipc/workspace-events-ws.ts::onClipboardChanged`（按 `kind` 分派 + 重连补刷）→ `ClipboardHistoryList.tsx` 订阅后立即重拉（**100 ms 前后沿节流**合并密集事件）；轮询 `2000 → 10000 ms` 降级为兜底。
- 验证：`adl-kernel` 事件 kind 单测、`adl-server` 帧形状单测；前端 `workspace-events-ws` 分派测试（`clipboard-changed` 仅唤醒剪贴板监听者）、`ClipboardHistoryList` 重拉测试；Rust/前端受影响套件 0 失败；真机「外部复制后数百毫秒内出现」由用户确认。
