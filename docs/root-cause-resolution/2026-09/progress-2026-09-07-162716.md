## 缓存机制设计

### 问题
`select_dsh_source` 每次调用都重新检测 dsh 来源（运行中 → 系统 → bundled → download），其中 `detect_system_dsh` 调用 `dsh --version` 耗时 ~1.5s，成为主要瓶颈。

### 方案
在 `ServerState` 中新增 `dsh_source_cache: Arc<RwLock<Option<DshSource>>>`：
- **首次 open**：执行完整检测（~100ms，已跳过 `--version`），结果写入缓存
- **后续 open**：直接读缓存（~0ms），跳过全部检测
- **关闭 dsh 时**：清除缓存（`close_inner` 中 `keep=false` 时置 `None`）

### 修改文件
| 文件 | 修改 |
|------|------|
| `crates/server/src/state.rs` | `ServerState` 新增 `dsh_source_cache` 字段 |
| `crates/server/src/engine.rs` | `init_server_state` 初始化缓存 |
| `crates/server/src/handlers/dsh.rs` | `run_open` 读写缓存；`close_inner` 清除缓存；`open` 传递缓存 |
| `crates/dsh-version/src/lib.rs` | `detect_system_dsh` 跳过 `--version` 调用 |

### 调试日志
- 缓存命中：`dsh::run_open: source cache HIT — reusing detected source`
- 缓存未命中：`dsh::run_open: source cache MISS — fresh detection completed`
- 缓存写入：`dsh::run_open: source cached for future calls`

## 预启动设计

### 问题
用户点击"打开 DeepSeek Harness"按钮后，dsh 进程才开始 spawn（~5-7s），导致界面打开缓慢。

### 方案
adl-server 启动完成后，在后台自动 spawn dsh，使用户点击按钮时进程已就绪。

### 时序
```
T0  main() 启动
T1  adl-server spawn → init_server_state (~200-800ms)
T2  TcpListener::bind → AD_SERVER_PORT= (server ready)
T3  start_background_services (clipboard listener)
T4  tokio::spawn → dsh pre-start 开始          ← 新增
T5  axum::serve 开始处理请求
    ... dsh 后台启动中 (~5-7s) ...
T13 开屏动画结束 (3.5-8s)
T14 用户点击 → run_open 快速路径命中 → 返回 URL (~0ms)
```

### 修改文件
| 文件 | 修改 |
|------|------|
| `crates/server/src/engine.rs` | `serve()` 中 `tokio::spawn` 后台调用 `pre_start_dsh` |
| `crates/server/src/handlers/dsh.rs` | 新增 `pub async fn pre_start_dsh(state)` |

### 关键保证
- **不阻塞**：`tokio::spawn` 是异步的，server 立即可用
- **不冲突**：`dsh_start_lock` 序列化并发 open 请求
- **幂等安全**：预启动失败时，用户点击会正常重新启动
- **缓存生效**：预启动时已填充 `dsh_source_cache`

### 调试日志
- 预启动开始：`dsh::pre_start: spawning dsh in background`
- 预启动完成：`dsh::pre_start: dsh ready, elapsed_ms=X`
- 预启动失败：`dsh::pre_start: dsh spawn failed — will retry on user click`
