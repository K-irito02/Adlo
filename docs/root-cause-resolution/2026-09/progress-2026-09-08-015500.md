# 进度 — 2026-09-08 01:55:00

## [已完成] 事项 1：DSH WebView2 遮挡悬浮层问题

- 状态：已完成
- 根因：DSH 界面运行在独立 WebView2 子窗口（HWND）中，其 HWND Z-order 高于主 WebView。主 WebView 内部的 HTML 悬浮层（菜单、下拉、对话框等）z-index 无法穿透独立 WebView2 HWND。这是一个**架构约束**——WebView2 在 Windowed hosting 模式下永远绘制在最上层。
- 方案：创建 OverlayManager 单例（集中式 MutationObserver + 几何重叠检测），检测到悬浮层与 DSH WebView 容器重叠时，将 DSH WebView 移出屏幕；悬浮层消失时恢复。
- 修复：见下方详细记录

---

## 详细记录

### Phase 0：根因调查

**问题描述：** DSH（DeepSeek Harness）界面出现后，应用程序中的悬浮层（汉堡菜单、右键菜单、下拉菜单、对话框等）被 DSH WebView2 窗口遮挡覆盖，无法正常显示。

**涉及代码区域：**
- `frontend/src/app/features/browser/useWebViewVisibility.ts` — 浏览器面板的悬浮层检测
- `frontend/src/app/features/dsh/` — DSH 面板相关组件
- `src-tauri/src/commands/browser.rs` — DSH WebView2 创建与定位

**调查发现：**
1. 浏览器面板已有完整的悬浮层检测机制（MutationObserver + `WEBVIEW_OVERLAY_SELECTOR`），但 DSH 面板**完全没有**
2. `useDshWebViewBounds` 只处理 ResizeObserver + bounds 同步，无 overlay 检测
3. WebView2 在 Windows 上是 OS 级 HWND，CSS z-index 无法跨越 HWND 层级

### Phase 1：确定路径

**路径 A（已确认根因）：** DSH WebView2 是独立 HWND，Z-order 由 Windows 窗口管理器决定，HTML 悬浮层无法穿透。

**类比：** 系统 title/原生菜单是 OS 窗口，天然盖在所有 HWND 之上；我们的 HTML 悬浮层只是主 WebView 内部的内容，出不了主 WebView 这个 HWND。

### Phase 2A：实现 OverlayManager（集中式方案）

**选择集中式而非扩展现有 selector 的理由：**
- 每新增一个悬浮层都要修改 selector 列表 → 维护负担
- 集中式 OverlayManager 单例：所有 WebView2 容器共享一个 MutationObserver，新增悬浮层只需改一处

**实现清单：**
1. `shared/overlayManager.ts` — OverlayManager 单例（选择器维护、MutationObserver、几何重叠检测、订阅机制）
2. `dsh/useDshWebViewVisibility.ts` — DSH 专用可见性 Hook
3. 重构 `browser/useWebViewVisibility.ts` — 移除内联 MutationObserver，改为订阅 OverlayManager
4. 17 个选择器覆盖所有悬浮层类型

### Phase 3：验证中发现的关键 Bug

**Bug 1（CRITICAL）：`activeRef.current` 永远为 `false`**
- 文件：`useDshWebViewVisibility.ts`
- 原因：`activeRef` 初始化为 `useRef(false)` 但从未设为 `true`，三个 effect guard 始终 early-return
- 影响：整个 DSH overlay 检测机制完全失效
- 修复：添加 `useEffect(() => { activeRef.current = isVisible; }, [isVisible])`

**Bug 2：选择器列表不完整**
- 初始只有 6 个选择器，遗漏了 11 个悬浮层类型
- 遗漏的包括：`.tooltip`、`.hint-card`、`.adl-prompt-modal`、`.adl-toast`、`.toast-card`、`.adl-statusbar__menu`、`.adl-conflict-modal-overlay`、`.adl-notif-dropdown`
- 后续根据用户反馈调整：移除 `.tooltip`（悬停小提示不需覆盖 WebView），新增 `.adl-hamburger__dropdown` 和 `.adl-hamburger__submenu`

**最终选择器列表（17 个）：**
```
.adl-sidebar-menu, .adl-multitree-entry__menu, .adl-menu__dropdown,
.adl-search-engine-popover, .adl-download-menu, .adl-confirm-overlay,
.adl-hamburger__dropdown, .adl-hamburger__submenu, .hint-card,
.adl-prompt-modal, .adl-toast, .toast-card, .toast-card-region,
.adl-statusbar__menu, .adl-statusbar__model-menu,
.adl-conflict-modal-overlay, .adl-notif-dropdown
```

### Phase 3→4：替代方案调研

用户提出"为什么悬浮层不能像系统 title 一样出现在 WebView2 上层"，触发了外部调研。

**调研范围：**
- WebView2 官方文档（Windowed vs Visual hosting）
- MicrosoftEdge/WebView2Feedback 仓库（issue #286 等）
- Electron BrowserView / WebContentsView 演进
- Tauri/wry 多 webview 相关 issue

**调研结论：**
- WebView2 有三种托管模式：Windowed（当前）、Window to Visual、Visual（合成模式）
- Visual hosting 可解决 z-index 问题，但 Tauri/wry 目前未接入
- 微软社区有 Airspace Solution（独立置顶窗口）方案

**评估的替代方案：**

| 方案 | 描述 | 结论 |
|------|------|------|
| B（iframe） | DSH 改用 iframe 嵌入主 WebView | 可能被 CSP 拦截，需实测 |
| C（原生菜单） | 右键菜单等改用 Tauri 原生 Menu | 样式受 OS 限制（非 owner-draw），无法保持现有 UI/UX |
| D（透明置顶窗口） | 独立透明 WebViewWindow 承载悬浮层 | 可行但改动量大（状态同步、定位、焦点管理），资源开销高 |
| E（Visual hosting） | 等 Tauri/wry 接入 WebView2 合成模式 | 依赖上游，时间不可控 |

**最终决策：保留方案 A（OverlayManager + 移出屏幕）**。原因：
1. 方案 C 样式不可控（无法保持品牌化 UI）
2. 方案 D 复杂度和资源开销高
3. 方案 A 已落地且稳定，零侵入

### Phase 2A 补充：临时测试验证（已清理）

为验证方案 C 和 D，曾添加临时测试代码（标题栏按钮 + Rust command + 透明卡片页面），验证后已全部清理。

**测试结论：**
- 方案 C：原生菜单确实盖在 DSH 之上且 DSH 不隐藏，但外观明显是系统菜单风格
- 方案 D：透明置顶窗口理论上可行，但实际测试中 WebView2 透明渲染有兼容性差异
