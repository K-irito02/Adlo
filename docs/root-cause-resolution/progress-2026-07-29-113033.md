## [x] 事项 1：Git可视化「分支图谱」表格行悬停背景色卡顿
- 状态：已完成
- 描述：滚动加载过多提交记录后，鼠标悬停在表格行上时，灰色背景效果有延迟、缓慢感
- 根因分析：hover 时 `setHoveredId` 触发 React 状态更新，导致整个 `BranchGraph` 组件重新渲染。`visibleRows.map(...)` 中 50+ 行的所有 JSX 元素（含 `AuthorAvatar`、`CopyButton`、`TooltipSimple` 等复杂子组件）被重新创建并进行协调。CSS `:hover` 背景过渡虽然独立于 React，但主线程被 React 协调阻塞，导致过渡效果感觉延迟。核心问题：table rows 的渲染与 `hoveredId` 状态耦合。
- 修复方案：将 table rows 提取为 `React.memo` 组件 `CommitTableRows`，仅依赖 `visibleRows`/`filterColumns`/`activeRefLabel` 等非 hover 相关属性。hover 时 `hoveredId` 变化仅触发 `SvgLanes` 重新渲染（必要的 SVG 节点高亮），table rows 跳过重新渲染。
- 验证（第一轮）：✅ 115 测试通过，0 ESLint 错误。悬停时 CommitTableRows 和 TagRow 跳过重新渲染。
- 验证（第二轮，额外优化）：⏳ 待用户验证
  - 移除了 CSS `transition: background 0.15s`（150ms过渡本身即被感知为延迟）
  - 拖拽 session 缓存 `tagRowEl`（避免每次 mousemove 的 querySelector）
  - 拖拽改用 `querySelectorAll` 直接迭代 + 内联计算中点位置（避免构造临时 rects 数组）
  - 拖拽 ghost portal 提取为 `DragGhostPortal` React.memo 组件（`dragColId` 未变化时不重创建 portal）
  - ghost 元素添加 `willChange: transform`（GPU 合成层提示）

## [x] 事项 2：Git可视化「分支图谱」标签行拖拽排序卡顿
- 状态：进行中（第四轮待验证）
- 描述：泳道和表格上方标签行区域中的标签进行拖拽排序时，有延迟、缓慢感
- 根因分析：拖拽过程中每次 mousemove 触发：(1) `document.querySelector` + `querySelectorAll` + `getBoundingClientRect` 造成强制同步布局；(2) `setTagRowOrder` 状态更新触发整个 `BranchGraph` 重新渲染，包括 table rows 和 SvgLanes。即使 RAF 批量处理了 state 更新，DOM 查询仍然在每帧执行。核心问题：tag row items 渲染与 BranchGraph 主组件耦合，拖拽更新触发了不必要的整树重渲染。
- 修复方案（第一轮）：将整行 tag row 提取为 `React.memo` 组件 `TagRow`（含内部 scroll 处理），拖拽时 `tagRowOrder` 变化仅触发 TagRow 重新排序渲染，CommitTableRows 和 SvgLanes 跳过重新渲染（除非 columnOrder 实际变化）。
- 验证（第一轮）：✅ 115 测试通过。拖拽时 TagRow 独立渲染。
- 修复方案（第二轮）：缓存 `tagRowEl` 于 dragSession ref（首次 mousemove 时查询一次，后续复用）；内联迭代 `querySelectorAll` NodeList（避免数组构造 + 额外内存分配）；提取 `DragGhostPortal` React.memo（`dragColId` 不变时不重创建 portal DOM 节点，避免 ghost 元素闪烁）。
- 验证（第二轮）：⏳ 待用户验证
- 修复方案（第三轮，2026-07-29 12:20）：首次启动拖拽时缓存所有非拖拽项的中点位置到 `dragSession.midpoints`（`getBoundingClientRect` 仅调用一次），后续 mousemove 循环读取缓存，完全消除强制同步布局。视觉反馈改用直接 DOM 操纵（`element.style.opacity = '0.3'`、`setAttribute('data-insert-before')`），零 React 重渲染参与。CSS 添加 `::before` 插入指示器（2px accent 竖线）。`mouseup` 时清理所有 DOM 视觉标记。
- 验证（第三轮）：❌ 用户反馈仍有卡顿，且不想要竖线指示器
- 修复方案（第四轮，2026-07-29 12:40）：彻底消除 mousemove 中所有 DOM 样式/属性写入 — 不再循环设置 opacity、不再读写 `data-insert-before`、不再调用 `querySelector` 查询目标元素。使用 CSS `transform: translateX()` 实现"让位效果"（非拖拽项在插入点后方的自动平移），配合 `transition: transform 0.08s ease` 实现平滑移位动画。拖拽项变透明由 `TagRow` 的 React state `opacity: isDrag ? 0.4 : 1` 一次渲染完成（不发生每帧更新）。幽灵元素跟随光标作为预览。mousemove 中唯一做的写操作：插入索引变化时设置非拖拽项的 `transform`（仅影响插入点附近的少数项）。
- 验证（第四轮）：❌ 用户反馈仍有卡顿，要求按 RCR 流程进行系统化根因排查 + 外部调研 + 添加调试日志
- 根因分析（Phase 1 完成）：
  - 根因 A：ghost 元素使用 `top`/`left` 定位 → 每次 mousemove 触发强制布局计算（layout + paint + composite），即使 ghost 是 `position: fixed`，`top`/`left` 更改仍会导致整页重排
  - 根因 B：无 RAF 合并（RAF coalescing）→ mousemove 事件以鼠标轮询率（125-1000Hz）触发，远高于屏幕刷新率（60Hz）。事件处理程序每事件执行一次，每帧浪费 8-16 次多余执行
  - 根因 C：无 CSS 隔离（containment）→ transform 写入非拖拽项时，样式重新计算传播到整个 DOM 子树
- 外部调研发现：业界最佳拖拽实现（react-grab、primer/react、react-table-dnd、react-use）均采用 RAF 合并 + `transform` 仅合成器定位 + CSS containment 三件套
- 修复方案（第五轮，2026-07-29 13:10 — 三个根因同时修复）：
  - (A) ghost 定位从 `top`/`left` 改为 `transform: translate(x,y) translate(-50%,-50%)` — 仅合成器操作，零布局
  - (B) mousemove 仅存储鼠标位置并调度 RAF，实际计算在 `requestAnimationFrame` 回调中执行 — 每帧最多处理一次
  - (C) CSS `contain: layout style paint` + `data-dragging` 属性隔离标签行子树 — transform 写入不传播到外部
- 验证（第五轮）：❌ 用户反馈"感觉没有任何变化"
- Phase 1 重新分析：前三轮聚焦于 drag 处理代码的 DOM 性能优化，但忽略了更重要的性能杀手 **hoveredLabel 状态更新引发整树重渲染**。拖拽时鼠标在标签按钮间移动会触发 `onMouseEnter`/`onMouseLeave` → `setHoveredLabel` → BranchGraph 整树重渲染（含 50+ CommitTableRows 行 + SvgLanes SVG 重计算）。这比 mousemove handler 的 DOM 操作昂贵得多。
- 修复方案（第六轮，2026-07-29 13:35）：
  - 新增 `dragActiveRef = useRef(false)` + `setHoveredLabelSafe` 包装器，mousedown 时设为 `true`、mouseup 时设为 `false`，在包装器中检查并跳过 `setHoveredLabel`
  - `TagRow` props 从 `setHoveredLabel` 重命名为 `onHoverChange`
  - 拖拽期间 `onMouseEnter`/`onMouseLeave` 不再更新 `hoveredLabel` 状态 → 阻止 CommitTableRows 和 SvgLanes 的不必要重渲染
  - 保留第五轮的三项优化（RAF 合并 + transform ghost + CSS containment）
