### 事项 2 追加问题 2b（两击回退）方案选项
- 根因：B 站 SPA 用 `pushState` 反复加/重排 tracking 参数 → WebView 原生历史栈冗余条目。`GoBack` 一次一个条目。WebView2 无删除历史条目 API。
- 选项：
  - **C1（推荐）JS 注入改写 pushState/replaceState**：文档创建时注入脚本包装 `history.pushState`/`replaceState`，对 url 剥离跟踪参数并排序后再入栈 → 原生历史不再产生冗余条目，回退一次到位。风险：会改变页面可见 URL（仅删跟踪参数，影响面小），对少数依赖确切 URL 的站点有兼容风险。
  - **C2 前端智能回退（循环 GoBack）**：前端记录每 tab 最近访问的「去重键」栈，点回退时比较目标与当前是否为同页（去重键相同则继续 GoBack 直到键变化）。不改页面，但增加多击异步延迟，且对 hash 路由站点可能误跳过。
  - C3 维持现状（接受浏览器原生行为：Chrome 对 B 站此类 pushState 同样需多击）。
- **浏览器行为调研结论（2026-08-13 23:00，用户要求先调研再定）**：
  - WHATWG HTML 规范 §7.2.5「History 接口」：`pushState`/`replaceState` 都委托给「shared history push/replace state steps」，对传入 `url` **没有任何「与当前条目 URL 相等则短路」的判断**——只有「initial about:blank 文档」会强制 `replace`。
  - §7.4.4「URL and history update steps」：**无条件新建**一个 session history entry（`newEntry` 总是被构造，即使 URL 与 active entry 完全相同），随后设置 document URL、latest entry、active entry 并异步 finalize。规范原文没有一处比较 `newURL` 与 `activeEntry` 的 URL。
  - 唯一「URL 相等 → replace」的启发式只存在于**普通导航 navigate 算法**的 note（"often, but not always"），且仅影响 `"auto"` 历史处理模式，**不适用于 history API**。
  - 推论：**Chrome/Edge（Chromium）对每次 `pushState` 都无条件新建历史条目，即使 URL 与当前完全相同**（与 Chromium issue 496807453「标准链接导航创建重复历史条目、回退需两击」一致）。也就是说浏览器**没有**任何可采纳的「去重方案」——C3（维持现状）本身就是 Edge/Chrome 的原生行为。
  - 结论：要做到单击回退，只能前端补偿——C1（注入改写 pushState：URL 归一化后与当前条目相同则改用 `replaceState`，从源头不产生冗余条目）或 C2（前端智能回退循环）。C1 与规范不冲突（是拦截页面脚本而非依赖浏览器去重），是唯一能真正「消除冗余条目」的路线。**待用户拍板**。
