- 次因（首帧闪烁）：`source-status` 尚未返回时 `versionSource=null`，同样会短暂显示三项。

### 讨论第二轮（2026-10-22 10:01）

用户反馈三点：① `running` 有两种成因（应用自行拉起 / 用户在外部手动运行），要求用合理设计屏蔽来源干扰或从根本解决；② 要求解释「目标解析为 none」的场景与现象；③ 首帧闪烁确认需要修。

#### 1. `running` 的本质与根因定性

- `running.managed` 已区分两种成因：`managed=true` 为本次应用会话拉起的受管进程（`version` 精确已知）；
  `managed=false` 为外部/残留进程（`version` 未知）。见 `crates/server/src/handlers/dsh.rs` L903–L917。
- **根本问题不是 running 本身，而是把「运行时实际来源」与「偏好解析来源」塞进同一个 `versionSource.effective` 字段**：
  running 一存在就遮蔽偏好，能力显隐与弹窗判定因此失真。
- 因此无论 running 来自应用自启还是用户手动，都应由同一设计消除影响，不需要区分成因。

#### 2. 推荐的根本方案：拆分两个语义字段（后端单一真源）

| 字段 | 语义 | 计算 | 消费方 |
|------|------|------|--------|
| `effective`（保留） | 运行时实际来源，可能是 `running` | `resolve_effective_source(mode, running.is_some(), host, system)` | 当前版本读数、运行状态说明 |
| `resolvedByMode`（新增） | 各来源在「忽略 running」下的解析结果 | 对 `auto/host/system` 各调一次 `resolve_effective_source(mode, false, host, system)` | 管理项显隐、切换弹窗判定、无可用来源提示 |

- 后端是来源优先级唯一真源，前端不再复制优先级逻辑（避免 TS/Rust 双写漂移）。
- 对 `managed=true` 与 `managed=false` 天然统一：两者都不参与 `resolvedByMode`。
- `running` 仍保留两项正当用途：当前版本读数（`running.version`）、以及「立即生效」需要重启时的事实依据。
- 备选方案（前端 `resolveStorageSource` 镜像优先级）不采纳：属双写，后续优先级调整易漂移。
- 备选方案（只在 `managed=true` 时遮蔽）不采纳：外部进程场景仍失真，且未触及字段语义混淆这一根因。

#### 3. 「目标解析为 none」的含义（答复用户第 2 问）

- **触发场景**：当前 `mode=auto`（或 `system`），系统安装可用、宿主为空；用户把来源切到「宿主安装」。
  目标 `host` 无任何已装版本 → 目标解析为 `none`。
- **当前现象**：静默落盘 `version_source=host`，无确认框；本次会话受管进程继续运行，当前版本读数仍显示系统版本；
  由于 running 存在，`effective=running`，连「无可用来源」提示也不显示。用户看不出异常，
  直到下次启动才发现 dsh 不再拉起（此时 `effective=none`）。
- **建议**：保留「不弹窗」（符合用户第 4 点），改为**常驻行内提示**——把 `dshNoSourceNote` 的显示条件
  由 `effective === 'none'` 改为 `resolvedByMode[mode] === 'none'`，切换后立即出现，无需 toast。
- 文案需调整：现有 `dshNoSourceNote` 写死「已切换到宿主安装」，不适用于 `auto` 下全空场景；
  拟新增/改写为通用表述（如「当前来源下没有可用版本，下次启动将无法拉起助手」），或按 mode 分两条 key。

#### 4. 首帧闪烁（用户第 3 点，确认修）

- 现状：`versionSource` 为 `null` 时 `systemManaged` 为 `false`，三项先渲染再被隐藏，形成闪烁。
- 修法：`versionSource !== null` 之前不渲染这三项（用户指定方案）；加载完成后按 `resolvedByMode` 一次性决定。
  代价是宿主来源下三项延迟约一次请求出现，可接受；不引入骨架屏。

### 第九轮追加（首屏跳动与「运行中」读数：方案讨论，未改代码）

#### 问题 1：每次启动后立刻进入版本管理，块内跳动/闪动

根因（代码取证）：

1. 三路数据分段到达，各自触发渲染：`fetchDshVersionStatus`、`fetchSourceStatus`、
   `fetchVersionCatalog` 并行且耗时不同（catalog 走网络最慢）。
2. `sourceReady=false` 时管理三行不渲染（`manageVisible`），数据返回后整块长高。
3. 灰字提示（`dshSystemManagedNote` / 无来源提示 / deferred 提示）按条件插入，行数变化。
4. `readout.sub` 与「最新版本 x」行后到，当前版本行从一行变两行。
5. `DshSettings` 与版本块挂载时都调用 `fetchSourceStatus`，重复请求、返回时序不同。
6. 应用重启后 store 为空，无跨启动缓存，每次启动重复首屏等待。

方案 A（推荐）：预取 + 请求去重 + 稳定占位（无加载动效）

- `fetchSourceStatus` 做 in-flight 去重；catalog 提前预取并做内存缓存（TTL）。
- `readout.sub` 槽位与「最新版本」行固定 `min-height`；管理三行未就绪时用等高空白占位
  （无扫光、无文字，不是骨架屏）。
- 优点：无闪烁、改动局部、无需新 API。
- 缺点：首次进入有约 100–300ms 空占位；窄窗口下提示换行仍会改变高度（需限制行数/预留两行）。
- 注意：占位高度必须与最终行高一致；不要用 `max-height` 过渡动画。

方案 B：结构恒定型

- 所有行始终渲染，未知值显示「—」，按钮禁用直至数据就绪。
- 优点：零布局变化、实现简单。
- 缺点：首帧信息密度低；需新增 i18n 键与禁用态样式；容易被误认为控件不可用。

方案 C：聚合快照接口

- 新增 `/dsh/settings-snapshot` 原子返回 source/version/catalog（catalog 服务端缓存），
  前端一次提交。
- 优点：根治分段渲染。
- 缺点：后端 + Tauri/Preview/Mock 三桥接改动大；catalog 网络慢会拖慢整体。

方案 D（不推荐）：高度过渡动画。动画布局属性成本高、易抖，只是掩盖问题。

#### 问题 2：「运行中（url）」读数的不合理/缺陷

1. **来源身份丢失**：`running` 只带 `url/port/managed/version`，没有记录是哪一来源拉起。
   `effective=running` 会遮蔽 mode，导致副行只有 URL；与提示文案「实际生效来源看当前版本行」矛盾。
2. **快照不刷新**：source-status 仅在挂载/操作时拉取，无轮询或事件；打开设置的时机决定
   是否有运行中（预拉起约十几秒），进程退出后也不会自动消失。
3. **首帧猜测误导**：`versionSource` 未返回时 fallback 优先用 `currentSelected`，可能显示
   一个并未实际生效的宿主版本；source-status 持续失败时该误导会一直存在。
4. **语义与样式**：外部进程版本未知时，主行显示「运行中(url)」并套 `is-empty` 灰态，
   把“状态”当成“版本”；长 URL 无截断约束。
5. **managed 判定边界**：只看 `dsh_state` 是否持有，未校验子进程是否已退出；极端情况下
   外部进程会被误标为本次会话拉起，版本归属错误。
6. **系统安装来源几乎不可见**：只要有进程在跑，`effective` 恒为 running，「系统安装（path）」
   只在进程退出后出现，用户可能误以为切源未生效。

设计解决方案：

- P1 后端：`ManagedDsh` 记录 spawn 来源（host/system），`running.source` 返回
  `host|system|external`；前端副行显示「运行中 · 系统安装（url）」或「外部运行（url）」。
- P2 刷新：新增轻量 `/dsh/running`（仅检测进程 + managed，不跑 `where`/版本探测）；
  面板可见时 5s 轮询、`document.hidden` 暂停。外部进程无法发事件，事件方案仍需低频轮询兜底。
- P3 首帧：`versionSource` 未就绪时不猜版本（显示中性的“状态读取中”或使用上次会话快照），
  禁止用 `currentSelected` 顶替实际来源。
- P4 展示：外部未知版本时主行 = 「版本未知」，副行 = 「运行中（host:port，外部启动）」；
  完整 URL 放 `title`。
- P5 健壮性：`get_source_status` 对 `dsh_state` 内 child 做 `try_wait`，已退出则按非 managed。

实施顺序建议：P1 + P4（信息正确）→ P3（首帧）→ P2（实时性）→ P5（边界）。

### 第十二轮追加（读数中途值跳变 → 骨架胶囊遮罩，2026-10-22 14:0x）

#### 用户反馈

在某些操作后，「当前版本」右侧内容（版本号、URL 等）会可见地变动，例如
「版本未知」随后变成真实版本。希望中途不暴露这些值，统一显示现有的骨架胶囊波浪动画。

#### 根因（按暴露顺序）

1. **首屏文本切换**：快照未返回时显示中性「状态读取中」文本，数据到达后直接换成真实版本。
2. **spawn 窗口竞态**：dsh 端口已监听但宿主尚未把 `ManagedDsh` 写入 `dsh_state`，
   此时 `/dsh/running` 或快照会把进程判为 `external`（版本未知）；下一轮又变成
   `managed=true` + 真实版本 → 用户可见「未知 → 真实」跳变。
3. **重启长尾**：`applyVersion` 结束后到下一次轮询之间，读数仍可能先显示旧值。
4. **轮询直更**：`/dsh/running` 每次返回都直接重渲染读数，没有中间遮罩。

#### 修复

后端（`crates/server`）：

- `ServerState` 新增 `dsh_starting: Arc<AtomicBool>`。
- `run_open` 在**真正要 spawn** 时（`HostInstalled` / `System` 两个分支）用
  `StartingGuard` 置位；spawn 成功写入 `dsh_state`、失败或 panic 退出时由 `Drop` 自动复位。
  `ReuseRunning` / `None` 不置位（没有实际拉起动作）。
- `/dsh/source-status`（含聚合快照）与 `/dsh/running` 均返回 `starting`，
  让前端在拉起窗口内明确显示骨架态，而不是猜测版本。
