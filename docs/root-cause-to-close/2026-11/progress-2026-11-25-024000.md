## [ ] 事项 1：DSH 站内设置弹窗的「更多账号信息 / 查询用量 / 充值」点击无反应

- 状态：已完成（2026-11-25 用户确认「所有的问题和任务都解决完成了」） | 类型：解决（行为缺陷） | 流程：本技能 P0–P3 已完成
- 决策（grilling 已定）：
- 根因（已确认，两条叠加）：
  - **主因：Tauri shell 插件把浏览器子 WebView 的 `target=_blank` 链接吞掉。** `tauri-plugin-shell` 向每个 WebView 注入 `document.body` 的 bubble 点击处理器：对 `http(s)/mailto/tel` 且 `target="_blank"` 的锚点调用 `window.__TAURI_INTERNALS__.invoke("plugin:shell|open", {path})` 并 **立即 `preventDefault()`**。浏览器子 WebView 不在 `capabilities/default.json`（`windows: ["main"]`）的授权范围，invoke 被拒；`preventDefault` 已生效 → 窗口冒泡的新标签路由永远拿不到事件 → 用户看到「完全没反应」。
  - 证据（真实 WebView2 + CDP）：`DOMDebugger.getEventListeners(document.body)` 返回 click/auxclick 的 `scriptId=10`，源码为 `(function(){…document.querySelector("body")?.addEventListener("click", … e("plugin:shell|open",{path:r.href}), t.preventDefault() …})()`；点击 `更多账号信息` 的 `Event.preventDefault` 调用栈为 `at HTMLBodyElement.<anonymous> (<anonymous>:1:396)`；`open-new-tab` 消息 0 条。能力文件 `windows: ["main"]` 只授权主窗口，子 WebView 的 `plugin:shell|open` 被拒。
  - **次因（dev 实例配置）：智能体站点链接拦截是全站范围。** `init_script.js` 的 `__adlAgentClickHandler` 对白名单站点内**任意** http(s) 锚点调用 `__adlSendAgentLink('url', href)` 并 `preventDefault()`，不区分「智能体对话正文」与「站点自身 UI」。slot-1/slot-2 dev 配置为 `agent_link_intercept=true` + 白名单含 `http://127.0.0.1:3080`，DSH 设置弹窗链接因此被转成 `adl-agent-link`（实测消息 `{"type":"adl-agent-link","kind":"url","url":"https://platform.deepseek.com/"}`），默认落到右侧面板而非当前宿主的新标签。
  - 对照（Chromium + 同一 `init_script.js`、无 Tauri shell 注入、拦截关闭）：同一页面点击得到 `{"type":"open-new-tab","url":"https://platform.deepseek.com/"}` 与 `new-window link routed`。链接本身为 `<a target="_blank" rel="noopener noreferrer">`（`/`、`/usage`、`/top_up`）。
- 修复（已实施）：
  1. `init_script.js` document-start 包裹 `EventTarget.prototype.addEventListener`：注册目标为 click/auxclick 且监听器源码包含 `plugin:shell|open` 时跳过（`__adlBlockShellLinkHandler`）。子 WebView 不再被 shell 插件 `preventDefault`。
  2. 智能体拦截只作用于「站点正文」：新增 `__adlIsSiteChrome(el)`（dialog/alertdialog/menu/navigation、aria-modal、data-menu-popup、nav/header/footer/aside）；chrome 内直接返回，由正常站点新窗口路由处理。
  3. 正常站点路由 `__adlRouteNewWindowEvent` 对 agent host 的早退改为「仅非 chrome」早退。
  4. 移除 agent 站点 `window.open` 重写里的 URL 拦截（无 DOM 上下文，登录/意见反馈等站点入口保持原生）；下载分支保留。
  5. `__adlPatchShellOpen` 作为未来 Tauri 注入可用 `__TAURI_INTERNALS__` 时的兜底（当前子 WebView 无 internals，改为不依赖它）。

## [ ] 事项 2：DSH 断连 / 3080 端口被占用时的恢复交互

- 状态：已完成（2026-11-25 用户确认「所有的问题和任务都解决完成了」） | 类型：优化（交互 + 恢复策略） | 流程：P0–P3 已完成
- 决策（已实施）：
  - `/dsh/open` 默认不杀进程：端口被占用时返回 `status='port_occupied'` + 占用进程列表（pid/name/cmdline/isDsh），前端确认框确认后以 `force=true` 结束占用进程并拉起项目内 DSH。
  - 端口空闲但进程已死：自动恢复；请求超过 1.2s toast「DeepSeek Harness 已断开，正在重新启动并打开…」，入口保持 busy、重复点击提示稍候。
  - 所有入口（中心入口页、欢迎页快捷站点/本地端口、中心/面板地址栏、浏览器树）共用 `ensureDshUrl`。
  - `pre_start` 使用 `PortPolicy::Reject`：端口占用时只记录跳过，不弹框、不杀进程。
- 根因 / 现状（已确认）：
  - `openDsh` / 欢迎页 3080 分流 → `/dsh/open`。
  - 断连自动恢复**已存在但完全静默**：杀掉宿主托管的 dsh 后点击入口，入口页 `aria-busy=true` 但无任何 toast；约 **22.7 秒**后 DSH 标签才完成导航（实测 1.5/3/6/10/16/22s 时间点全程无 toast，22s 时 `page.evaluate` 因导航销毁上下文失败）。用户在这 20 余秒内看到的是「完全没反应」，会反复点击。
  - 端口被占用：`free_stale_dsh_on_default_port` 对**命令行识别为 dsh** 的占用者直接 `taskkill /F`（含用户自己 `npx @deepseek-ai/dsh web` 启动的外部实例），对非 dsh 占用者返回 `Err`，前端仅记录全局错误卡片。用户要求改为「先确认再杀」，并在断连自动恢复时给 toast。
- 修复决策（待用户确认）：
  - `/dsh/open` 不再隐式杀进程：端口被占用时返回结构化 `status='port_occupied'` + 占用进程列表（pid/name/cmdline/isDsh），前端弹确认框；确认后以 `force=true` 重新调用，后端结束占用进程并拉起项目内 DSH。
  - 端口空闲但进程已死：保持自动恢复；请求超过 ~1 秒即 toast「正在重新启动并打开」，入口保持 busy、重复点击只提示稍候。
  - 所有入口（中心入口页、欢迎页快捷站点/本地端口、中心/面板地址栏、浏览器树）共用同一解析器，避免只修一处。

- 现状问题：
  1. 标题「3080 端口被占用」是技术事实，没有先说用户目标（打不开 DeepSeek Harness）。
  2. 正文含内部术语「项目内」「dsh」；「打开…前需要先结束…。结束这些进程并重新启动项目内的…吗？」一句过长。
  3. 组件把「包含非 dsh 程序」警告拼在问句之后（`message + ' ' + warning`），读起来像事后补充；应先警告再问。
