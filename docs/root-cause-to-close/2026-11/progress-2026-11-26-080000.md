## [x] 事项 2：代码行演变 / 提交时间线 / 文件热点 标题右侧时间筛选控件缺失

- 根因（代码 + 持久化状态双重证据）：
  1. 三个图表的控件由 `TimeRangeAwareCard` 条件渲染：`timeRange.hasTimeRange && timeRange.timeRange`（`GitVisualizationView.tsx:117`）。`timeRange.timeRange` 只来自 store 的 `gitVisTimeRange[activeWorkspaceTab][chartId]`。
  2. 为这三个图表写默认范围（`defaultTimeRange()`）的**唯一**入口是 `useChartData` 的初始化 effect；提交 `90dd75aea`（2026-07-30「perf(branch-graph)」）给它加了 `initializedRef` 一次性守卫，同一组件挂载内只初始化**一个** workspace。
  3. 因此：首个渲染的 `activeWorkspaceTab` 若不是最终展示的工作区（默认 `workspace-1`、旧路径 hash、或用户在标签栏切到另一个工作区），默认范围就写到了别的工作区键上；切到真正展示的工作区后守卫已锁死 → 三个图表没有 store 范围 → 控件不渲染。
  4. 热力图组不受影响：`HeatmapCardGroup` 的控件用本地 `tabRangesRef`（有 `defaultTimeRange()` 兜底）而非 store，所以它仍然显示 —— 与用户「只有这三个没有」的现象完全吻合。
  5. 持久化取证（`%LOCALAPPDATA%\com.adlo.app.slot-2\EBWebView\Default\Local Storage\leveldb` 解码）：`adl:changes.activeWorkspaceTab = ""`；`adl-git-vis:time-range = {"workspace-1":{…5 个图表…}}`；当前工作区 id 为 `workspace_7114785d` / `workspace_8b3a686f`（`config.json` 的 `workspace_natural_order`），旧键 `workspace-1` / `workspace_5fe3ffc6` / `workspace_3bf908e6` 均不再对应现存工作区。
  6. 结论：不是「代码被删除」，而是 2026-07-30 引入的一次性守卫 + 工作区 id 变更（项目/目录改动使稳定 id 变化，旧范围键成为孤儿）共同导致的回归。

## [x] 事项 3：面板打开期间新增工作区，Git 可视化标签栏不出现新工作区

- 状态：已完成（2026-11-26 用户确认） | 类型：解决（回归） | 流程：本技能 P0–P6
- 决策（grilling 已定）：用户新增工作区后应即时出现，无需关闭再打开 Git 可视化页面。
- 根因：`WorkspaceTabBar` 的标签顺序 `tabOrder` 用 `useState(() => workspaceTabs.map(...))` **只在挂载时取一次**；渲染用 `orderedTabs = tabOrder.map(id => tabMap.get(id))`，新工作区虽进入了响应式的 `workspaceTabs`，但不在 `tabOrder` 里，被过滤掉。重新挂载（关闭/再打开 Git 可视化）会重建 `tabOrder`，所以只有那时才出现。同一缺陷也覆盖「面板先挂载、工作区清单后加载」的场景。
