Agent 编程产品如何把“工作过程”展示在界面上

从运行时事件、持久化状态到时间线 / 卡片 / Diff 的完整解释；覆盖 OpenCode、Pi、Codex、TRAE SOLO、Claude Code。

生成时间：2026-08-08 ｜ 本地源码核验：OpenCode、Pi ｜ 其余闭源产品仅依据官方公开资料与可观察产品行为，不将推断写成内部事实。

先说结论：界面展示的不是“神秘思考流”，而是一份可渲染的事件账本

通俗版：Agent 像一个在工作台上干活的人。每做一步都会写一张小票：开始读文件、读到了什么、准备运行命令、等待你的许可、修改了哪个文件、命令成功/失败。UI 只是把这些小票分别做成聊天气泡、折叠步骤、权限卡片和 Diff 面板。

专业版：成熟方案通常是 provider streaming → runtime event log → normalized state/projection → renderer。模型 token、工具参数增量、工具执行生命周期、用户决策和文件差异都有稳定 ID；前端按 ID 增量合并，断线后从权威快照/持久记录恢复。

一套产品实际需要的 6 层

层职责为什么不能省
1. 模型适配把 Anthropic/OpenAI/本地模型各自的流式格式转为统一 text_delta、reasoning_delta、tool_call。不同厂商对 reasoning、并行工具、半截 JSON 的表达不同。
2. Agent runtime工具循环、队列、取消、重试、权限策略、子 Agent、沙箱。这是“执行真相”；UI 不应自行猜测工具是否完成。
3. 事件协议有类型、ID、顺序号、时间戳的事实，例如 tool.started、permission.asked。让桌面端、Web、CLI、自动化接口能看见同一过程。
4. 存储与恢复保存关键消息、工具结果、用户批准、文件变更摘要；短暂 token 增量可只走 live stream。刷新/重连后不能丢会话，也不能把“半句 token”误当永久历史。
5. 投影状态reducer 将事件归并为按 session/message/part/request/file 索引的 UI 状态。避免每来一个 token 就重算整段会话；支持局部更新与虚拟列表。
6. 多视图渲染时间线、问答卡、授权卡、终端输出、文件树、diff、最终摘要都是同一状态的不同投影。“文件已修改”不应只藏在聊天文本中。

两种主流展示架构，以及何时选用

A. 本地 Agent server + Web/桌面 UI（OpenCode 式）

Agent 在本地进程运行，UI 通过 HTTP/RPC 做初始加载，通过 SSE/WebSocket 订阅实时事件。

可多端可重连适合桌面产品

优点：前后端解耦；浏览器、Tauri/Electron、CLI 都可复用协议；可做事件回放和远程连接。
代价/注意：必须处理顺序、去重、事件丢失和重连；不要把高频 token 逐条直接触发全树渲染，需合帧/批量；敏感工具输出与凭据需要脱敏和访问边界。

B. 进程内 runtime + TUI/IDE 扩展（Pi / Claude Code 常见）

同一进程内的 Agent 发出事件，终端 UI 或 IDE 扩展直接订阅并更新组件；也可额外导出 JSON / RPC 给外部宿主。

低延迟实现直观终端友好

优点：链路短、部署简单；终端可采用增量重绘。
代价/注意：UI 与 runtime 容易耦合；若日后要桌面/Web 多端，必须及早抽出稳定事件协议和会话持久层。

C. 云端隔离执行 + 本地/网页审阅（Codex 云端任务形态）

执行环境与交互界面分离，界面订阅远端任务状态、日志和最终 diff；用户审阅后再合并/同步。

优点：隔离强、长任务不占本机、方便并行。
代价/注意：网络延迟、文件同步、密钥和供应链安全更复杂；云端进度通常更适合展示“可验证步骤与摘要”，而非暴露原始模型内部推理。

“思考过程”到底该怎么展示？

关键区分：模型可提供 reasoning/thinking 内容，不等于产品必须或应该展示完整 chain-of-thought。安全且常见的设计是显示可验证的工作摘要（计划、正在读取的文件、将执行的工具、执行结果、错误原因），并把原始 reasoning 视模型/产品策略决定的可选私有数据。Pi 的源码确实支持 thinking 块显示/隐藏；但对于闭源产品，不能仅从 UI 猜出其显示的就是完整内部推理。
  • 推荐 UI：“正在分析 X”“准备修改 3 个文件”“测试失败：原因 Y”+ 可展开的工具输入/输出 + 文件 diff。
  • 不推荐：把无结构 token 当作唯一状态源；或把授权要求嵌在 markdown 文本里，导致无法可靠批准、超时、重试与审计。

给 AI Digital Life 的可执行设计建议

  1. 定义跨 Provider 的 AgentEvent discriminated union：run.started、message.delta、reasoning.summary、tool.proposed/started/output/result、approval.requested/resolved、question.requested/resolved、files.changed、run.settled。
  2. 为每个事件给 eventId、sessionId、runId、messageId、toolCallId、单调 sequence 与时间戳。所有 reducer 必须幂等；并行工具不能以“到达顺序”充当显示顺序。
  3. 将 durable facts（完整消息、工具参数/结果、批准、最终 diff）存盘；将 token/标准输出 delta 标为 ephemeral。重连策略：先拿快照，再订阅 afterSequence，最后合并 live delta。
  4. 将 UI 分成 Timeline、Activity/Tool drawer、Approval/Question dock、Changed files/Diff 四个投影，共享同一 store。问答与权限走 Tauri command/事件桥，浏览器 preview 也实现同一接口，以保证双端一致。
  5. 对 30–60Hz 以上的 delta 做 animation-frame 批量提交；长会话虚拟化；工具输出截断并支持“展开/下载”；任何日志先脱敏，绝不把密钥、环境变量原文自动渲染。
