# 内嵌浏览器直连搜索的人机验证风险

> **体裁**：外部证据调研（结论 + 来源 + 对 Adlo 的适配判断），不是实现规范，也不改源码。
> **调研日期**：2026-11-23（下表「访问日期」均为该日）。
> **范围**：Google / Bing 搜索人机验证的触发条件；Cloudflare / DataDome / Akamai / HUMAN 公开文档对「自动化 / 嵌入式客户端」的判定；合规边界；`/search?q=` 深链与首页搜索的差异。
> **方法说明**：本网络环境无法直连 Google 域（`curl` 与抓取工具均超时），Google 官方页文本经搜索引擎索引取得并与官方 URL 一一对应；其余来源为直接抓取。反检测教程、打码服务、爬虫框架文档一律不作为结论依据，只在能反证或标注为社区观察时引用。

## 1. 结论摘要

1. **Google 官方把「unusual traffic」归因于网络/IP 层面的自动化流量**：VPN、IPv6 隧道、学校/公司等共享网络、ISP 上的其它滥用者、恶意软件，以及「机器人、程序、自动化服务、搜索抓取器、排名查询软件」。官方页面**没有**把「过期 cookie」「未登录」「新设备」「地址栏直接搜索」列为触发条件。
2. **但 Google 官方确实承认 cookie/JS 缺失会让 reCAPTCHA 不可用**：Project Shield 文档写明关闭 JavaScript 或 cookie 的读者、无痕模式读者可能无法访问受 reCAPTCHA 保护的站点；reCAPTCHA 自身依赖 `_GRECAPTCHA` cookie 做风险分析。因此「冷 profile 降低通过率」是**可解释的机制**，不是官方公布的「触发条件」。
3. **「清除/过期 cookie 会更容易被验证」在官方口径里不成立，方向上甚至相反**：Google 帮助页与 Google 社区都把「清缓存和 cookie」当作排障手段；社区侧真正被反复观察到的相关现象是「验证通过后 Google 会下发一个豁免 cookie，没有它就会反复被问」。
4. **Bing 没有任何官方文档说明搜索验证的触发条件**。微软公开的只有 Microsoft 账号安全检查的排障页（无痕、拦截器、VPN/代理、cookie+JS、共享网络 IP 被标记、损坏的浏览器数据），它与 bing.com 搜索验证是否同一套规则**未经证实**。
5. **反爬厂商公开文档确认的通用信号**包括：TLS/JA3-JA4 与 HTTP/2 指纹、HTTP 头顺序与「声称的浏览器版本 vs 实际执行行为」不一致、headless/自动化框架、`navigator.webdriver`（HUMAN 明确点名）、**「内建函数与属性的一致性」检查**（DataDome 明确点名）、行为遥测（鼠标轨迹、时序）。
6. **没有任何厂商公开文档点名 WebView2 / Electron / Tauri / `chrome.webview`**。Cloudflare 反而在移动 WebView 文档里官方支持运行 Turnstile，并给出硬性要求：JS + DOM storage、**全程 UA 一致**、设备特征稳定、**不得修改核心浏览器行为**、**cookie/localStorage 必须持久**；「会话中途改 UA」「存储不持久」都会直接导致挑战失败。
7. **嵌入式环境不是「必然被拦」，而是「容错更低」**：Cloudflare 把「embedded browsers / 重度修改的浏览器引擎」列为 limited support，把「自动化浏览器、Selenium/Puppeteer/Playwright/Cypress」列为不支持解生产挑战。Akamai 白皮书进一步说明：内置浏览器框架可能缺少反爬所需的能力，建议改用独立浏览器实例。这是目前最接近「WebView 更容易被验证」的一手厂商表述，但它是**能力缺失**，不是「厂商专门针对 WebView」。
8. **对 Adlo 而言，地址栏深链本身不是主因**。Google 自己的 Chrome 帮助文档给出的地址栏搜索 URL 就是 `https://www.google.com/search?q=%s`——Chrome 从地址栏搜索也走同一个深链。真正的结构性差异在会话状态与客户端指纹：两套独立 UDF 造成的冷 profile、每页注入的 init script（覆盖 `window.open`、`Location.prototype`、`history`、`document.title` 并接管点击）、`window.chrome.webview` 与 Tauri 注入的全局，以及元数据补抓路径可能用空 profile 的隐藏 WebView 再加载一次（非每次搜索必然触发）。
9. **合规红线清晰**：Google ToS 要求「不得用界面以外的方法访问」，Microsoft Services Agreement 要求「不得规避访问限制、不得绕过技术保护措施」。**自动解/代过验证码、伪装 UA/Client Hints、隐藏 webview 标识、代理池轮换**属于规避检测/规避访问控制，不应做；**减少自家多余指纹、保持标准会话、让用户手动完成验证并保留结果 cookie**属于正常工程范围。

> **口径纠正（重要）**：本仓既有诊断笔记写了「Google 官方文档明确『发送过期 cookie 时可能被判定为异常流量』」（`docs/root-cause-to-close/2026-11/progress-2026-11-23-191217.md:15`）。本次逐字复核 `support.google.com/websearch/answer/86640` 全文，**没有** cookie 相关表述；官方只要求「JavaScript 已启用」。该说法应降级为「社区观察/机制推断」，不能作为官方结论引用。

> **界线（本报告的判断，不是法律意见）**：
>
> - **正常工程**：保持默认 UA、让 cookie 在同一 profile 内持久、按标准导航访问、减少自家脚本对页面原生对象的改写、减少自家后台自动请求。
> - **灰区**：把「先访问首页再搜索」做成自动流程（无用户意图时近似「养号」）；验证码出现后自动重试；为通过评分而人为制造浏览历史。
> - **不可做**：伪造 UA / Client Hints、隐藏 `chrome.webview` 或 `__TAURI_INTERNALS__`、注入 stealth 补丁、自动解/代过验证码、代理池轮换、复用他人 cookie、把 SERP 抓取伪装成浏览器。
> - 条款风险是确定的；「绕过技术保护措施」在各国法律下的定性不同（美国 CFAA 类争议、欧盟与中国的对应规则各异），需法务判断，本报告不给结论。

### 3.2 可控 / 不可控 / 不能做

**可控（代码与产品决策）**

- 停止对原生对象的覆盖，优先用 WebView2 原生事件实现同等能力（`NewWindowRequested`、`DownloadStarting`）；这是当前最像「反检测规避目标」的一类自家改写。
- 减少不必要的全局注入与点击拦截的作用域（例如仅在需要的 origin 上启用 agent 拦截）。
- 让元数据抓取对「搜索引擎结果页」直接跳过（不依赖 robots 的 fail-open），并让隐藏 WebView 路径也遵守同一份 deny-list。
- 同一 UDF 内保持 cookie 持久；不要在退出/切 tab 时清理会话；不要人为缩短 cookie 生命周期。
- 保持默认 UA 与 Client Hints；不要在 tab 之间切换 UA 或语言。
- 把「打开系统浏览器」作为验证码逃生通道（系统浏览器有真实、温暖的 profile）。

**不可控**

- 出口 IP 的信誉、是否共享网络/VPN、ISP 段历史（Google 官方明确把这些列为首要因素）。
- Google/Bing 的判定模型、阈值、是否下发豁免 cookie。
- reCAPTCHA 是否出现、出现的是 checkbox 还是图片网格。
- 地区差异（EEA/UK/CH 的同意流程会额外插入 consent 页）。
- WebView2 与 Edge 的运行时差异（两者同引擎、同 UA、同 TLS 栈；这部分对 Adlo 有利）。

**不能做**

- 伪造 UA / `Sec-CH-UA` / 平台 / 时区来「看起来像 Chrome」。
- 隐藏 `window.chrome.webview`、`__TAURI_INTERNALS__` 或自家注入痕迹（stealth 补丁）。
- 自动解验证码、接第三方打码、复用他人 `GOOGLE_ABUSE_EXEMPTION` cookie。
- 代理池轮换、按请求换 IP。
- 用 `Adlo/1.0 … MetaFetcher` 直接抓取 `/search` 结果页并解析。

**双端一致性提示**：浏览器模式（Vite 预览，真实 Chrome/Edge + 正常 profile）通常比桌面 WebView2 更容易通过验证。这是用户可感知的行为差异；修复方向应是让桌面端更接近标准会话（上表 P0/P1），而不是给浏览器模式增加同样的人为限制。
