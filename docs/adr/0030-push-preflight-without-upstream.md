# 无上游推送：后端保留自动建立上游，前端必须先预检且绝不自动提交

**Status**: accepted（2026-11-22）

变更面板的「推送」在无 upstream 分支上，后端会静默执行 `git push -u <remote> HEAD`（优先 `origin`，否则唯一远程）。这意味着「无上游」不会失败，用户也无法从结果看出远端分支何时被建立。决定：

1. **保留后端自动建立上游的行为**，不在 Rust 侧改成「无 upstream 即报错」；远端分支的建立仍由一次正常 push 完成。
2. **前端在推送前显式预检**：先刷新该工作区快照并读取当前分支；只有「工作区干净且已有 upstream」才直接推送；否则弹出一次合并确认，提供「提交并推送」「仅推送已提交」「取消」。
3. **绝不自动提交**：选择「提交并推送」时复用既有提交对话框，提交成功后自动继续推送（`ahead` 按提交前数值 +1）；提交失败不推送，原因留在提交对话框。
4. **失败统一进右下角错误提示卡**（`level=error` + 重试）；重试前重读 `ahead`/upstream，成功后清掉该工作区同一 scope 的旧失败卡。首次推送成功使用通用「推送成功」，有 upstream 时按 `ahead` 显示数量或「已是最新」。

## Considered Options

- **后端拒绝无 upstream 的推送**：能强制用户先配置，但会让「首次推送」变成两步外部操作，且改变已有 IPC 语义；前端仍要解释失败原因，收益不足。
- **前端对所有推送都弹确认**：行为最一致，但干净且已有 upstream 的日常推送多一次无信息量的点击。
- **静默自动 `push -u` + 不提示**：路径最短，但用户无法确认「远端分支被创建」这一有副作用的决策，也无法选择先提交本地改动。
- **脏工作区自动提交后再推送**：少一步交互，但提交信息的语义与责任被应用代劳，属于不可接受的自动化。

## Consequences

- 「无 upstream」从错误态变成可确认的正常路径；文案与测试需区分「首次推送成功」「已推送 N 个提交」「已是最新」。
- 同一工作区的推送/拉取共享忙碌互斥，错误卡重试也走同一守卫；重试前必须重新读取分支状态，不能用失败时的旧值。
- 复测首次推送需要干净的、从未推送过的分支或工作树；已被推过一次的分支会自然拥有 upstream。
