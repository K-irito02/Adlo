# 站点元数据改为按需补齐，显式刷新分两段抓取

**状态**: accepted
**日期**: 2026-11-23

启动批量预热会为每个书签/历史条目创建隐藏 WebView，造成启动抖动与日志噪声，且未展示的条目并不需要立即补齐。现决定：移除启动预热；被动条目在展示且缺图标时按需做一次轻量元数据读取（不发完整页面渲染），同一域名 5 秒间隔、每分钟 40 次预算，超出预算的条目留在队列中等待而不是丢弃；用户显式「刷新网站图标与标题」先做轻量读取拿图标，再做一次完整渲染拿渲染标题，轻量读取得到的静态标题不写回标签或历史；完整渲染只用于显式刷新与活跃条目的失败回退。robots 判定与预览端保持同一语义。

## Considered Options

- **保留启动批量预热**：启动时一次性补齐全部书签/历史；但每条都要建隐藏 WebView，条目越多启动越抖，且用户可能永远不打开这些条目。
- **被动条目逐行走静默渲染**：补齐最完整；但列表一次渲染数百行会形成隐藏 WebView 风暴，资源与日志都不可接受。
- **全程只做轻量读取（含标题）**：成本最低；但单页应用与详情页的静态标题往往只是站点名，会把已渲染的真实标题降级，且无法兑现「刷新标题」。
- **本次采用：按需轻量补齐 + 显式刷新两段**：启动零预取；被动列表只做限速的轻量读取；只有用户显式刷新或活跃条目失败时才做完整渲染。

## Consequences

- 冷启动不再批量修复全部书签；缺图标的条目在首次展示后逐步补齐，补齐时间取决于域名限速与预算。
- 显式刷新最坏要等一次轻量读取加一次完整渲染（数秒级），这是用户主动操作的代价；换来的是渲染标题与静态标题不会互相覆盖。
- 静态标题永远不会写进标签或历史；完整渲染失败的条目保持原状，不降级、不锁死后续渲染标题的更新。
- 限速与预算都是会话内存状态，重启后清零；失败条目仍按失败墓碑退避，不会因重启反复重抓。
- 隐藏页面渲染成为显式/回退路径，被动路径不再创建隐藏 WebView；后续若新增被动入口，不得绕开这一约束。
