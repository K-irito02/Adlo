# 应用更新走官方 updater：清单双源（Gitee 优先、GitHub 兜底），签名密钥不可轮换

**Status**: accepted（2026-11-18）

桌面应用自身的版本升级使用官方 `tauri-plugin-updater`，不做自研安装器。决定：**构建期由 minisign 私钥签名安装包，公钥内置在 `tauri.conf.json`；版本清单（`latest.json`）同时发布到 Gitee 与 GitHub 两处，应用按「Gitee → GitHub」顺序尝试，并在交给插件前先用应用自己的代理感知 HTTP 客户端预检清单内容是否可用；只发布 NSIS 安装包并按当前用户安装，MSI 与绿色包不参与自动更新；版本号以 `tauri.conf.json` 为准，tag 固定 `vX.Y.Z`，只做稳定通道。**

## Considered Options

- **只做「检查 + 打开下载页」**：实现最省，无需签名与清单；但用户每次更新都要手动下载、手动安装，且首个公开版本之后仍要再返工一次交互与发布流程。
- **自研下载 + 调起安装器**：用 SHA-256 校验、避开 minisign；但完整性只到「清单与安装包同源发布」这一级，进度、失败恢复、安装等待都要自己写，等于重造官方插件。
- **官方 updater + 只挂 GitHub**：最省运维；但 GitHub 在大陆直连不稳定，正是本项目要避免的单点。
- **官方 updater + 双源清单**（本次采用）：签名校验、进度事件、被动安装都由插件提供；代价是每次发版要向两处发布清单，并且 Gitee 侧要接受「清单放仓库文件」这一变通。
- **Gitee 侧用 Pages 或固定 tag 的滚动附件**：前者需实名且有下线历史，后者要反复删传附件、接口不稳；仓库内 `release/latest.json` 的 raw 直链是唯一稳定且可匿名的选择。

## Consequences

- 私钥即更新通道的根信任：**丢失则永远无法给已安装用户推送更新**，泄露则等于把通道交给第三方。私钥与密码各存两处离线介质，CI 只读 Secret。轮换必须先发一个「同时内置新旧公钥、用旧私钥签名」的桥接版本，再下一版只用新密钥。
- 插件只在 HTTP 非 2xx 时切换下一个 endpoint，因此「Gitee 返回 200 但内容是网关 HTML」不会被自动兜底——预检必须由应用自己完成，否则这类故障会表现为「检查更新永远失败」。
- Gitee 没有「永远指向最新 Release」的稳定地址，清单因此落在仓库 `main` 分支的 `release/latest.json`；每次发版多一个机器人提交，这是双源方案的固定成本。
- Windows 上安装开始时应用会被强制退出：更新只能在用户主动点「安装」后发生，不能静默替换正在运行的应用。
- 只发 NSIS 意味着不提供 MSI 企业分发；将来若要加，MSI 必须明确标注「不参与自动更新」，否则同一台机器会出现两份安装记录。
- 浏览器模式没有可被替换的安装体：更新入口保留但禁用，并说明「随宿主构建更新」。
