# 站点元数据失败墓碑持久化 + 请求键别名回写

**状态**：已接受
**日期**：2026-11-12

## 背景

启动预热（GLOSSARY「启动预热」）为被动条目批量补齐站点元数据。此前失败抓取
（超时/登录墙/反爬）不写入任何缓存条目，`fail_count`/`next_retry_at` 字段形同虚设 →
永久失败站点每次启动都重抓；且 WebView2 上报的是跳转后 URL（GLOSSARY「重定向分叉」），
`report()` 把条目写在上报 URL 键下，而启动预热与 `browser_page_meta_get` 只按请求 URL
键 `peek`，重定向站点永远 miss。两个分叉叠加：dev 实例每次启动重建几十个隐藏 WebView2
重抓同一批书签。

## 决策

1. 失败落「失败墓碑」：只写失败计数 + 下次可重试时间（指数退避 `min(5min×2^min(n,5), 2h)`），
   保留既有标题/图标字段，且**持久化**（Rust SQLite / 预览 JSON），跨重启生效。
2. 静默抓取结束后按**请求键**别名回写：非空 meta 走既有 `report` 门控（占位/质量/data-URI
   守卫不变），全空落墓碑。预热与 get 均用统一的「有效缓存命中 ∨ 退避中」短路。
3. 不引入清理 TTL，不为墓碑设最大寿命；成功的 `report` 自然清零退避。

## 取舍

- 墓碑持久化 vs 仅会话内存：刻意优于预览端原状（预览端原为会话内存，已一并改为持久化）。
- 双写别名 vs get/warmup 双键 peek：双键探测需要"请求键 → 上报键"的映射，而映射本身
  依赖一次成功抓取（鸡生蛋）；双写复用既有门控、无需新结构，且别名写入对无重定向场景无害（重复 report 为 no-op）。
