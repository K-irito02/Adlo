# 设置刷新按行/块限定作用域，环境按依赖重检

设置面板的刷新从「只有个别按钮」扩展为统一能力后，最容易退化的语义是**作用域**：一次刷新到底影响一行、一个块，还是整组。约定如下。行级刷新只重读本行，进行中不禁用或变淡其它行；同一时刻的多次显式刷新在内部串行，且只允许最后发起的那次快照写回，避免旧响应覆盖新读数。块级刷新重读本块全部内容（含没有行级图标的行），与行级刷新共用同一条队列和卡片忙碌门。

环境组另有独立后端契约：`/env/recheck` 接收 `{ deps?: string[] }`，只探测请求的依赖并与当前缓存合并，未请求字段保持原值，因此「基础依赖」与「系统组件」两块互不联动；`netprobe` 表示外网连通性而非可重装依赖，请求中出现即 4xx。冷缓存（进程内尚无快照）退回全量探测并写回，此时两块会一起变新，属已知耦合。界面文案据此分工：行/块图标统一称「刷新」，环境聚合按钮称「重新检测」。

**Considered Options**: 全组刷新——实现简单，但每次操作都会重检无关依赖、两块无法独立，且与「不联动禁用其它行」的用户要求冲突；每行各自并发拉快照——更快，但旧响应可能覆盖新读数，回归过版本读数的既有竞态；环境块也走全量重检——避免冷缓存耦合，但网络探测与无关依赖会被反复触发，违背「按块独立」；允许 `netprobe` 重检——没有可重装语义，只会制造虚假的刷新入口。

**Consequences**: 新增环境依赖时必须同步加入 `recheckable` 集合，否则 `/env/recheck` 会以 4xx 拒绝；冷缓存退回全量这一点必须保留在架构文档中，不能因为「两块的旧值一起变新」就误判为联动 bug；串行队列当前是面板实例级的，跨挂载不保证全局串行，后端合并仍须保持锁内原子；显式刷新失败必须有用户可见反馈，卡片忙碌（安装/卸载/检查在途或桥不可用）时才禁用刷新动作，行级刷新在途不属于卡片忙碌。
