# 编辑器存盘分离「未保存草稿 / 已保存版本 / 外部版本」，自写回声不得触发存盘冲突

**Status**: accepted

文件面板保留 1s 空闲自动保存，但存盘链不再把一次保存的响应直接写回编辑器。决定：**同一文件的保存按调用顺序串行；只有仍持有最新草稿的保存请求可以推进「已保存版本」；应用自身写入产生的工作区通知按内容指纹识别为「自写回声」，不得立存盘冲突；真实外部变更由磁盘内容与已保存版本/草稿比对后判定；保存前若存在新鲜的工作区信号，先读盘复核。** 异步读盘落定后必须重取草稿与当前选区；有未保存草稿时不得把磁盘旧快照写回编辑器的受控 `value`，也不得把外部内容写入按文件身份保存的「已保存版本」缓存。

## Considered Options

- **只修两个症状的最小补丁**：给外部旗加 mtime 判断、给保存响应加草稿判断。改动小，但保留「编辑器受控值与磁盘基线是同一字段」的结构缺陷，后续格式化、补丁应用、分支切换仍可能重新引入回退。
- **完整 VS Code 式自动保存**：增加 `off` / `afterDelay` / `onFocusChange` / `onWindowChange`、热退出与 Compare 视图。产品化程度最高，但超出本次问题范围，且会引入设置 UI、持久化与双端行为决策。
- **本次采用的结构化修复**：保留现有自动保存交互，按「草稿 / 已保存版本 / 外部版本」分离职责，只补齐串行、代际、回声识别与读盘分类。

## Consequences

- `fileContent` 的语义是「已保存版本」，不是编辑器的实时缓冲区；有未保存草稿时禁止用它回写受控 `value`。
- 每次保存遇到新鲜 watcher 信号可能多一次读盘；这是为区分自写回声与真实外部变更付出的成本，不要按「每次保存都必须零额外 I/O」去优化掉。
- rename / move 等改变路径的操作必须先 flush 草稿，否则草稿键会与新路径分叉。
- 真实外部冲突仍然由冲突卡片裁决；「保存成功」不等于可以清掉外部旗，只有磁盘内容与已保存版本/草稿一致时才可清。
- 相关术语见 [GLOSSARY.md](../../GLOSSARY.md) 的「未保存草稿」「已保存版本」「自写回声」「存盘冲突」。
