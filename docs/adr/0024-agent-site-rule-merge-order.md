# 智能体站点规则合并：站点优先、同 id 替换、停用只作用全局

**Status**: accepted（2026-11-14）

智能体站点规则分两层：全局规则对全部白名单站点生效，站点覆盖携带该站点自己的站点规则与「停用全局规则」清单。决定：**合并时先放站点规则、再放全局规则；同 id 时站点规则替换全局规则，命中顺序也靠前；`disabledRuleIds` 只作用于全局规则，站点规则用自身启用开关表达；查找从点击目标所在元素起向上逐级进行，同一元素内按合并后的顺序自上而下尝试，选择器与属性值满足且能解析出可打开目标才算「命中」，命中即停止；匹配成功但目标不可解析时继续尝试同元素的下一条规则，再上溯。** 「本地文件」预设固定打开文件，「自定义正则」可选择打开文件或打开网址；打开网址的相对值按页面解析且只接受 http(s)，打开文件只接受显式本地路径（`file://`、盘符或 UNC）。

## Considered Options

- **全局优先、站点规则追加在后**：实现更直观，但站点覆盖无法替换同 id 的全局规则，用户只能靠相互冲突的规则顺序碰运气；停用全局规则与追加站点规则也会出现「先命中谁」的歧义。
- **引入显式 priority 字段**：表达能力最强，但把排序责任推给用户与外部 Agent，配置更难写对，也容易与列表顺序产生第二套优先级来源。
- **按 id 合并属性（站点规则只覆盖同 id 规则的字段）**：可以避免整条替换，但规则字段之间存在联动（选择器、属性、预设、动作），部分覆盖会产生用户无法预期的组合。
- **本次采用：站点优先 + 同 id 整条替换 + 停用只作用全局**：与「站点覆盖是局部调整」的模型一致；用户看到的顺序就是实际命中顺序，同 id 的站点规则是明确的整体替代。

## Consequences

- `config.json` 的规则数组顺序是有语义的：同一层内先列出的规则先命中；外部 Agent 直接改配置时必须保持这一点。
- 站点规则停用（`enabled: false`）时，同 id 的全局规则不会回退生效——该 id 在这个站点上就是关闭状态。这是「替换」语义的必然结果，不是遗漏。
- 匹配成功但目标不可解析（例如打开网址命中 `ftp://`，或自定义正则命中相对路径后按打开文件解析）不算命中，继续尝试同元素的下一条规则，再上溯；因此「命中」与「选择器匹配」不是同义词。
- 元素上溯是有语义的：内层元素先于外层元素尝试，外层容器的规则不会抢走内层链接的点击。
- 站点规则先合并意味着站点上的同 id 规则永远压过全局版本；修改全局规则不会影响已被站点同 id 覆盖的站点。
