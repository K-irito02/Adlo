# 0020 · 网站图标以共享镜像为真源，书签图标快照只播种不落持久层

**状态**：已采纳
**日期**：2026-11-12

## 背景

从 Edge / Chrome 导入的书签在本机从未访问过，站点元数据缓存里没有条目。图标槽位把
「从未抓取」当成「加载中」处理，靠 5 秒超时降级成首字母；而浏览器面板的树行在折叠/展开时
会重新挂载，超时状态不保留——于是每次展开都重新转圈。导入文件本身携带 `ICON` 图标快照，
已写入书签条目的 `iconUri`（见 ADR-0017 的 2026-11-12 修订），但没有任何展示路径消费它。

共享站点元数据缓存（标题与网站图标）是标签页、书签、历史共用的既有真源；持久层的
`should_replace_favicon` 规定已有图标以 `data:` 开头时永不替换。

## 决定

1. **网站图标真源 = 共享站点元数据镜像**（持久层 + 前端只读镜像）。标签页、书签、历史、
   搜索里的收藏行都从这一份取图标。
2. **书签 `iconUri` 只作为镜像的播种来源**：导入成功后、以及每次启动水合完成后写入前端
   内存镜像，**不写入共享持久层**。真实图标以 data-URI 广播到达时覆盖快照；仅携带
   favicon URL 的广播保留快照（与 `applyBroadcastUpdate` 的既有合并语义一致）。
3. **图标占位由调用方声明**：活跃条目（有在途元数据抓取）显示加载指示；被动条目
   （书签 / 历史 / 搜索收藏行）直接显示站点首字母，不挂超时计时器。

## 备选方案与取舍

- **把快照写进共享持久层（含 provisional 标记）**：否决。`should_replace_favicon` 对
  `data:` 的不可替换规则会让快照永久锁定真实图标，必须同时改 Rust schema、迁移与双端
  镜像，收益与风险不匹配。
- **保留组件内统一的 5 秒超时占位**：否决。组件无法知道「是否真有在途抓取」，被动列表
  每次展开都会重演一次加载态——正是本次要消除的问题。
- **展示侧直接读 `iconUri`、不播种镜像**：否决。搜索等消费同一镜像的入口无法受益，
  每个列表都要各自记得传快照。

## 后果

- 跨会话依赖启动播种（书签 `iconUri` 是持久化真源），共享持久层不新增 schema。
- 导入文件没有 `ICON` 的条目在真实抓取前显示首字母；真实图标到达后原地升级。
- 搜索等消费共享镜像的入口自动获得导入图标。
- localStorage 会因导入图标增长（见 ADR-0017 修订记录的已知代价）。
