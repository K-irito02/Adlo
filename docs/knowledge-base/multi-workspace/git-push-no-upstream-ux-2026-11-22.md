# Git 推送无 upstream 的前后端语义与反馈（2026-11-22）

## 背景

变更面板的「推送」在无 upstream 分支上曾表现为：点一下就直接成功，但用户不清楚远端分支是何时建立的；同时失败只有顶部 toast，提交/推送的先后关系也不明确。

## 根因与事实

- Rust 后端 `push` 在没有 upstream 时会自动执行 `git push -u <remote> HEAD`（优先 `origin` 或唯一远程）。**这是既定后端行为，不是前端 bug**。
- 因此前端不能假设「无 upstream 的推送会失败」；必须在动作前显式确认「是否提交当前改动 / 是否建立上游」。
- 前端若在失败后把错误卡挂在 `git:push:<workspaceId>` 这类带工作区的 scope 上，后续成功必须按**前缀**清卡；`clearErrorToasts(scope)` 的完全相等匹配不会清掉它们。

## 现行 UX 契约

1. 推送前先刷新该工作区快照，再查 `listGitBranches`；只有「干净 + 有 upstream」才直推。
2. 其余情况弹一次合并预检：`提交并推送` / `仅推送已提交` / `取消`。
3. 提交成功后自动推送，`ahead` 按提交前数值 +1；提交失败不推送，原因留在提交对话框。
4. 首次无 upstream 推送成功显示通用「推送成功」；有 upstream 按 ahead 显示「已推送 N 个提交」或「已是最新」。
5. 推送/拉取失败写右下角持久错误卡（`level=error` + 重试），重试前重读 ahead/upstream，成功后清掉该工作区旧卡。
6. 忙碌态放在 `workspaceSlice.gitOpsBusy`：同一工作区的菜单、行内按钮、错误卡重试共享串行守卫；工作区标题显示文字扫光。

## 测试注意

- 用独立测试仓库验证时，若分支已被推过一次，它就有 upstream；要复测「首次推送」需新建分支或工作树（例如 `feature-no-upstream-3`）。
- 断网/拒绝推送可用无效远程或中断网络模拟；不要依赖「删掉本地 upstream 配置」后立即断言失败——后端会自动 `-u` 重建。

## 教训

- 后端「自动做对」的行为，前端仍要把它变成用户可确认的决策，否则成功也像意外。
- 带作用域的错误提示要有明确的清理路径；嵌套 scope 场景优先使用前缀清理。
