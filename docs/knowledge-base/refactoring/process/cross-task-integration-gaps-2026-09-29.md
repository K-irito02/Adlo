# 逐任务审查看不见的「跨任务整合缺口」（2026-09-29）

## 背景

一次 14 任务的 SDD（subagent-driven-development）执行：每任务都有独立实现者 + 独立审查者（spec 合规 + 代码质量双判定），全程 14/14 通过；之后又做了一轮「全分支审查」。全分支审查在**无 Critical** 的前提下抓出了两个逐任务审查**结构上无法发现**的问题。

## 抓到了什么

| 缺口 | 为什么逐任务审查看不到 |
|---|---|
| 聚合「恢复全部默认」的同名按钮「立即迁移并重启」**只提示、不重启**，与组级同名按钮行为分叉 | 组级流程（任务 6/8）与聚合流程（任务 10）分属不同任务，各自内部自洽；分歧存在于**两者的语义对照**，任何单任务审查都不会把两条相邻流程并排比对 |
| 存储「本来就全默认」被显示为「存储不可用，已跳过」 | 返回 `null` 的决定在任务 2（纯函数层），把它一律渲染为「不可用」的文案在任务 10（对话框）；两侧各自通过了各自的任务审查 |

另有一类同类问题：**只提示一条 toast**（双失败场景的单错误契约收窄）、**`downloadFailure` 在编排器里被丢弃**——都是「生产者特意多返回了信息、消费者没有消费」的跨任务漏接。

## 根因

1. **任务边界切在「文件/职责」上，而缺口长在「接口两侧的语义」上。** 每个任务审查者只看自己那段 diff + 自己的 brief，brief 里写的是「本任务要做什么」，不含「相邻任务承诺了什么」。
2. **计划/规格本身可能把要求写偏。** 本次设计文档写「沿用现有重启提示文案」，而正确要求是「沿用重启**动作与**文案」；计划写「`null` → 不可用」，而 `null` 实际承载了四种语义。逐任务审查不会质疑自己被分配的需求，于是忠实实现了偏掉的需求。
3. **测试由实现者按 brief 写。** brief 没覆盖的组合（异步锚点、双失败、首组失败）自然没有测试，绿测会给假信心——本次「锚点跳转」的测试恰好只覆盖唯一能通过的同步路径。

## 对策（已在本项目落地）

1. **保留「全分支/全分支审查」这一环，且用最强模型。** 它的价值不是重复检查代码质量，而是**跨任务语义对照**。审查提示里应显式要求：「把新流程与其**被替代的既有流程**逐项差分」「核对生产者多返回的字段是否被消费」。
2. **把「差分既有流程」写进计划的 Self-Review 检查项**：凡是「把 A 流程改成走共享实现」或「新增一条与既有流程同名的入口」，都要逐项列出被替代实现的每个分支/文案/动作，并声明新实现如何对应。
3. **接口返回判别联合而非 `null`/布尔**，让语义不同的结局在类型上不可混淆（消费者被迫穷尽处理）。
4. **提取共享逻辑时先枚举「多错误并存」的组合**，判断单错误契约是否够用；不够就让返回值携带关键子步骤的独立结果。
5. **让「不修复」也必须成文**：审查发现的每一条都要有裁决 + 理由 + 若判断有误的代价，供人类伙伴复核。虚假的「pre-existing」标签本身就是一种错误（本次一条「改前就如此」的判定被审查者推翻：该行为变更是本次提取引入的）。
