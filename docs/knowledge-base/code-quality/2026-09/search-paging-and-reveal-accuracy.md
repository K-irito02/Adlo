# 检索分页与跳转落点精准化（事项 1–5）

> 日期：2026-09-18 | 来源：文件面板检索模式优化（右侧面板 → 检索文件模式），含两轮多 Agent 审查循环

## 背景

本轮解决了 5 个事项：预览落点高亮（直角贴边 + 远距瞬时定位）、高亮时序缺陷、大纲导航瞬时定位、编辑器链路"首次点击落点不准、第二次准"（偶发）、检索结果分页与「显示全部」。过程中沉淀了三条可复用教训。

## 关键经验

### 1. 分页上限用"提前 return"会把截断伪装成"已取尽"

原实现在命中累计到 `MAX(200)` 时直接 `return`，导致两个问题：**第 200 条之后的文件根本没被搜索**（用户以为"没有结果"，其实是"没扫到"）；且不回总数，前端只能用"命中数 ≥ 上限即视为被截断"的保守推断（恰好取尽会误报）。

**修复模式**：分页窗口 `{offset, limit}` + "跳过 offset → 收满 limit → **再多探一条**判定 `hasMore`"。多探一条让 `hasMore` 成为精确值，"恰好取尽"与"还有更多"可区分。另外：**凡因取消而提前退出的扫描，必须保守上报 `has_more = true`**，否则取消竞态下的截断页会伪装成"已取尽"终结 UI 的续页入口。

### 2. CodeMirror 高度表是估算值：落点校验必须用渲染后几何，且基准要与滚动 API 一致

`EditorView` 的内部高度表在内容被绘制前只是**估算值**（官方 System Guide：*"initially estimated, measured accurately when content is drawn"*）。用 `getTopForLineNumber`（取自高度表）连续两次采样相同来判定"已稳定"，会**稳定在错误位置**，误差随行号线性放大（1439 行 × 每行几像素 ≈ 数百像素）。

**修复模式（渲染实测闭环）**：用 `coordsAtPos(pos)` 读**绘制后**的真实几何与滚动容器中心求差，偏差即校正（`nudged`），未渲染则重发近似定位（`redispatched`），连续 N 次实测在容差内才认为到位。

**两个容易踩的坑**：
- **基准必须与滚动 API 一致**：`scrollIntoView(pos, { y: 'center' })` 居中的是**整行块中心**（源码：`topPos = (block.top + block.bottom) / 2 - viewHeight / 2`），不是行首。若实测基准用"行首 top"，已正确居中的行会被判成"偏上约半行高"，触发一次约 9px 的虚假校正下沉。两个子代理曾对此结论相反，最终以源码裁决。
- **量测行必须与揭示行同口径钳制**：stale 越界行不钳制时 `doc.line()` 抛 RangeError → 量测恒失败 → 重发循环直到上限，帘子拖满 3s。钳制逻辑抽成唯一 helper 供揭示与量测共用。

### 3. 工程侧：Windows 下脚本写文件的三个坑

- Python 以文本模式 `open(p, 'w')` 写文件会把 `\n` 转成 `\r\n`（项目基线 LF，ESLint 报 `Delete '␍'`）——改完必须用二进制方式核对/修回换行符。
- `git diff --name-only` 输出的是**仓库根相对路径**，而 `git diff -- <path>` 的 pathspec 相对当前 CWD——从子目录执行会全部未命中，生成一批 0 字节快照。生成快照前逐文件核对非空。
- `while read` 管道读清单时，末行若无换行符会被 `read` 静默跳过；用 `find` 而非 `ls`（点文件会被 `ls` 隐藏）核对产物数量。
