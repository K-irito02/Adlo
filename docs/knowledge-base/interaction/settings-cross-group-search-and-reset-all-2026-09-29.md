# 设置面板跨组搜索与「恢复全部默认」交互经验（2026-09-29）

## 背景

设置面板首行工具栏改造：

- **搜索**：原先只检索 `general` 组 8 项、且搜索态会卸载富组件；改为跨全部 6 组的跳转式搜索（统一索引 + DOM 锚点 + 滚动高亮 + `mod+F`）。
- **恢复全部默认**：原先只重置偏好 patch，静默忽略存储/浏览器/DSH 三组；改为聚合四组（偏好 → 浏览器 → DSH → 存储），存储最后（可能迁移文件并重启）。

## 经验 1：跳转到「异步挂载」的锚点，单帧 `requestAnimationFrame` 一定不够

最初实现是「切组 → 下一帧 `querySelector(锚点)` → 命中就滚动高亮，未命中静默返回」。它在同步渲染的组（`workspace`、`browser`、`storage:corePaths`）都能工作，测试也只覆盖了同步的 `workspace` 锚点 + `waitFor`，**恰好绕开了唯一会失败的路径**：`storage:treeCache` 的锚点在 `treeStats ? (…)` 条件内，而 `treeStats` 初值取缓存、为空时需异步 IPC 回包——冷缓存下切组后一帧内锚点必然不存在，于是「切了组但没有滚动、也没有高亮」，且没有任何错误提示。

**结论**：跳转目标是**数据驱动、可能延迟挂载**的元素时，必须用「状态化意图 + 有界重试」而非单帧查询：

- 把跳转意图存进 state（如 `pendingJump = { group, anchor }`），由 `[pendingJump, activeGroup]` 驱动的 effect 解析；
- 锚点未出现则逐帧重试，且有**明确上限**（时间上限比帧数更稳，避免高刷屏/低帧率差异）；
- 上限用尽要停止并留下可观测痕迹，不要静默永久等待；
- 清理要成对：重试调度、高亮移除定时器都要在「下一次跳转前」与「组件卸载时」清理；换组时要清空悬置意图，否则用户手动回到该组会触发一次无搜索上下文的「幽灵跳转」。
- **测试必须覆盖异步路径**：用冷缓存 + 故意延迟 N 帧回包的桩，断言最终落到锚点并带高亮类。同步路径的用例会给假信心。

## 经验 2：让导航在搜索态常显后，所有「会切组」的入口都必须同时收起搜索

搜索态内容区渲染的是结果列表，被切到的组组件**并未挂载**。因此任何「只切组、不收搜索」的入口都会变成死点击。本次踩了两次：

1. 点组**名称**（已修：选中即收起搜索）；
2. 点组行的**「恢复该组默认」图标**——它不只是死点击，还会置下「待处理」信号，而该信号由目标组组件挂载时消费，于是组级确认框被**推迟到用户日后回到该组时才弹出**（一个延迟爆发的 bug）。

**结论**：把导航设为常显时，逐一梳理导航上**所有会改变 `activeGroup` 的交互**（选择、重置、预热、快捷键），确保它们都统一走「先收起搜索」的入口函数，而不是各自 `setActiveGroup`。

## 经验 3：模态对话框的焦点契约要主动做，`aria-modal` 本身不做事

聚合确认框起初声明了 `role="dialog" aria-modal="true"` 却完全不管理焦点：portal 渲染在 `body` 末尾，键盘用户无法到达确认键（确认键还要等存储计划算完才出现），背后控件仍可聚焦，且可与组级确认框形成双 `aria-modal` 叠加。

**结论**：本仓 `ConfirmDialog` / `StorageMigrateDialog` 已有做法——开框聚焦对话框内元素、主操作可用时聚焦它、不可用时退到取消，关闭时不把焦点留在已分离的 portal 节点。新对话框直接沿用，不要重新发明。另注意 jsdom 不实现浏览器的焦点修正规则，`document.activeElement` 断言只能证明「焦点被移入」，不能证明真实浏览器的模态契约——后者需在 WebView2/Chromium 实测。

## 经验 4：「立即迁移并重启」的按钮，文案与动作必须同时迁移

聚合框复用了存储组对话框的既有键 `storageMigrateNow`（「立即迁移并重启」），但只照搬了**提示文案**（`storageRestartRequired`），没有照搬**重启动作**（`window.digitalLife.storage.restartApp()`）。结果同名按钮在组级会真的重启、在聚合流程只提示用户手动重启。

**结论**：复用既有交互文案时，必须同步核对**该文案承诺的动作**是否也被复用。设计文档若把要求写成「沿用现有重启提示文案」，它会把「动作 + 文案」降级成「仅文案」——写要求时就该写明动作。这类「两条相邻流程的语义分叉」逐任务审查看不到，只有跨任务/全分支审查能发现。

## 经验 5：判别联合别塌缩成一个 `null`

存储计划计算有四种结局：无桥、状态不可读、预检 IPC 失败、**四块本来就全默认**。最初都返回 `null`，UI 一律渲染「存储不可用，已跳过」——于是「存储本是出厂默认」这一**常见**路径被错误地描述为不可用。

**结论**：UI 需要对不同结局说不同话时，底层就该返回判别联合（`ready` / `allDefault` / `unavailable`），不要用一个 `null` 承载语义不同的多种原因。

## 经验 6：单错误契约会静默丢掉多错误场景的一条提示

下载路径恢复由「路径步 + 开关步」两段组成，两者**都执行**（开关复位与路径解耦）。原实现各自失败各发一条 toast；提取为共享纯序列后只返回**首个**失败，双失败场景因此少一条提示。

这是可接受的收敛（触发面是两条独立桥同时失败，幸存文案未变），但要点是：**提取时先枚举「多错误并存」的组合，判断单错误契约能否表达**。若不能且场景重要，就让返回值带出关键子步骤的独立结果（本次为此给执行结果加了 `downloadFailure`，使下载族文案与 `failedStatus` 解耦）。
