# Root Cause to Close（根因排查 → 收尾归档全生命周期）

> **一句话：** 先证明根因，再改代码；改完用日志/测试证明有效；收尾走 R1/R2 审查、文档同步、清理。
>
> **真相优先级：** 当前代码 / 命令输出 > 进度文件 > 本技能 > 记忆。
>
> **文档基准：** 本技能所有 `docs/...` 以仓库根（`adlo/` 的父目录）为基准；禁止在 `adlo/docs/` 另建目录。命令基准：`git` 在仓库根；`pnpm` / `cargo` 在 `adlo/` 下执行（`pnpm --dir frontend ...` 即 `adlo/frontend`）。
>
> **工具称谓：** 本文用「读取 / 搜索 / 运行 / 子代理 / 询问卡片（grilling 轮次）」指代能力，不绑定具体 harness；执行时按当前环境选用对应工具。「读取」可看 `.gitignore` 内日志，「搜索」不能。

## 0. 章节路由

| 我在做什么                                         | 去            |
| -------------------------------------------------- | ------------- |
| 判断该不该用本技能、是需求还是问题                 | §1 范围与原则 |
| 建进度文件、grilling 提问、处理脱敏/日志/埋点/测试 | §2 通用协议   |
| 还没定位根因                                       | P0            |
| 根因已确认 / 未确认                                | P1            |
| 写失败测试、改代码、加验证日志                     | P2            |
| 触发验证、读日志、决定是否通过                     | P3            |
| 用户已批准收尾，开始审查                           | P4            |
| 同步规则 / 技能 / 术语 / 文档                      | P5            |
| 清理临时产物、提交、总结                           | P6            |

## 1. 范围与原则

### 1.1 适用范围

| 类型               | 特征                                            | 走法                                                       |
| ------------------ | ----------------------------------------------- | ---------------------------------------------------------- |
| 解决 / 优化 / 调整 | Bug、测试失败、回归、偶发、性能、结构或行为修正 | 本技能 P0–P6                                               |
| 收尾               | 本轮开发完成、准备结束会话                      | 从 P4 进；P0–P3 已有结论则复用，不重做                     |
| 需求相关           | 新功能、新组件、行为变更                        | 先记进度文件，再走 `brainstorming`；本技能负责其后的 P4–P6 |
| 混合               | 需求 + 附带问题                                 | 同一进度文件记录两部分；审查与文档同步覆盖两类             |
| 不确定             | 无法判定                                        | 按 §2.2 的 grilling 轮次问用户，禁止直接开工               |

**单一主线：** 同一会话只走一条主线、只建一套进度文件，不并行启动与本技能重叠的根因/收尾流程。不要在每次编辑后触发收尾；编辑后只做分级测试（§2.6）。

### 1.2 铁律与核心原则

1. **未完成根因调查前，禁止提出或实施修复。**
2. 先确认意图，再调查；先找到根因，再修复。
3. 进度文件是唯一真实来源，禁止依赖记忆。
4. 只跑受影响的测试；全量测试仅在变更面广或收尾兜底时、经用户同意后跑。
5. 审查发现默认都要修，修前先验证真实性。
6. **P3 通过后必须停下等用户批准才能进 P4**（自动化通过 ≠ 用户批准；用户明示免测并授权视为批准）。批准后 P4 → P5 → P6 直通，阶段内该问的仍要问。
7. **决策先正文、后 grilling 轮次 / 卡片：** 完整分析 / 报告放正文；卡片只放本轮 frontier 的 2–4 个短选项（§2.2）。

### 1.3 预检（进入 P0 前）

1. **分类** — 按 §1.1 判定类型；不确定先问。
2. **探索（只读，不修复）** — 优先 `codegraph-knowledge-graph` 查符号 / 调用链；读相关文件、配置、`git log --oneline -20`。
3. **复述并等待确认** — 向用户确认三句话：问题 / 任务是什么、涉及哪片代码、计划按什么方向排查；用户确认前禁止进 P0（需求类型先记进度再进 brainstorming 例外）。混合 / 需求任务：brainstorming 的 space 与实施计划要同时覆盖附带的问题类事项。

**Exit criteria：** 类型已定、代码区域已定位、用户已同意方向、引用用户产物（日志 / 抓包 / 截图）的脱敏已完成、进度文件已建好并列出全部事项（解决 / 优化 / 调整类型同样必须在进入 P0 前建好）。

## 2. 通用协议（贯穿全程）

### 2.1 进度文件（唯一真实来源）

- **位置：** `docs/root-cause-to-close/YYYY-MM/progress-YYYY-MM-DD-HHmmss.md`；模板 `docs/root-cause-to-close/_template.md`。
- **状态：** `待处理 → 进行中 → 待用户确认 → 已完成`。自动化 / 日志通过只到 `待用户确认`；`已完成` 只在用户确认已解决后标记。
- **时机：** 开工前列出全部事项（含中途新增）；进入 P0 置 `进行中`；每阶段 / Step 完成**立即**写结论、证据、决策理由、下一步；上下文压缩前确认已落盘；P6 前通读确认状态。用户提新任务立即追加 `待处理` 并告知；重排优先级则旧事项备注「已暂停 — 重排至 [新事项]」。
- **只留一份当前状态：** 每轮用 `check:changed` / Vitest 输出校对数字，原地替换旧文案；旧轮结论压成一行（状态 + 最新计数 + 验证出处）。禁止同轮并存互相矛盾的版本，禁止新增小节而不替换旧版本。
- **数字：** 测试数、行数、轮次、条数必须来自命令输出或重新计数。循环期引用失败数时同时写当时用例总数（如 `4 failed | 23 passed`（当时 27 条））。证据数字只在最终门禁跑完后粘贴一次，禁止先填预期值再改。提交数写 `git log --oneline <base>..HEAD`，不写总数。
- **子代理报告：** 完整报告落盘：R1 用 `.review-diffs/<scope>-r1-rev<N>-report.md`，R2 用 `<scope>-r2-rev<N>-report.md`（`check-review-gate.mjs` 只读 R1 前缀）。报告需自包含输入（快照路径、任务描述）、输出（逐项结论、severity、建议修复）、依据。返回消息只给路径 + ≤5 行摘要 + `需修复项：N`。主代理收到后：正文转写关键信息 + 正文索引报告路径（缺一不可）。

### 2.2 用户提问与确认（正文先输出，问题走 grilling 轮次）

**铁律：** 任何需要用户拍板 / 知晓的提示，都先用正文完整输出分析或报告，再按 `grilling` 的轮次格式提问；卡片只承载本轮决策，不承载分析。只弹卡片、正文没有实质内容 = 违规。纯状态汇报可不提问；一旦需要用户回应，就按 grilling 轮次提问。

**grilling 轮次（所有决策 / 多方案 / 调研 / 门控 / 进度关卡都用）：**

1. **建设计树** — 把待定事项拆成决策树；只把「前置已定」的决策放进本轮 frontier（frontier = 现在就能问、不必猜未答答案的问题）。
2. **一轮问完 frontier** — 每个问题编号，写成「是 / 否即接受推荐」的形式，并给出 `➡️` 推荐答案；不要一轮只问一个互不依赖的问题。
3. **等回答再重算** — 用户回答后，已定决策推出新 frontier；把已定决策（含理由）写入进度文件，依赖本轮未定答案的问题放到下一轮，不提前问。用户两个方案都不接受 → 视为新决策树，回第 1 步重开一轮，不自行折中。
4. **事实自己查** — 文件、代码、命令、日志、外部资料用读取 / 搜索 / 子代理查，不把可查的事实变成问题；只把决策交给用户。
5. **共识前不动手** — 用户确认达成共识（或明确批准）前，不实施有副作用的改动。

**正文（先发）：**

- **决策 / 多方案 / 调研：** 对比总表 → 逐套专业讲述 + 一句话类比 + 优点 / 缺点 / 注意事项（不美化、不省略）+ 来源链接 + 推荐项；调研类另附来源原文要点与适配结论（技术栈、双端一致、治理约束、许可维护、复杂度）。
- **报告 / 门控 / 升级：** 逐条写全结果、证据、每轮尝试与结论，不压缩成选项文案。

**卡片（后发）：** 只放本轮 frontier 的短决策（2–4 个选项）。单个问题有明确选项时直接列该问题的选项（如 A / B / 先讨论）；多个问题且卡片工具支持多问时逐题收集，否则用「全部按推荐 / 部分调整（正文回复）/ 先讨论」三项。先单独发完整正文消息，确认发出后再发卡片工具调用；纯工具轮次（无正文、只弹卡片）视为违规。

**轮次格式：**

```text
❓ **Q1** - **<问题标题>**：<问题正文，可含多个选项>

➡️ <推荐答案>

---

❓ **Q2** - **<问题标题>**：<问题正文>

➡️ <推荐答案>
```

> 编号在本轮内有效；跨轮引用写「上一轮 Q1」或「R2-Q1」，避免多轮后编号重复造成歧义。

### 2.3 脱敏红线

- 密钥 / token / 凭据一律写 `<REDACTED>`；凭据走环境变量，不进正文与进度文件。禁止以「对照 / 举例」为由复述原文；只写「已将 <字段名> 替换为 `<REDACTED>`」。
- 抓取产物（HAR、日志转储、core dump、截图录像）只引用承载信号的行，先确认无敏感信息，不贴全文。
- 脱敏后仍不足以诊断时，向用户索取：(a) 可复现环境访问权限；(b) 脱敏产物；(c) 临时生产埋点许可。禁止带着信息缺口猜进 P0。

### 2.4 日志协议

`.adl-logs/` 等被 `.gitignore` 排除，**只能用读取（绝对路径），禁用搜索**。逐项检查，缺项跳过；`multi` 会话文件按 `LastWriteTime` 取最新；同名覆盖文件直接读；大文件先读尾部 80 行，命中 ERROR 再全文。

| 检查项              | 路径                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------- |
| 桌面壳 + 浏览器前端 | `<仓库根>/.adl-logs/terminal-logs*.txt`、`debug-logs*.txt`、`debug-logs-browser*.txt` |
| 后端引擎            | `<仓库根>/adlo/.adl-logs/adl-server-logs*.txt`                                        |
| 本地运行 / 诊断     | `<仓库根>/adlo/.run-logs/`、`/diagnostic-logs/`                                       |
| 发布态              | `<数据根>/logs/`（无 `.adl-logs`）                                                    |

**判读：** ERROR（崩溃堆栈 / IPC 失败等功能错误）必须修或记录；WARN 评估；INFO / DEBUG 忽略。**完成条件：无未解 ERROR。**

### 2.5 调试埋点触发（加完必须触发一次）

加了日志 / 埋点必须产生一次日志再下结论；「加完即认为生效」不算验证。

1. **按手册启动：** 读 `docs/development/log-system-manual.md` §1，用 CLI 加日志：桌面 `pnpm dev:tauri -- --log-level trace --terminal-log-mode multi`；浏览器 `pnpm dev:preview -- ...`；双端 `pnpm dev:both -- ...`。`--` 不可省；设过 `RUST_LOG` 先 unset（硬顶）。启动后先断言 `[ADL-LOG]` / `[ADL-CLI]` 行（session-only，重启即失效）。
2. **触发（二选一）：**
   - A. 有自动化能力（优先环境内置 browser 工具，否则 `playwright-cli`；见 `references/playwright-cli-experience.md`）→ 自己驱动，复现后读最新日志断言。
   - B. 无能力 → 用户当「手」：给编号步骤（启动模式 → 打开地址 / 窗口 → 点击 → 看什么）并声明预期日志文件与标记；等用户回复「操作完成」后再读日志。
3. **记录：** 进度文件记「本次用 A / B 触发」。

**「UI 动了」≠「日志写了」：两者都要断言。**

### 2.6 测试协议（分级执行）

- **定位范围：** `git diff --name-only` → Rust 按 crate（`cargo test -p <crate>`）、前端按 `__tests__/` 相关文件（`vitest run <file>`）；保持 clippy / tsc 通过（`cargo check` 不单跑，clippy 已覆盖编译）。
- **默认只跑受影响部分：** 修复后、每轮审查后、收尾均同。全量（`cargo test --workspace` / 前端全量 `test`）仅在变更面广或分级已通过需兜底时、经用户同意后跑；前后端两组同一消息并行，禁串行。
- **先单后全：** 迭代期先跑受影响单文件；全量门禁只在落盘与收尾前各跑一次。
- **已提交后只改文档：** 在 `adlo/` 下运行 `pnpm --dir frontend run check:changed -- --base HEAD --skip-tests`（只跑静态项）；需要含测试时去掉 `--skip-tests`。不带 `--base` 会把整条分支的用例再跑一遍。
- **回归用例交付前做删除性推演：** 把修复回退一次，确认用例变红再恢复；进度文件记「回退后：<用例名> 变红」。没有回退证据的用例按未验证处理，不得写成回归保护。
- **工具失败：** 只修工具报告的问题；自动修复引入新变更则重跑类型检查；3 次不通过 → 停并报告等指示。
- **flaky：** 疑似用例连跑 5 次，≤2 败视为 flaky（验收排除并记录），>2 败视为真失败。

## P0：根因调查（修复前必须完成全部适用步骤）

1. **读错误信息** — 完整堆栈、行号、错误码，不跳过警告。
2. **建紧反馈环**（先有环，再谈假设）— 一条能稳定变红的命令，须实际跑过并贴出调用与输出。候选：失败测试 / CLI 复现脚本（固定 fixture + 已知快照）/ `playwright-cli` 驱动 DOM-console-网络 / 回放真实抓包 / 最小 harness / `git bisect run` / 新旧双版本差分 / 用户当手（编号步骤）。
   - **成环四标准（缺一不算）：** 变红能力（断言用户原症状，而非「没崩」）；确定性（次次同判；偶发 bug 先把复现率抬到可调试）；秒级；可无人值守运行。
   - **最小化：** 偶发问题先做维度分离对照（隔离 vs 全量、单 worker vs 并行、有缓存 vs 无缓存、CI vs 本地、固定 seed vs 随机）；再逐个砍输入 / 调用方 / 配置 / 数据 / 步骤，每砍一次重跑，只保留「去掉即变绿」的要素。
   - **无成环命令禁止进 P1**；先按脱敏红线向用户索取复现条件，不要猜。
3. **查近期变更** — `git log --oneline -20`；怀疑某提交则 `git bisect`。
4. **多组件取证** — 能断点 / REPL 先断点（一个断点胜过十行日志）；否则在组件边界埋点记录进出状态，先定位「哪一层坏」。诊断日志带唯一前缀 `[DBG-xxxx]`，P6 单 grep 清零。性能退化不看日志：先建基线测量（计时 harness / profiler / query plan），先测量后修。
5. **数据流追踪** — 从表象向上追到源头，在源头修。前端用 `new Error().stack` + `console.error`；Rust 用 `tracing::error!` / `dbg!`；在危险操作**前**记录。
6. **模式分析** — 找可工作的相似功能，逐项列差异，列出依赖的组件 / 配置 / 环境。
7. **列 3–5 个排序假设再逐个验证**（一次一变量）— 单假设锚定是常见死因。每个假设必须可证伪并记入进度文件：「如果 <X> 是根因，那么 <改 Y> 问题消失 / <改 Z> 加重」。**先把排序表给用户看再动手**（用户不在线则按自己的排序继续，不阻塞）。验证用最小诊断性改动，成立进 P1 / P2A，不成立还原后换下一假设，不叠加改动。
8. **外部调研（触发即做，不得硬试）** — 触发：无方案 / 无候选 / 知识盲区 / 多次失败 / 方案分歧 / 直觉有更好做法。通道并行：最新资料（查询词带年份，读原文）+ 官方文档（版本对齐）+ 社区（区分「提议」与「已落地」）+ 同类产品对标（2–3 个）。复用前过适配：技术栈、运行环境（双端一致？）、治理约束（分层 / i18n / 权限 / 安全）、许可与维护、复杂度。多方案按 §2.2 走 grilling 轮次。

**Exit criteria：** 能说出候选根因及证据链，或已穷尽手段并记录每条路为何走不通（进 P1 路径 B）。

## P1：定径

- **路径 A（根因已确认，需全满足）：** 能解释确切机制；能从触发点追到表象；改根因可修且无副作用 → P2A。
- **路径 B（未确认，需全满足才可判）：** (a) 已穷尽 P0 全部手段（含外部调研）；(b) 属环境 / 第三方无升级路径 / 不可修复外部因素；(c) 已记录调查过程与排除理由。三条全满足 → P2B；任一条不满足 → 回 P0。

## P2：修复

### P2A：直接修复（已知根因）

1. **先建失败测试**（`test-driven-development`；无自动化条件则一次性复现脚本）。但必须有正确接缝：测试须按调用现场的真实触发链路复现 bug；接缝太浅则不建——假信心的回归测试不如不建，记为架构发现（并入 P1 路径 B「不可修复」依据）。回归用例从公共入口进入；禁止把私有方法 / 内部字段的唯一断言当回归保护（删掉修复必须变红）。
2. **在源头一次只改一处**，不顺手改进。
3. **搜同类根因模式**并一并处理。
4. **加验证日志**（进出、转换前后值、错误路径、依赖假设），加完必须触发一次（见 §2.5）。临时日志用 `[DBG-xxxx]`；`check:changed` 的 source-hygiene 会拦截未豁免的 debug-tag——诊断期在该行尾加 `hygiene-allow`，P6 仍按前缀清零；或改用 `debugLogCollector` 收集的普通 `console` 输出。
5. 记进度文件 → P3。

**Exit criteria：** 失败测试已建（或已按接缝规则记为架构发现）**且**源头单点改动完成 **且**同类根因已扫 **且**验证日志已加并触发。

**失败迭代：** 第 1–2 次回 P0 或补外部调研；第 3 次起**停止**并质疑架构（每次修爆新位置 / 需大规模重构 / 修一处坏一处 → 与用户讨论，配合外部调研做架构评估）。

### P2B：预防性措施（无根因）

按六维评估候选（覆盖范围 / 复杂度 / 副作用 / 可维护性 / 误判风险 / 可逆性）→ 按 §2.2 走 grilling 轮次 → 实施并记录 → P3。

## P3：验证

1. **补日志**（P2A 已加则跳过）：格式 `[时间戳] [级别] [组件::函数] 消息 — 键=值`；DEBUG 路径追踪 / INFO 状态转换 / WARN 预期异常 / ERROR 意外失败。
2. **触发验证：** 有自动化能力则自己驱动（§2.5）；否则用户当「手」（编号步骤，等「操作完成」再读日志）；**不预告成功**；记进度文件。
   - **后端接口**（不起桌面壳）：`pnpm --dir adlo run serve:server`——先构建 `adl-server`，再以临时数据目录启动，打印 URL 与 `proxyEffective`；不要手跑旧二进制。
   - **UI / 主题：** 在真实浏览器 / WebView 读 `getComputedStyle`（亮暗两套都读），把 color / background / 关键变量写入进度文件。CSS 文本断言、截图、肉眼判断都不能替代 computed style。
   - **进程 / 环境：** 用真实子进程或终端验证最终二进制 / 最终快照；纯函数单测不能替代。
   - **桌面专属分支**（`isTauriShell` / WebView2 / 原生对话框 / 仅桌面可见）：二选一并在进度文件记录：① `pnpm run e2e`（或 `e2e:build` + 单 spec）；② 编号用户手动步骤并以用户回复为准。浏览器 + mock 单测不能证明桌面端行为。
3. **日志分析**（只取最新）：预期条目在 → 生效；错误条目 → 边界缺口；条目缺失 → 路径未触发；意外模式 → 假设错。
4. **分流：**
   - 通过（日志 + 触发方双确认）→ 状态置 `待用户确认`（不要直接 `已完成`），停下走 P3→P4 门控。
   - 部分有效 → 回 P2 补缺口并记录。
   - 无效 / 回归 → 记录后按 方案 → 代码 → 方法 → 架构 逐层排查。
   - 用户说没解决 → 记「用户报告无效」进失败迭代（最多 3 轮，第 4 轮禁止，直接升级报告）。
   - 用户报视觉差异但自动化无法复现 → 先索要截图 / 录屏 + 精确步骤（注明浏览器预览还是 Tauri 桌面），确认前不改设计数值试探；「未复现」与「已修复」分开记录。

### P3→P4 门控（禁止自行进入 P4）

P3 自动化通过后必须停下，按 §2.2 用 grilling 轮次报告验证结果并提问，等用户亲自测试（用户可明示免测并授权，视为批准）。获准后**必须在进度文件写入**：`- P3→P4 用户批准：是（YYYY-MM-DD）`；用户明确授权直接收尾时写 `不需要（用户已明确授权直接收尾）`。没有该标记，`review-snapshot.mjs --rev 1` 与 `check-review-gate.mjs --phase r1` 会拒绝。

**两种确认分开记录：**

- **(a) 确认已解决：** 用户说「解决了 / 搞定了」→ 标记 `已完成` + 时间戳。
- **(b) 批准进入收尾：** 用户明确同意（「可以进收尾 / 进 P4 / 批准 / 可以」）→ 可进 P4。
- 同一句可同时满足两者；只得到 (a) 时仍须等明确批准。模糊词（「好了」「应该行」）二次确认一次，且二次确认后仍需用户给出明确的 (b) 批准句（「可以进收尾 / 进 P4 / 批准 / 可以」）；第二次「好了」不算批准。取得 (a) / (b) 后读进度文件做进度关卡：有未完成事项逐项问用户（正文逐项写，可与批准合并为同一轮 grilling）。

## P4：审查引擎

> **范围边界：** P4 只修**代码与代码内注释**。`GLOSSARY.md`、`docs/adr/`、`docs/design-system/`、`docs/operations/ui-manual/`、`docs/root-cause-to-close/**`、`docs/superpowers/specs/**` 的修订留到 P5。P4 发现这些文档过期时，**当场写进进度文件的 P5 待办台账**（文件:行 + 修法 + 来源 F#），不把文档改动送进下一轮快照。台账只存在于对话 / 记忆时，复审无法判定已记录。

### 4a. 前置检查

- **P3→P4 批准门控（机械）：** `node adlo/scripts/check-review-gate.mjs --phase r1 --progress docs/root-cause-to-close/YYYY-MM/progress-*.md`。缺标记则退出 1，禁止生成 rev1 快照（`review-snapshot.mjs --rev 1` 也会复核）。
- `git branch --show-current`、`git status --short`；未跟踪文件判定是否为本次产物。
- 定点预检（源自 `code-review`）：`git rev-parse <定点>` 可解、diff 非空才派发；坏 ref / 空 diff 在此失败。
- 磁盘（可选）：`pwsh -NoProfile -File adlo/.cargo/clean-target.ps1 -WhatIf` 干跑后问用户；`target/debug` 超 30 GB 才全量 `cargo clean`（永久删除）。

### 4b. 采集变更 + 快照

| 类型             | 命令                                                                                |
| ---------------- | ----------------------------------------------------------------------------------- |
| 未提交（含暂存） | `git diff HEAD`                                                                     |
| 已提交未推送     | `$BASE = git merge-base origin/HEAD HEAD`；`git diff "$BASE..HEAD"`（无远端则跳过） |

**用 merge-base，不用 `origin/HEAD`**：分支落后时后者会把别人已合入 main 的改动算进本次审查。两类都无变更 → 跳过 4c–4e（进度文件记理由），只保留分级测试。

1. `.review-diffs/` 已在 `.gitignore`，P6 删除。**先完成 4c 门禁再生成快照**（格式 / 类型失败发生在快照后会整轮返工）。
2. **一键快照：** `node adlo/scripts/review-snapshot.mjs --rev <N>`。脚本：解析 base（`merge-base(origin/HEAD, HEAD)`，无远端回退 `HEAD`）→ `git add -N` 未跟踪文件 → 每文件写 `<safe>-rev<N>.diff` → 写 `changed-files-rev<N>.txt` / `commits-rev<N>.txt` / `manifest-rev<N>.md`；空 diff 直接失败。文件数明显多于预期时先核对 base 是否等于本分支分叉点。
   - 手工等价物：`git diff --output=<safe>-rev<N>.diff HEAD -- <file>`——**`--output` 必须在 `--` 之前**（否则被当成 pathspec）。
   - **编码安全：** 禁止把 `git diff` 经 PowerShell 管道 / `Out-File` 转存（会把 UTF-8 中文转成 GBK 乱码）。
   - **未跟踪文件：** 脚本已 `git add -N`；手工执行必须先做，否则快照漏审。
   - **临时文件守卫：** 未跟踪的纯数字名 / `.tmp/.log/.out/.bak` 会被拒绝；临时脚本 / 输出放 `$env:TEMP` 或 `.review-diffs/tmp/`；确需纳入用 `--allow-untracked`。
   - **绝对断言门控：** 新增注释含「必然 / 永远 / always / never…」会生成 `claims-rev<N>.md` + `claims-ack-rev<N>.md`；未逐条标 `[x]` 并写证据 / 降级措辞时脚本非零退出。不要用 `--allow-claims` 跳过核对。
3. 子代理只读快照，禁止终端 `git diff`；每轮修复后 rev 递增**全量重生成**，复审看最新完整 diff（禁只看增量 / 复用旧快照）。派发时给 `manifest-rev<N>.md` 路径。

**派发前自检（判断项）：**

1. 每个新增 / 修改用例的标题逐词核对断言；标题承诺的行为至少有一个会失败的断言。
2. 接线 / 委托类修复有用例覆盖调用点，不只测纯函数。
3. 新增注释只描述代码能证明的事实，不把意图写成事实。
4. 用户可见文案承诺的行为已在本轮双端落地。

### 4c. 两轮循环审查（顺序门控，两轮都不可跳过）

**生成快照前门禁：** 中间修复轮跑 `check:changed -- --skip-tests`（lint / format / typecheck）；**最终快照**跑完整 `check:changed`（含受影响测试）与 `check:rust:changed`。门禁失败先修，再生成快照，不把门禁可发现的问题交给审查子代理。

```powershell
# 在 adlo/ 下执行
pnpm --dir frontend run check:changed -- --skip-tests   # 中间轮：静态项
pnpm --dir frontend run check:changed                   # 最终快照：含测试
pnpm run check:rust:changed                             # 最终快照：Rust 受影响 crate
```

中间轮禁止跑完整测试门禁（实测单次数分钟，连续多轮会白烧；见 `references/review-brief.md`）。最终快照必须跑一次完整门禁。

**门控铁律：**

1. 两轮都必须跑（有变更时；无变更按 4b 跳过并记理由），每轮至少一次完整子代理派发。禁止以「自判干净」「改动小」「上一轮已删日志」等理由跳过 R1 / R2 或任一次复审。**自判 ≠ 审查通过**，只有子代理返回「零问题」才算通过。
2. **顺序门控：** R2 禁止与 R1 并行或提前启动。R1 循环达到「本轮零问题」并记入进度文件后，才允许进 R2；R2 达到「本轮零问题」才允许退出 P4。**派发 R2 前必须跑** `node adlo/scripts/check-review-gate.mjs --phase r2`；**进入 P5 前必须跑** `--phase exit`（R1 / R2 最新报告都须「需修复项：0」且 R2 至少一份）。门控非零即禁止继续。
3. **每轮都是循环：** `审查（本轮范围）→ 4d 验证 → 4e 修复 → rev 递增全量重生成快照 → 同范围复审`，直到本轮零问题。禁止「每轮只审一次就放行」。

**本轮零问题：** 最新一次子代理审查经 4d 逐项验证后无「需修复」残留（误报 / 有据保留已记理由，且下一轮复审无异议）。「需修复」= critical / high / medium，或会改变行为 / 事实的 low（错误注释、失效引用、错误文案）；纯风格、可选优化、已记录理由的保留项不算。**进度文件 / 设计文档的事实漂移属 P5，写入 P5 台账即视为关闭，不阻塞零问题；代码注释 / i18n 的 low 仍按需修复计。** low 可一次批量修完，只复审一次。

- **R1 循环（正确性，不通过不进 R2）：** 按事项数派发（1–5 个事项逐项各派 1 个；>5 个时 diff <50 行的小事项可合并、大事项仍逐项），同一消息并行派发。**可写子代理只允许写指定报告文件，源码只读；只有只读代理时，要求它把完整报告放进返回消息、由主代理落盘。** 每个提示词只给：`references/review-brief.md` 路径 + 本轮 manifest + 文件范围 + 要验证的上轮项 + 报告路径；规约、气味基线、强制检查项、报告契约都在简报里，不逐条粘贴。覆盖：根因与正确性、设计质量、副作用与安全、预存问题、优化机会。修完 rev 递增后仍用 R1 范围复审；**同一轮次最多 3 次完整派发，第 4 次停止并升级给用户（附每轮未闭合项）；定向复核不计入上限**。
- **派发范围互斥：** 同一文件只归一个 scope；共享文件（`App.tsx`、`BrowserPanel.tsx`、`shared/ipc/` 等）由主代理指定归属，其他 scope 只读上下文、不产出 finding；合并时仍去重。
- **R2 循环（清理，仅 R1 零问题后进入）：** 同样读 `references/review-brief.md`。即使 R1 已删日志 / 死代码，仍必须完整派发一次。覆盖：死代码、冗余守卫、根因修后多余的防御、应删 / 降级的诊断日志。不标：正当错误处理、系统边界验证、生产 warn / error 日志。修完 rev 递增后仍用 R2 范围复审，循环至零问题。
- **合并：** 去重（同文件同行同类留最详者）→ severity 降序。

### 4d. 主代理问题验证（修复前置，逐项必做并记进度文件）

默认都要修，仅下表情形可不修（仍须先验证：重读代码、核对调用链、排除误报与过期快照）：

| 情形                                                                       | 处理                                                         |
| -------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 误报 / 过期快照假阳性                                                      | 不修，记理由                                                 |
| 用户特殊设计 / 正当防御 / 合理兼容（有注释 / 文档 / 提交佐证）             | 仍须检查优化空间；确认无改进才保留并记理由；无法确认则问用户 |
| 无用防御（根因修后多余、重复守卫）/ 不合理·偷懒兼容 / 非本次引入但在范围内 | 修（含预存与低级别问题）                                     |

「不修」理由写入进度文件，并在下一轮派发时粘进子代理提示词（子代理看不到其它上下文）；其可异议，成立则重估，循环至一致。

### 4e. 修复循环与升级

- 需走 grilling 轮次的情形（满足任一）：动核心架构 / 大重构 / 破兼容、业务决策无法自判、多套可行方案、新依赖或安全策略变更、无法判定是否用户特殊设计。**正文先给完整方案分析（逐套优缺点风险 + 推荐项），卡片只放本轮 frontier 的 2–4 个短选项。** 若已定方案推翻 / 改变 ADR 或术语，记入 P5 待办台账（P4 不改文档）。
- 约束：只修验证通过的问题；守 `.agents/rules/` 与双端一致、i18n、无硬编码文本等治理；不带无关变更。
- 每轮修完必须 rev 递增全量重生成快照，并重跑同范围审查；同一问题 3 轮未解 → 停并报告等指示。

**Exit criteria：** 已批准收尾（P3→P4 门控通过，或从 P4 直进的已授权）**且** R1 零问题 **且** R2 零问题（先后达标，有进度文件记录；无变更跳过须记理由）**且**分级测试通过。任一轮未跑、未循环至零问题，都不算 P4 完成。

**最终状态证据：** 最后一次端到端 / 视觉验证之后又改了代码，必须在最终快照上重跑对应验证（浏览器 `getComputedStyle` / 真实二进制 / PTY），并在进度文件记录命令与时间；否则不算 P4 完成。

## P6：清理 + 总结

**顺序铁律：** 最后一次分级测试 / 全量门禁通过后，再清理与总结提交；门禁返工产生新增改动时，先重建快照并重跑同范围审查，不得带着未验证的改动进清理（清理删除快照后无法复审）。

### 6.1 清理（预授权，无需再问；先用读取确认存在，年龄按 `LastWriteTime`）

- [ ] 两处 `.adl-logs/`（仓库根与 `adlo/`）超 7 天文件。
- [ ] `debug-logs*.txt`、`debug-logs-browser*.txt`、`adl-server-logs*.txt` 运行残留。
- [ ] 根 `test-artifacts/` 超 3 天临时文件。

- `git status` 确认只含本轮改动；按 `type(scope): summary` 提交（scope：`core/frontend/rust/stores/browser/terminal/ipc/docs/deps`）。

### 6.3 总结（只读进度文件生成，禁凭记忆）

1. 总表每个单元格只写**一行短结论**（状态图标 + ≤20 字），禁止换行、`|`、括号长说明。
2. 轮次、数量、hash、理由等细节放表下条目，一行一条。
3. 子代理转写与索引另起段落，不进表。

## Quick Reference

| 阶段                                | 关键动作                                                                                                            | 完成条件                                  |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| 预检                                | 分类 → 探索（codegraph 优先）→ 复述确认                                                                             | 用户同意方向                              |
| 记录                                | 建 `docs/root-cause-to-close/YYYY-MM/progress-*.md`，每阶段即记                                                     | 唯一来源最新                              |
| P0                                  | 读错 → 紧反馈环（四标准）→ 最小化 → 查变更 → 取证（断点优先 / 日志带 tag）→ 追流 → 比模式 → 3–5 排序假设 → 外部调研 | 成环命令 + 根因证据链或穷尽记录           |
| P1                                  | 全条件判定 A（修根因）/ B（预防）                                                                                   | 路径明确                                  |
| P2                                  | 失败测试 → 单点修 → 查同类 → 加日志；失败 3 次停                                                                    | 改在源头                                  |
| P3                                  | 补日志 → 触发验证（自动优先 / 用户为手）→ 最新日志分析 → 分流；3 轮上限；通过置 `待用户确认`，停下等批准            | 双确认 + 用户明确批准                     |

## 相关技能与规则

- `brainstorming` — 需求类型的设计（space 与计划覆盖附带问题类事项）
- `grilling` — 用户提问与决策轮次（设计树 / frontier / 推荐答案）；§2.2 的提问格式依据
- `codegraph-knowledge-graph` — 预检 / P0 的代码探索
- `test-driven-development` — P2A 失败测试
- `systematic-debugging` — P0 调查方法论补充；本技能负责端到端编排
- `diagnosing-bugs` — 紧反馈环 / 排序假设 / 埋点优先级（本技能脱敏红线与 P0 步骤 2/4/7、P2A 接缝的依据）
- `code-review` — 双轴审查与定点 / 规约 / 气味基线（P4 前置预检与 R1 的依据）
- `verification-before-completion` — 宣告成功前验证
- `run-project-surfaces` — 按手册启动 Tauri / 浏览器 / 双端（启动器，不代操作）
- `playwright-cli` — 浏览器模式自动化触发；经验见 `references/playwright-cli-experience.md`
- 规则 `mandatory-testing`（`.agents/rules/mandatory-testing.md`）— 每次变更的验收流程；与本技能测试协议互补（前者轻量、后者收尾兜底）
- 外部可选（引入前先与用户确认）：Playwright MCP、WebdriverIO `@wdio/tauri-service`
