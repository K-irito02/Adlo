# Root Cause to Close（根因排查 → 收尾归档全生命周期）

## Overview

本技能是**单一全生命周期流程**：意图确认 → 根因调查 → 修复 → 验证 → 审查 → 文档同步 → 清理总结（测试协议贯穿全程，质量结论汇总于 P6）。

> **铁律：未完成根因调查前，禁止提出或实施修复。**

**核心原则：**

1. 先确认意图，再调查；先找到根因，再修复。
2. 进度文件是唯一真实来源，禁止依赖记忆。
3. 所有阶段只跑受影响的测试；收尾按需加全量。
4. 审查发现默认都要修，修前必须先验证真实性。
5. 阶段门控：P3 完成后禁止自行进入 P4，必须停下用「询问卡片」等用户亲自测试并明确批准（自动化验证通过 ≠ 用户批准；用户明示免测并直接授权亦视为批准，见 P3→P4）；用户批准后，P4 → P5 → P6 一气直通，阶段之间不再请示（阶段内部的强制请示如 4e、多方案决策、全量测试、磁盘清理等仍按各自规则触发）。
6. 决策输出：凡需用户拍板（多方案 / 外部调研结论 / 4e 修复方案等），**完整分析必须作为常规回复正文先输出，用户看过正文后再弹「询问卡片」**；卡片只承载决策本身与简短选项（见「问答卡片输出协议」）。

**生命周期：** 预检 → P0 调查 → P1 定径 → P2 修复 → P3 验证 → P4 审查 → P5 文档同步 → P6 清理总结。

> **文档路径基准：** 本技能所有 `docs/...` 以**仓库根目录**（含根 `AGENTS.md` 与 `docs/` 的治理根，即 `ai-digital-life/` 的父目录）为基准。禁止在 `ai-digital-life/docs/` 下另建目录。

## When to Use / When NOT to Use

- Bug、测试失败、意外行为、性能退化 → 走全流程。
- 本轮开发工作完成、准备结束会话 → 从 P4 进入（P0–P3 已有结论则复用，不重做；此即用户已授权收尾，不再补 P3→P4 批准）。
- 用户明确要求收尾 → 同上。
- 不要在每次代码编辑后触发收尾部分；编辑后只做分级测试（见「测试协议」）。

**单一主线（避免重复触发）：** 同一会话只走一条主线、只建一套进度文件（见「记录协议」），不并行启动与本技能功能重叠的其它根因/收尾流程。

## 工具称谓约定（环境无关）

本文档**不绑定任何具体编程产品 / 客户端 / harness**，统一使用下列能力称谓指代工具。**实际执行时，由 agent 依据自身所在环境可用的工具集，自行判断并选取对应工具**；本文档不罗列、也不比较各客户端 / harness 的工具差异。

| 能力称谓 | 覆盖动作 | 关键约束 |
|---------|---------|---------|
| **读取** | 读文件、列目录（用绝对路径） | 查看被 `.gitignore` 排除的日志等，只能用读取，**禁用搜索** |
| **搜索** | 按内容 / 按文件名路径检索 | 多数搜索工具遵循 `.gitignore`，故搜不到被忽略的日志；不得用于 `.adl-logs/`、`diagnostic-logs/` 等 |
| **运行** | 执行 shell 命令（git / cargo / pnpm / PowerShell 等） | 子代理审查时禁止其自行运行 `git diff`，只能读快照 |
| **子代理** | 派发子任务并回收其报告 | 完整报告必须落盘为独立文件；返回消息只给路径 + 摘要 |
| **询问卡片** | 向用户弹出选项卡片请求决策 / 批准 | 只放一句问题 + 2–4 个短选项；完整内容一律走正文（见「问答卡片输出协议」） |

> 下文凡写「询问卡片」，一律指"向用户弹出询问 / 选项卡片"这一动作；「运行」指各端 shell 执行工具；「读取」「搜索」「子代理」同理。

## 预检：分类 → 探索 → 确认（进入 P0 前必须完成）

### 1. 内容分类

| 类型 | 特征 | 处理 |
|------|------|------|
| 需求相关 | 新功能、新组件、行为变更（"做新东西"） | 先记进度文件（见「记录协议」），再调 `brainstorming`；其 space 与实施计划阶段必须同时覆盖附带的解决/优化/调整问题 |
| 解决/优化/调整 | Bug、性能、结构、行为修正（"改已有东西"） | 走本技能 P0–P6 |
| 混合 | 两者都有 | 同一进度文件记录两部分，审查与文档同步均覆盖两类 |
| 不确定 | 无法判定 | 用「询问卡片」问用户是"新需求"还是"解决问题"，禁止直接开工 |

### 2. 探索相关代码（只读，不修复）

- 优先用 `codegraph-knowledge-graph` 查符号与调用链，替代逐文件爬取。
- 阅读相关文件、配置、近期变更（`git log --oneline -20`）。

### 3. 复述并等待确认

向用户确认三句话：问题/任务是什么、涉及哪片代码、计划按什么方向排查。用户确认前禁止进入 P0（需求类型先记进度再进 brainstorming 例外）。

**Exit criteria：** 类型已定、代码区域已定位、用户已明确说同意方向，且进度文件已按「记录协议」建好并列出全部事项（解决/优化/调整类型同样必须在进入 P0 前建好，不得延后到 P0 中途补建）。

## 通用协议（贯穿全程）

### 记录协议：进度文件（唯一真实来源）

- **目录：** `docs/root-cause-to-close/YYYY-MM/`（不存在则创建）。
- **文件名：** `progress-YYYY-MM-DD-HHmmss.md`（精确到秒）。
- **状态值：** `待处理` → `进行中` → `待用户确认` → `已完成`。**`已完成` 仅在用户确认已解决后标记**；自动化/日志验证通过只到 `待用户确认`（见 P3）。

```markdown
# 进度 — YYYY-MM-DD HH:mm:ss

## [ ] 事项 1：[简述]
- 状态：待处理 | 类型：解决/优化/调整 | 流程：本技能 P0–P6
- 根因：
- 修复：
- 验证：
- 审查报告：`.review-diffs/...`（转写摘要 + 索引路径）
```

| 时机 | 操作 |
|------|------|
| 开工前 | 建文件，列出全部事项（含中途新增），初始 `待处理` |
| 进入 P0 时 | 该事项状态由 `待处理` 置 `进行中` |
| 每阶段/Step 完成时 | **立即**写入结论 + 关键证据 + 决策理由 + 下一步，禁止"稍后" |
| 用户提新任务（任何阶段） | 立即追加 `待处理` 并告知用户；重排优先级则旧事项备注"已暂停 — 重排至 [新事项]" |
| 上下文压缩前 | 确认关键信息已落盘 |
| P6 前 | 通读文件确认事项状态 |

**子代理报告规则：** 任何子代理必须把完整报告写入独立文件（`.review-diffs/<对象>-rev<N>-report.md`），自包含输入（快照路径、任务描述）、输出（逐项结论、severity、建议修复）、依据。返回消息只给路径 + 摘要。主代理收到后**同时**做两件事：正文转写关键信息、正文索引报告路径（缺一不可）。

> 主代理只能拿到子代理最终返回消息，故必须落盘报告文件。

### 问答卡片输出协议（所有询问通用：正文先完整输出，卡片只放决策）

**铁律：任何一次弹出「询问卡片」，卡片都只承载"决策本身"（一句问题 + 简短选项）；一切分析、方案、调研结论、验证结果、升级/进度报告等实质内容，必须作为常规回复正文先完整输出。只弹卡片、正文没有完整内容，视为违规；用户看不到正文即等于你没说。**

适用范围（不限于决策）：凡需用户拍板或知晓的询问，含 P0 步骤 8 外部调研结论 / 多方案产出、P2B 预防性措施选型、P4e 需用户裁决的修复方案、P3→P4 验证报告与进度关卡、P3 失败迭代升级报告，以及任何要求用户批准 / 选择的场景。

**第一步 — 正文（回复文本，必须先可见）按内容类型包含：**

- **决策 / 多方案 / 调研类：**
  1. 对比总表（方案 × 关键维度）。
  2. 逐套：专业讲述 + 一句话类比 + 优点 / 缺点 / 注意事项（不得美化、不得省略）+ 来源链接。
  3. 调研类另附：来源原文要点（读原文不只看摘要）+ 适配结论（技术栈 / 双端一致 / 治理约束 / 许可维护 / 复杂度）。
  4. 明确推荐项及理由。
- **报告类（验证结果 / 升级报告 / 进度关卡）：** 把完整结果、证据、每轮尝试与结论逐条写全，不压缩成选项文案。

**第二步 — 「询问卡片」：** 只放 2–4 个短选项；选项名为方案名 / 简短结论，其说明最多一句话、不重复正文分析。

**禁止：** 把分析或报告只写进卡片；用卡片代替正文；选项需要用户看不到的信息才能理解；选项文案堆砌优缺点/风险/来源（这些属于正文）。

**执行顺序铁律（harness 无关，防正文不可见）：** 必须分两步走——先单独发送一条完整的正文消息（不得与工具调用合并、不得省略、不得把实质内容只写进 question 选项），确认正文已发出后，再在下一步发送「询问卡片」工具调用。禁止纯工具轮次（无正文、只发卡片工具调用）：这种轮次在用户界面只渲染卡片、正文区无任何输出，用户即等同于没看到分析，视为与“只弹卡片”同等违规。

### 日志协议

`.adl-logs/` 等被 `.gitignore` 排除，**只能用读取（绝对路径）操作，禁用搜索（多数搜索遵循 `.gitignore` 而漏掉它们）**。

| 检查项 | 路径 |
|-------|------|
| 桌面壳 + 浏览器前端 | `<仓库根>/.adl-logs/terminal-logs*.txt`、`debug-logs*.txt`、`debug-logs-browser*.txt` |
| 后端引擎 | `<仓库根>/ai-digital-life/.adl-logs/adl-server-logs*.txt` |
| 本地运行/诊断 | `<仓库根>/ai-digital-life/.run-logs/`、`/diagnostic-logs/` |
| 发布态 | `<数据根>/logs/`（无 `.adl-logs`） |

规则：逐项检查，缺项跳过不 block；`multi` 会话文件（`*-<时间戳>.txt`）先按 `LastWriteTime` 取**最新一个**，覆盖式同名文件直接读。**分析标准按日志级别（与阶段 Pn 无关，勿混淆）：ERROR（崩溃堆栈 / IPC 失败等功能错误）必须修或记录，WARN 评估，INFO/DEBUG 忽略；完成条件：无未解 ERROR。**

### 调试埋点触发与自动化验证（能力边界）

凡在 P0 / P2 / P3 加了调试日志或埋点，加完必须触发一次产生日志再下结论，禁止"加完即认为生效"。

1. **按手册启动：** 先读 `docs/development/log-system-manual.md` §1，用 CLI 启动对应模式并调高日志：桌面 `pnpm dev:tauri -- --log-level trace --terminal-log-mode multi` / 浏览器 `pnpm dev:preview -- --log-level trace --terminal-log-mode multi` / 双端 `pnpm dev:both -- ...`（`--` 不可省；设过 `RUST_LOG` 先 unset，它是硬顶、CLI 顶不开）。启动后先断言 `[ADL-LOG]` / `[ADL-CLI]` 行确认覆盖生效（`session-only`，重启即失效，不要误判为 bug）。
2. **触发埋点（二选一）：**
   - A. 有自动化操作能力（浏览器模式用 `playwright-cli`，见相关技能与 `references/playwright-cli-experience.md`）→ 自己驱动触发，复现后按日志协议读最新文件断言。
   - B. 无能力 → 用户充当"手"：给出编号步骤（启动哪个模式 → 打开哪个地址/窗口 → 点击哪里 → 看什么），并声明预期日志文件与关键标记；等用户回复"操作完成"后再读日志分析。
3. **能力现状：** 浏览器模式走 A（见 `references/playwright-cli-experience.md`）；桌面壳点击走 B。每次在进度文件记录"本次用 A / B 触发"。

组合示例：`run-project-surfaces` 起 preview → `playwright-cli` 打开其打印的 URL 触发埋点 → 按日志协议读 `debug-logs-browser*.txt` 最新文件断言。**"UI 动了" ≠ "日志写了"，两者都要断言**（只看其一会得出错误结论）。

### 测试协议（分级执行）

- **定位受影响范围：** `git diff --name-only` → Rust 按 crate（`cargo test -p <crate>`）、前端按 `__tests__/` 相关文件（`vitest run <文件>`）；同时保持 clippy/tsc 通过（`cargo check` 不单跑，clippy 已覆盖编译）。
- **默认只跑受影响部分**（修复后、每轮审查后、收尾均同）。全量命令（如 `cargo test --workspace` / 前端全量 `test`）仅在变更面广、或分级已通过但需最终兜底时，经用户同意才执行；前后端两组同一条消息并行跑，禁串行。
- 仅修工具报告的问题；自动修复引入新变更则重跑类型检查；3 次不通过 → 停并报告等指示。
- flaky 判定：疑似用例连跑 5 次，≤2 败视为 flaky（验收排除并记录），>2 败视为真失败。

## P0：根因调查（修复前必须完成全部适用步骤）

1. **读错误信息** — 完整堆栈、行号、错误码，不跳过警告。
2. **稳定复现** — 记录确切步骤；无法复现则加日志埋点、查环境差异、看最新调试日志（见日志协议）；埋点加上后必须实际触发一次（见调试埋点触发节）；**不要猜测**。
3. **查近期变更** — `git log --oneline -20`；怀疑某提交则 `git bisect`。
4. **多组件取证** — 先在组件边界埋点记录进出状态，定位"在哪一层坏"，再深入。
5. **数据流追踪** — 从表象向上追到源头，在源头修。前端用 `new Error().stack` + `console.error`；Rust 用 `tracing::error!` / `dbg!`；在危险操作**前**记录。
6. **模式分析** — 找可工作的相似功能，逐项列出差异；列出该功能依赖的组件/配置/环境。
7. **假设验证（一次一变量）** — 写下单一假设并记入进度文件 → 做最小诊断性改动（验证用，非修复）→ 成立则进 P1/P2A，不成立则还原后换新假设，不叠加改动。
8. **外部调研（触发即做，不得硬试）**
   - **触发**：无方案、无候选、知识盲区、多次失败、方案分歧、直觉有更好做法。
   - **通道（并行）**：最新资料搜索（查询词带年份如 2026，读原文不只看摘要）+ 官方文档（版本与项目对齐）+ 社区（区分"提议"与"已落地"）+ 同类产品对标（2–3 个）。
   - **适配（复用前必过）**：技术栈、运行环境（双端一致？）、项目治理约束（分层/i18n/权限/安全）、许可与维护、复杂度。
   - **多方案产出**：正文先按「问答卡片输出协议」完整输出（对比总表 → 逐套专业讲述 + 一句话类比 + 优点/缺点/注意事项（不得美化省略）+ 来源链接 + 推荐项），**再**弹出「询问卡片」等用户决策（卡片只放简短选项，分析不进卡片）。

**Exit criteria：** 能说出候选根因及其证据链，或已穷尽手段并记录每条路为何走不通（进 P1 判 B）。

---

## P1：定径

- **路径 A（根因已确认，需全满足）：** 能解释确切机制；能从触发点追到表象；改根因可修且无副作用 → 进 P2A。
- **路径 B（未确认，需全满足才可判）：** 已穷尽 P0 全部手段（含外部调研）；属环境/第三方无升级路径/不可修复外部因素；已记录调查过程与排除理由。未满足 → 返回 P0，禁止提前进预防性措施 → 进 P2B。

---

## P2：修复

### P2A：直接修复（已知根因）

1. 先建失败测试（`test-driven-development`；无自动化条件则一次性复现脚本）。
2. 在源头一次只改**一处**，不顺手改进。
3. 搜同类根因模式并一并处理。
4. 加验证日志（进出、转换前后值、错误路径、依赖假设），加完必须触发一次（见调试埋点触发节），禁止加完不跑。
5. 记进度文件 → 进 P3。

**失败迭代：** 第 1–2 次返回 P0 或补外部调研；第 3 次起**停止**并质疑架构（每次修爆新位置 / 需大规模重构 / 修一处坏一处 → 与用户讨论，配合外部调研做架构评估）。

### P2B：预防性措施（无根因）

按六维评估候选（覆盖范围 / 复杂度 / 副作用 / 可维护性 / 误判风险 / 可逆性）→ 正文先按「问答卡片输出协议」完整输出多方案分析（含六维对比与推荐项），「询问卡片」只放简短选项 → 实施并记录 → 进 P3。

---

## P3：验证

1. **补日志**（P2A 已加则跳过）：格式 `[时间戳] [级别] [组件::函数] 消息 — 键=值`；级别 DEBUG（路径追踪）/ INFO（状态转换）/ WARN（预期异常）/ ERROR（意外失败）。
2. **触发验证：** 有自动化操作能力则自己驱动触发（见调试埋点触发节），否则把用户当"手"：给出编号操作步骤（启动哪个模式、打开哪个地址/窗口、点击哪里、预期哪个文件出现什么日志），等用户回复"操作完成"后再读日志；**不预告成功**；记进度文件。
3. **日志分析**（按日志协议只取最新）：预期条目在 → 生效；错误条目 → 边界缺口；条目缺失 → 路径未触发；意外模式 → 假设错。
4. **分流：**
   - 通过（日志 + 触发方双确认）→ 状态置 `待用户确认`（**不要直接标 `已完成`**；`已完成` 仅由用户确认解决后标记，见「记录协议」），停下走 P3→P4 门控（获批才进 P4）。
   - 部分有效 → 回 P2 补缺口并记录。
   - 无效/回归 → 记录后按 方案 → 代码 → 方法 → 架构 逐层排查。
   - 用户说没解决 → 记"用户报告无效"进失败迭代（最多 3 轮，第 4 轮禁止，直接升级报告：每轮尝试、学到什么、未解架构问题；等待批准期不计入迭代轮次）。

**P3→P4 过渡（用户批准门控，禁止自行进入 P4）：** P3 自动化验证通过后必须停下，弹出「询问卡片」向用户报告验证结果并等待用户亲自测试（用户可明示免测并直接授权，此时视为已批准，记入进度文件）。**验证结果按「问答卡片输出协议」作为正文完整输出，卡片只放批准/不批准等短选项。**

两种确认**分开记录**（自动化通过本身两者都不算）：

- **(a) 确认已解决：** 用户说"解决了/搞定了"等 → 标记 `已完成` + 时间戳。
- **(b) 批准进入收尾：** 用户明确同意（"可以进收尾 / 进 P4 / 批准 / 可以"）→ 可进 P4。
- 同一句可同时满足两者（如"解决了，可以收尾"）。只得到 (a)、未得到 (b) 时，仍须等明确批准。
- 无论走哪条路径，取得 (a)/(b) 后都要读进度文件做进度关卡：有未完成事项逐项问用户（逐项内容走正文；可与批准问合并为一次「询问卡片」）。
- 模糊词（"好了""应该行"等）二次确认一次："确认已解决、可进收尾了吗？"——用户答"可以"才算批准。

## P4：审查引擎

### 4a. 前置检查

- `git branch --show-current`、`git status --short`；未跟踪文件判定是否为本次产物。
- git 在仓库根执行；`cargo`/`pnpm` 在 `ai-digital-life/` 执行；命令前按规则 `.agents/rules/commands.md` 设 PATH。
- 磁盘（可选）：`clean-target.ps1 -WhatIf` 干跑后问用户；`target/debug` 超 30 GB 才全量 `cargo clean`（**永久删除**，不进回收站）。

### 4b. 采集变更 + 快照预生成

| 类型 | 命令 | 说明 |
|------|------|------|
| 未提交（含暂存） | `git diff HEAD` | — |
| 已提交未推送 | `git diff origin/HEAD..HEAD`（`origin/HEAD` 不存在则跳过） | 已推送的不审 |

两类都无变更 → 跳过 4c–4e（进度文件记理由），仅保留 Exit criteria 中的分级测试。有变更时按下述建快照，再进 4c 两轮必跑：

1. 建 `.review-diffs/`（已在 `.gitignore`，P6 删除）。
2. 按文件拆快照：文件列表 = `git diff --name-only HEAD` ∪（存在时）`git diff --name-only origin/HEAD..HEAD`；每文件把两来源的 diff 拼接为 `<路径斜杠换下划线>-rev<N>.diff`（例：`src_app_foo.ts-rev1.diff`）；同步写 `changed-files-rev<N>.txt`。
3. 子代理只读快照，禁止终端 `git diff`；每轮修复后 rev 递增**全量重生成**，复审看最新完整 diff（禁只看增量/复用旧快照）。

### 4c. 两轮循环审查（顺序门控，两轮皆不可跳过）

**门控铁律（违反即 Red Flag，见底部表格）：**

1. 两轮都必须跑（有变更时；无变更按 4b 跳过并记理由），且每轮至少一次完整的子代理派发：禁止以"自判已干净""上一轮已删日志/死代码""改动小""看起来没问题"等任何理由跳过 R1、R2 或其中任意一次复审。**自判 ≠ 审查通过**，只有子代理返回的"零问题"才算通过。
2. 顺序门控：R2 禁止与 R1 并行、禁止提前启动。只有 R1 循环达到"本轮零问题"并记入进度文件后，才允许进入 R2；只有 R2 循环达到"本轮零问题"，才允许退出 P4。
3. 每轮都是循环：`审查（本轮范围）→ 4d 验证 → 4e 修复 → rev 递增全量重生成快照 → 同范围复审`，直到本轮零问题。禁止"每轮只审一次就放行"。

**本轮零问题的定义：** 该轮最新一次子代理审查结果，经 4d 逐项验证后，无"需修复"项残留（误报 / 有据保留已记理由、且下一轮复审子代理无异议）。只要还有需修复项，或"不修"被子代理成功异议，就不算零问题，继续本轮循环。

- **R1 循环（正确性，不通过不进 R2）**：按事项数派发（1–5 个事项逐项各派 1 个子代理；>5 个事项时，diff <50 行的小事项可合并、大事项仍逐项），同一条消息并行派发（可写文件子代理，仅允许写指定报告文件，源码只读）。覆盖：根因与正确性、设计质量、副作用与安全、预存问题、优化机会。每项给文件+行号、severity（critical/high/medium/low）、类别、描述、建议修复。修完 rev 递增后，**仍用 R1 范围**复审，循环至 R1 零问题。
- **R2 循环（清理，仅 R1 零问题后进入，同样循环至零问题）**：即使 R1 修时已删日志/死代码，仍必须完整派发一次，不可省略。覆盖：死代码、冗余守卫、根因修后多余的防御、应删/降级的诊断日志。不标：正当错误处理、系统边界验证、生产 warn/error 日志。修完 rev 递增后，**仍用 R2 范围**复审，循环至 R2 零问题。
- **合并（主代理执行，每轮各做一次）：** 去重（同文件同行同类留最详者）→ severity 降序。

### 4d. 主代理问题验证（修复前置，逐项必做并记进度文件）

默认都要修，仅下表情形可不修（仍须先验证真实性：重读代码、核对调用链、排除误报与过期快照）：

| 情形 | 处理 |
|------|------|
| 误报/过期快照假阳性 | 不修，记理由 |
| 用户特殊设计 / 正当防御性代码 / 合理兼容（有注释/文档/提交佐证、利长期演进） | 仍须检查优化空间；确认无改进才保留并记理由；无法确认则问用户 |
| 无用防御（根因修后多余、重复守卫）/ 不合理·偷懒兼容 / 非本次引入但在范围内 | 修（含预存与低级别问题） |

"不修"理由写入进度文件并带给下一轮子代理，其可异议，成立则重估，循环至一致。

### 4e. 修复循环与升级

- 需「询问卡片」的情形（满足任一）：动核心架构/大重构/破兼容、业务决策无法自判、多套可行方案、新依赖或安全策略变更、无法判定是否用户特殊设计。**正文先按「问答卡片输出协议」给出完整方案分析（逐套优缺点风险 + 推荐项），卡片只放 2–4 个简短选项。**
- 约束：只修验证通过的问题，守 `.agents/rules/` 与双端一致、i18n、无硬编码文本等治理；不带无关变更。
- 每轮修完必须 rev 递增全量重生成快照，并重跑**本轮同范围**审查（不可自判跳过本轮复审、不可跳轮、不可用"只看增量/复用旧快照"代替）；同一问题 3 轮未解 → 停并向用户报告等指示。

**Exit criteria：** 已批准收尾（P3→P4 门控通过，或从 P4 直进的已授权）**且** R1 循环零问题 **且** R2 循环零问题（两轮先后达标，有进度文件记录；**无变更按 4b 跳过审查轮次除外，须在进度文件记理由**） + 分级测试通过。任一轮未跑、未循环至零问题，都不算 P4 完成。用户已在 P3→P4 批准收尾，P4 达标后直接进 P5，中间不停留。

## P6：清理 + 总结

**清理（预授权范围，无需再问用户）**（先用读取确认存在再删，年龄按 `LastWriteTime`）：两处 `.adl-logs/`（仓库根与 `ai-digital-life/`）超 7 天文件；`debug-logs*.txt`、`debug-logs-browser*.txt`、`adl-server-logs*.txt` 运行残留；根 `test-artifacts/` 超 3 天临时文件；删除 `.review-diffs/` 全部快照。用过 `playwright-cli` 则一并清理其测试产物：关闭残留浏览器会话（`close-all`），删除仓库内 `.playwright-cli/` 目录（快照/trace/录像）与测试截图；产物若在 Temp 目录则整批删除。

**清理范围边界：** 上述"本技能自有临时产物"才属预授权；`.run-logs/`、`diagnostic-logs/`、发布态 `<数据根>/logs/` 及被跟踪文件不在预授权内，需清理时另行询问。删除未提交源码/他人改动/被跟踪文件、或执行 `cargo clean` 等破坏性操作前，必须先向用户询问（对应底部 Red Flag"未经确认的清理"）。

| 某阶段完成未立即落盘；子代理无独立报告；总结凭记忆；进度关卡未过先进收尾 | 记录协议 |

| 破坏性 git 操作；未经确认提交/清理（`cargo clean` 为永久删除） | 全程 |

## Quick Reference

| 阶段 | 关键动作 | 完成条件 |
|------|---------|---------|
| 预检 | 分类 → 探索（codegraph 优先）→ 复述确认 | 用户同意方向 |
| 记录 | 建 `docs/root-cause-to-close/YYYY-MM/progress-*.md`，每阶段即记 | 唯一来源最新 |
| P0 | 读错→复现→查变更→取证→追流→比模式→单变量假设→外部调研（卡住即触发） | 根因证据链或穷尽记录 |
| P1 | 全条件判定 A（修根因）/ B（预防） | 路径明确 |
| P2 | 失败测试→单点修→查同类→加日志；失败 3 次停 | 改在源头 |
| P3 | 补日志→触发验证（自动优先/用户为手）→最新日志分析→分流；3 轮上限；验证通过置 `待用户确认`，停下等用户批准，禁自行进 P4 | 双确认通过 + 用户明确批准 |
| P4 | 前置检查→快照（未提交 ∪ 未推送）→R1 循环至零问题→R2 循环至零问题（两轮顺序、每轮循环、皆不可跳过）→验证→修复循环；达标后直接进 P5 | R1 与 R2 先后零问题 |
| P5 | 九类文档逐项表态 + 三目录同步 + 索引登记；完成后直接进 P6 | 列出更新 |
| P6 | 按龄清理 + 读进度文件总结 | 用户知晓结果 |
| 测试（全程分级） | `git diff` 定位受影响，clippy/tsc + 分级 test，禁全量替代 | 零警告错误 |
| 埋点触发（P0/P2/P3 加埋点后） | 按手册启动→驱动/编号步骤触发→读最新日志断言 | 日志与断言对上 |
| 询问卡片（决策/报告/门控） | 正文先完整输出（总表/逐套/来源/推荐/报告全量）→ 再弹卡片（只放短选项） | 用户先看到完整内容再选择 |

> **四处"3"是各自独立的计数，互不折算：** P2A 同一根因修复失败 3 次 → 停并质疑架构；P3 用户报告未解决满 3 轮 → 升级报告；P4 同一审查问题修复 3 轮未解 → 停并请示用户；测试协议"自动修复后类型检查 3 次不通过 → 停并报告"。
