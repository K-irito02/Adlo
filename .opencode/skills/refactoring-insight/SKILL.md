# 重构洞察（Refactoring Insight）

对 ai-digital-life 项目执行系统性重构洞察，发现架构设计问题与性能优化机会，生成洞察报告和实施计划，并按增量迭代方式执行实施。

---

## 触发条件

当用户表达以下意图时，立即调用本技能：
- "执行重构洞察"
- "生成重构报告"
- "分析代码质量 / 扫描重构机会"
- "refactoring insight / code quality scan"
- 任何涉及项目级代码质量评估与重构规划的请求

---

## 总流程

```
阶段 1: 宏观审视 → 阶段 2: 系统扫描 → 阶段 3: 生成报告 → 阶段 4: 生成实施计划 → 阶段 5: 执行实施
```

---

## 阶段 1: 宏观审视（整体大框架）

在深入具体文件之前，先建立全局视图：

### 1.1 架构概览
- 读取 `docs/重构洞察/REFACTORING_PROGRESS_REPORT.md` 了解已完成的重构轮次
- 读取 `docs/重构洞察/REFACTOR_INSIGHTS_SUMMARY.md` 了解历史发现和待处理项
- 读取最新一期的 `docs/重构洞察/refactor-insight-*.md` 了解上轮发现和遗留问题
- 检查 `.trae/rules/` 中相关规则文件了解当前架构约束

### 1.2 宏观统计
- 统计各子目录的文件数量和大文件分布（>500 行、>1000 行）
- 识别 `frontend/src/` 中组件膨胀点（>800 行的组件文件）
- 识别 `src-tauri/src/commands/` 中函数膨胀点（>80 行的函数）
- 识别 `crates/` 中 crate 规模和依赖关系
- 统计 CSS 文件行数分布（>1000 行的大文件）
- 统计 `!important` 使用量

### 1.3 宏观问题识别
- 是否存在上次洞察遗留的未处理项
- 是否存在违反架构约束（如层级越界、crate 依赖倒置）的模块
- 是否存在新引入的膨胀组件/函数/文件

---

## 阶段 2: 系统扫描（从小处着手）

基于宏观审视结果，按以下维度逐项扫描：

### 2.1 前端 TypeScript/React 扫描

| 扫描项 | 方法 | 阈值 |
|--------|------|------|
| 大组件文件 | `Grep` 统计 `frontend/src/` 下 `.tsx` 文件行数 | >800 行标记 |
| 大 Hook 文件 | `Grep` 统计 `frontend/src/` 下 `use*.ts` 文件行数 | >300 行标记 |
| 重复 JSX | 扫描同一文件中重复渲染的组件块（如两次相同组件仅 props 不同） | 可提取为组件 |
| 多组独立状态 | 扫描组件中 `useState` 数量 | >5 组建议提取 Hook |
| 深层相对导入 | 扫描 `'../../../../'` 等深层导入 | 建议使用 `@` 别名 |
| 硬编码字符串 | 扫描非 i18n 的 UI 文本 | 必须替换为 i18n key |
| `console.log` 残留 | 扫描调试日志 | 必须清理 |
| 选择器未 useShallow | 扫描 `useAppStore` 调用是否使用选择器 + useShallow | 优化重渲染 |
| React.memo 缺失 | 扫描列表项组件是否缺少 memo 包装 | 优化列表渲染 |

### 2.2 Rust 后端扫描

| 扫描项 | 方法 | 阈值 |
|--------|------|------|
| 大函数 | `Grep` 扫描 `src-tauri/src/commands/` 和 `crates/` 中的函数体长度 | >80 行标记 |
| 不必要的 clone | 扫描函数签名中参数为 `String` 但仅用于引用传递的场景 | 建议改为 `&str` |
| 大 lib.rs | 扫描 `crates/*/src/lib.rs` 行数 | >300 行建议模块化 |
| 错误处理 | 扫描 `unwrap()` / `expect()` 使用 | 建议改为 `?` 或 Result |
| Mutex 使用 | 扫描 `std::sync::Mutex` 使用 | 评估是否可降级为 RwLock |

### 2.3 CSS 样式扫描

| 扫描项 | 方法 | 阈值 |
|--------|------|------|
| 大 CSS 文件 | `Grep` 统计 `frontend/src/styles/` 下 `.css` 文件行数 | >1000 行建议拆分 |
| `!important` 滥用 | 扫描 `!important` 声明数量 | 每个文件 >10 处标记 |
| 硬编码颜色 | 扫描 hex/rgb/hsl 颜色值（排除 CSS 变量定义文件） | 必须替换为 `var(--...)` |
| `transition: all` | 扫描该模式 | 必须替换为具体属性 |
| 死 CSS | 扫描孤立 CSS 文件（无对应组件引用） | 建议删除 |

### 2.4 跨领域扫描

| 扫描项 | 方法 |
|--------|------|
| 桥接层对齐 | 检查 `tauri-bridge.ts` / `preview-bridge/` / `mock-bridge.ts` 方法签名一致性 |
| IPC 契约 | 检查 `shared/ipc.ts` 与实际实现是否一致 |
| 死代码 | 搜索 `@deprecated` 标注、导出但未使用的函数/类型 |
| Store 膨胀 | 检查各 slice 文件行数，>500 行建议拆分 |

### 输出文件

```markdown
# 重构洞察报告 – ai-digital-life
**生成日期**：YYYY-MM-DD

| 位置（文件:行/函数） | 问题描述 | 优化建议 | 优先级 |
|----------------------|----------|----------|--------|
|                      |          |          |        |

## 2. 性能优化
| 位置（文件:行/函数） | 问题描述 | 优化建议 | 优先级 |
|----------------------|----------|----------|--------|
|                      |          |          |        |

## 3. 其他发现（可选）
- 若无则省略此节。

### 本轮统计数据

| 指标 | 数值 |
|------|------|
| xxx  | xxx  |

> 由自动化重构洞察生成于 YYYY-MM-DD HH:MM:SS
```

### 问题描述规范

- **位置精确**：`文件路径:L行号/函数名`，如 `frontend/src/app/features/browser/BrowserPanel.tsx:L91-167`
- **描述具体**：说明当前状态、为何是问题、影响范围
- **建议可行**：给出具体的优化方案，而非模糊建议
- **优先级判定**：

| 优先级 | 判定标准 |
|--------|----------|
| 🔴高 | 影响功能正确性、架构严重违规、超大文件/函数（>1000 行）、大量重复代码 |
| 🟡中 | 组件/函数超标但未达临界值、CSS 规范违规、性能可优化但非瓶颈 |
| 🟢低 | 代码风格改进、次要优化、非紧急清理 |

### 统计指标

报告末尾必须包含本轮统计数据表，至少包含：
- 前端组件/Hook 提取数量
- Rust 函数拆分/clone 消除数量
- CSS 文件拆分/`!important` 清理数量
- 预测代码行变化（+新增 / -删除）

## 阶段 4: 生成实施计划

洞察报告生成后，自动生成实施计划文档。

### 输出文件

- 路径：`docs/重构洞察/refactor-plan-YYYY-MM-DD.md`

### 计划模板

```markdown
# 重构实施计划 – YYYY-MM-DD

## 执行顺序

按优先级排序，同优先级中按"最小变更→最大变更"排序：

| 序号 | 任务 | 优先级 | 变更范围 | 预计影响 |
|------|------|--------|----------|----------|
| 1    |      | 🔴高   | 单文件   | 低风险   |
| 2    |      | 🔴高   | 多文件   | 中风险   |
| ...  |      |        |          |          |

## 执行原则

1. **先小后大**：优先执行单文件、低风险变更，积累信心后再推进大范围变更
2. **每步验证**：每完成一项变更，立即运行类型检查 + 相关测试
3. **不破坏现有功能**：所有修改不得改变 UI/UX 行为
4. **失败即停**：任一步骤失败，停止后续执行，分析原因后决策

## 风险控制

| 风险项 | 缓解措施 |
|--------|----------|
| 组件拆分导致功能回归 | 先运行现有测试，拆分后再次运行确认 |
| Rust 签名变更导致编译失败 | 先 cargo check，再 cargo test |
| CSS 拆分导致样式错乱 | 拆分后视觉验证关键页面 |
```

## 阶段 5: 执行实施

### 执行流程

```
生成计划 → 逐项执行 → 每项验证 → 更新进度报告 → 清理收尾
```

### 5.1 逐项执行

按实施计划中的序号顺序执行，每项遵循：

1. **执行前**：读取目标文件，确认当前状态
2. **执行变更**：遵循最小变更原则，不做无关修改
3. **执行后验证**：
   - 前端变更：`pnpm --dir frontend run typecheck` + `pnpm --dir frontend run test`
   - Rust 变更：`cargo check --workspace` + `cargo test --workspace`
   - CSS 变更：`pnpm --dir frontend run lint:fix` + `pnpm --dir frontend run format`
4. **验证通过** → 标记完成，继续下一项
5. **验证失败** → 修复问题后重新验证，3 次仍失败则报告用户

### 5.2 同步更新进度报告

每完成一项变更，更新 `docs/重构洞察/REFACTORING_PROGRESS_REPORT.md`：

- 在"完成状态"表格中追加本轮记录
- 格式：`| 第N轮 | YYYY-MM-DD | 内容摘要 | ✅ |`

### 5.3 更新洞察汇总

全部任务完成后，更新 `docs/重构洞察/REFACTOR_INSIGHTS_SUMMARY.md`：

- 在"按日期索引"表格中追加本轮记录
- 在"各日洞察摘要"中追加本轮摘要段落

### 5.4 清理收尾

- 清理临时文件
- 确认无遗留的 `console.log` 调试代码
- 执行最终四维门禁检查（ESLint / Prettier / Clippy / rustfmt）

---

## 约束与禁止项

| 约束 | 说明 |
|------|------|
| 核心原则 | 所有修改不得破坏现有功能效果以及 UI/UX |
| 影响评估 | 变更前识别涉及模块与依赖，设计完整测试用例，覆盖相关功能路径 |
| 风险把控 | 确保变更是经充分论证的正向改进，能提升性能、安全、可维护性或体验后方可实施 |
| 最小变更 | 仅修复发现的问题，不做无关的代码变更 |
| 禁止跨 Phase 变更 | 不引入超出当前 Phase 范围的功能或架构变更（见 `phase-boundary.md`） |
| 禁止凭空猜测 | 无法定位根因时，使用调试日志而非猜测性修复 |
| 验收强制 | 全部变更完成后必须执行结束验收流程（见 `mandatory-testing.md`） |
