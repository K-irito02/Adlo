# 根因排查与解决

## 概述

随机修复浪费时间并制造新 Bug。快速补丁掩盖根本问题。

**核心原则：** 先找到根因，再修复。未与用户确认意图之前，禁止进入 Phase 0 调查或任何修复阶段（预检的代码探索除外）。

**阶段：** 预检（内容分类、探索与确认）→ 0（调查）→ 1（路径）→ 2A（直接修复）/ 2B（预防性）→ 3（验证）→ 过渡（触发检测）→ 4（收尾归档）。

**贯穿全程：** 进度追踪（进度文件为唯一真实来源）、阶段自动记录（防上下文丢失）、测试分级执行（只执行受影响的测试）。

> **文档路径基准（重要）**：本技能中所有 `docs/...` 路径均以**仓库根目录**（含根 `AGENTS.md` 与 `docs/` 的治理根，即 `ai-digital-life/` 的父目录）为基准。即使当前工作目录位于 `ai-digital-life/` 子工作区，也必须写入根仓库的 `docs/`，禁止在 `ai-digital-life/docs/` 下另建文档目录。

## 预检：内容分类、探索代码与确认意图

**进入 Phase 0 之前必须完成。** 防止误解用户意图。在探索与确认完成之前，禁止进入 Phase 0 或做出任何修复（需求相关类型例外：先记录进度文件再进入 brainstorming）。

### 第 0 步：内容类型分类

收到用户内容后，先分类再决定处理流程，禁止直接进入探索或修复：

| 内容类型 | 判定特征 | 处理方式 |
|---------|---------|---------|
| **需求相关类型** | 新功能、新组件、页面、创意、行为变更等"要做新东西" | 使用 `brainstorming` 技能设计，**同时**将事项记录到进度文件 |
| **解决/优化/调整类型** | Bug 修复、性能优化、结构调整、行为修正等"改已有东西" | 走本技能流程（第 1 步探索 → 确认 → Phase 0-4） |

**规则：**

1. **需求相关类型**：调用 `brainstorming` 技能，并**立即将事项记录到进度文件**（标题、状态 `进行中`、产物路径）。brainstorming 产出设计后回到本技能流程衔接实施。
2. **解决/优化/调整类型**：继续第 1 步探索代码。
3. **混合内容**：需求部分走 brainstorming，解决/优化/调整部分走本流程；两部分在同一进度文件记录，互不遗漏。
4. **当需求相关类型使用了 brainstorming 且任务同时包含解决/优化/调整问题时**：brainstorming 的 **space（探索/发散）阶段**与**实施计划阶段**必须**同时覆盖这些解决/优化/调整问题**，不能只设计需求部分。进入 brainstorming 前，把两部分事项一次性全部写入进度文件，作为 brainstorming 阶段任务的输入。
5. 分类不确定时，询问用户该内容属于"新需求"还是"解决/优化/调整问题"。

### 第 1 步：探索相关代码

- 基于用户提示词，定位并阅读相关代码（文件、调用链、配置、近期变更）
- 优先使用 `codegraph-knowledge-graph` 技能查询符号与调用链，替代逐文件爬取
- 快速理解上下文，形成初步判断，不急于提出方案

### 第 2 步：向用户复述理解

用简短语言向用户确认：

1. **问题/任务** — "你遇到的问题是 X / 你希望完成的任务是 Y"
2. **涉及的代码区域** — "我理解问题可能涉及 [文件/模块]"
3. **初步方向** — "我计划按 [方向] 排查，是否与你的预期一致？"

### 第 3 步：等待用户确认

| 用户反馈 | 操作 |
|---------|------|
| 确认一致 | 创建进度文件，进入 Phase 0 |
| 纠正/补充 | 调整理解，必要时重新探索，循环直到对齐 |
| 方向有偏差 | 停下，向用户重新澄清后再继续 |

### 确认清单

| 项 | 检查点 |
|----|--------|
| 问题/任务 | 描述与用户实际要解决的完全一致 |
| 代码区域 | 已定位相关代码并理解其上下文 |
| 方向 | 用户认可计划的排查方向 |
| 范围 | 任务边界清晰，未擅自扩大或缩小 |

## 进度追踪

在整个排查过程中，维护一份**进度文件**追踪所有问题、任务及其解决状态。

### 文件管理

- **目录**：`docs/root-cause-resolution/`（不存在则创建）
- **文件组织**：按月归档到 `docs/root-cause-resolution/YYYY-MM/` 子目录，不存在则创建
- **文件名**：`progress-YYYY-MM-DD-HHmmss.md`（精确到秒，避免重复）
- **状态值**：`待处理` → `进行中` → `已完成`（仅在用户确认后）

### 文件格式

```markdown
# 进度 — YYYY-MM-DD HH:mm:ss

## [ ] 事项 1：[问题/任务的简要描述]
- 状态：待处理
- 根因：
- 修复：
- 验证：

## [ ] 事项 2：[简要描述]
- 状态：进行中
- 备注：正在排查…
```

### 更新规则

| 时机 | 操作 |
|------|------|
| 工作开始前 | 创建文件，列出所有问题/任务，初始状态 `待处理` |
| 开始处理某事项 | 状态设为 `进行中` |
| 调查/修复过程中 | 追加过程记录（根因发现、修复尝试、验证步骤） |
| 用户确认解决 | 标记 `已完成`，记录确认时间戳 |
| 用户提出新任务（任何时候） | 立即追加新事项，告知用户 |
| 进入 Phase 4 前 | 检查所有事项，未完成的先与用户确认 |

### 新任务处理

用户在任何阶段提出新任务时：
1. 立即追加到进度文件，状态 `待处理`
2. 告知用户："已记录新任务：[描述]"
3. 继续当前工作，除非用户明确重新排定优先级
4. 若重新排定优先级，前一个事项备注"已暂停 — 重新排定至 [新事项]"

### 核心规则

- 即使是"简单"问题也必须创建进度文件
- 每次重要事件后立即更新，不要"稍后"
- 进度文件是活跃工作的唯一真实来源，不要依赖记忆
- Phase 4 前必须读取文件确认所有事项状态

## 阶段自动记录（防上下文丢失）

**目的：** 防止上下文压缩导致必要信息丢失。所有关键信息必须存在于文档中，禁止依赖 Agent 记忆、回溯或追踪。**主 Agent 与子 Agent 都必须自动记录到对应文档。**

### 主 Agent：每阶段完成后立即记录

每个阶段（预检、Phase 0、1、2A/2B、3、过渡、4）**完成时立即**更新进度文件，写入该阶段：

- **结论** — 根因/方案/验证结果
- **关键证据** — 错误信息、日志摘要、复现步骤、数据值
- **决策与理由** — 选了哪条路径、为什么
- **下一步** — 下一阶段入口信息

| 时机 | 记录内容 |
|------|---------|
| 预检分类完成 | 事项清单、类型（需求/解决/优化/调整）、处理流程 |
| 每阶段完成 | 阶段结论 + 关键证据 + 决策理由 + 下一步 |
| 上下文压缩前 | 确认所有关键信息已写入文档 |

阶段完成即记录，禁止"稍后一起记"。

### 子 Agent：必须写入独立报告文件

**任何派发的子 Agent（Phase 4 审查循环及其它）都必须将完整报告写入独立报告文件**（如 Phase 4 审查：`.review-diffs/review-issue-N-revM.md`；其它子 Agent：对应归档目录）。报告文件必须自包含：

- **输入** — diff 快照路径、审查范围、任务描述
- **输出** — 结论、严重性、建议修复方案
- **上下文** — 判断依据、引用的代码位置

返回消息只需给出**报告文件路径 + 关键摘要**，完整信息在文件中。

> **已实测（2026-08-15）：** 主 Agent 无法读取子 Agent 的窗口/会话上下文，只能获得子 Agent 的最终返回消息（隐藏信息无法透出）。因此子 Agent 必须写独立报告文件，不能依赖返回消息承载必要信息。

### 主 Agent 转写与索引

子 Agent 报告返回后，主 Agent 立即将关键信息**转写**到进度文件，**并**将对应子 Agent 报告**索引**添加到进度文件——两件事必须同时执行，不是"转写或索引"二选一：

1. **转写关键信息** — 结论摘要、需处理的问题列表、严重性（直接写入进度文件正文）
2. **添加子 Agent 报告索引** — 报告文件路径（如 `.review-diffs/review-issue-N-revM.md`）

使进度文件成为唯一真实来源：正文含可直接使用的关键信息（转写），同时保留可回溯完整报告的路径（索引）。任何子 Agent 报告丢失时仍可恢复。

## 测试策略（分级执行）

**所有阶段只执行受影响的测试，不固定执行全量测试。** 根据变更内容定位受影响的测试文件或 crate，仅运行这些测试。

| 时机 | 执行范围 |
|------|---------|
| Phase 2A/2B/3 修复或验证后 | 只跑受影响部分：Rust `cargo test -p <受影响crate>`、前端 `vitest run <受影响测试文件>`；保持 clippy/tsc 通过 |
| 子代理循环内每轮修复后 | 同上，只跑受影响部分 |
| Phase 4 收尾验证 | 只跑受影响部分：根据变更范围定位受影响的测试，不执行全量测试 |

**受影响测试定位方法：**
- 通过 `git diff --name-only` 获取变更文件列表
- Rust：根据变更文件路径判断所属 crate，运行 `cargo test -p <crate>`
- 前端：根据变更文件匹配相关测试文件（`__tests__/` 目录下同名或相关文件）

## Phase 0：根因调查

在尝试任何修复之前，必须完成以下所有步骤。

### 第 1 步：仔细阅读错误信息

- 完整阅读堆栈跟踪，注意行号、文件路径、错误码
- 不要跳过任何错误或警告
- 错误信息通常包含精确的解决方案

### 第 2 步：稳定复现

- 能否稳定触发？确切步骤是什么？
- 如果无法复现：
  - 在疑似触发点添加日志埋点
  - 检查环境问题（操作系统、Node 版本、配置差异）
  - 查看调试日志：`debug-logs.txt`（Tauri）或 `debug-logs-browser.txt`（浏览器）
  - 使用控制台工具：`__clearDebugLogs()` 清除旧日志，`__exportDebugLogs()` 手动导出
  - **不要猜测** — 收集更多数据直到能复现或隔离触发条件

### 第 3 步：检查近期变更

- `git log --oneline -20` 查看近期提交 — 什么改动可能导致此问题？
- 怀疑某次提交引入时，使用 `git bisect` 二分定位
- 新依赖、配置变更、环境差异

### 第 4 步：收集多组件证据

当系统包含多个组件时，在提出修复方案前先添加诊断埋点：
- 记录数据进出每个组件边界时的状态
- 验证环境/配置的传播
- 运行一次收集证据，确定**在哪里**出问题，再深入调查

### 第 5 步：数据流追踪

当错误位于调用栈深处时，向后追踪找到原始触发点：
- 错误值从何处产生？是谁用错误值调用了当前函数？
- 持续向上追踪直到找到源头，在源头修复而非表象处

手动追踪困难时，使用堆栈追踪：

**前端（TypeScript）：**
```typescript
const stack = new Error().stack;
console.error('DEBUG 操作:', { directory, cwd, stack });
```

**后端（Rust）：**
```rust
tracing::error!(?path, ?config, "操作失败");
// 或快速调试：dbg!(&value);
```

> 使用 `console.error()` / `tracing::error!()`（日志器可能被抑制）；在危险操作之前记录，而非失败之后；包含上下文和堆栈。

### 第 6 步：模式分析

- 查找可工作的示例 — 什么相似的功能是正常的？
- 对比参考实现，列出正常与异常之间的每一个差异
- 理解依赖关系 — 此功能需要哪些组件、配置、环境？

### 第 7 步：假设与验证（科学方法）

1. 形成单一假设："我认为 X 是根因，因为 Y" — 要具体，**[进度] 记录到进度文件**
2. 最小化验证 — 做**最小**可能的诊断性改动，一次只改一个变量（**仅用于验证假设，不是修复**）
3. 验证后继续 — 有效则确认根因并进入 Phase 2A；无效则形成**新**假设，不在已有改动上叠加

### 第 8 步：外部调研（没有方案或需要调研时）

上述步骤中遇到以下任一情况时，必须触发外部调研，不得闷头硬试：

| 触发场景 | 说明 |
|---------|------|
| 尚无设计解决方案 | 需要给出方案但内部暂无成熟想法时，先调研再设计，禁止凭空设计 |
| 没有候选方案 | 所有方案评估后均不可行 |
| 完全不知道如何解决 | 缺乏相关知识或经验 |
| 遇到特别顽固的问题 | 多次尝试后问题依然存在 |
| 技术方案有根本性分歧 | 现有知识无法判断哪种方案正确 |
| 怀疑有更好的做法但不知道 | 直觉感到当前方案不够好 |

**调研通道（按需组合，并行执行）：**

1. **最新资料搜索**（`WebSearch` / `WebFetch`）— 搜索相关最新信息资料，查询词带年份（如 2026），优先近 1-2 年内容；拿到链接后用 `WebFetch` 读原文，不只看搜索摘要
2. **官方文档核验** — 相关库/框架/语言的官方文档为准，确认 API 现状、推荐做法与废弃说明；文档版本须与项目实际版本对齐
3. **社区讨论** — GitHub Issues/PR、Stack Overflow、官方论坛/Discord：看真实踩坑、维护者表态、已合并的解法，区分"有人提议"与"已落地验证"
4. **同类产品对标** — 找 2-3 个同类型产品，看它们如何处理相同问题（交互、架构、数据流），提炼可借鉴的优秀方案

**技术栈与环境适配（对标与复用前必做）：**

照搬前先过一遍下表，不满足则降级或放弃：

| 适配项 | 检查问题 |
|-------|---------|
| 技术栈 | 语言/框架/运行时是否一致？需引入新依赖吗？成本多高？ |
| 运行环境 | 桌面/浏览器/服务端差异？双端行为能否一致？ |
| 项目约束 | 是否违反现有架构分层、权限、安全、i18n 等治理规则？ |
| 许可与维护 | 对方方案的许可是否允许？上游是否仍在维护？ |
| 复杂度 | 团队能否理解与维护？调试成本如何？ |

**判断与取舍：**

结合自身知识做取舍，不盲目复制：外部方案只是输入，最终以"根因 + 项目约束"裁决。每个候选方案标注来源链接，说明采纳/舍弃理由。不知道时，说"我不理解 X"，继续调研而非硬上。

**产出格式（调研结论必须写入进度文件）：**

- **单方案**：专业讲述（机制、调用链、关键代码位置）+ 一句话通俗解释（打比方）+ 优点/缺点/注意事项 + 来源链接
- **多方案（2-3 套为宜）**：先给对比总表，再逐套展开，每套固定结构：
  - **专业讲述** — 原理、关键步骤、涉及模块
  - **通俗解释** — 用一句话类比让非专业读者听懂
  - **优点 / 缺点 / 注意事项** — 缺点与注意事项不得省略或美化
  - **推荐度** — 明确标注最推荐项及理由
- 展示后用 `AskUserQuestion`（OpenCode：`question`）请用户讨论选择，等待决策后再实施

**查询模板：**
```
"[技术/库] [问题描述] 最佳实践 2026"
"[错误信息或症状] 解决方案 site:github.com"
"[同类产品名] [功能/问题] how it works"
"[库/框架] [API] official docs migration"
```

> 结合项目上下文调整，不要盲目复制。不知道时，说"我不理解 X"，触发外部调研。

## Phase 1：确定路径

### 路径 A：已确认根因

**条件（必须全部满足）：**
- 能够解释导致问题的确切机制
- 能够从触发点到表象追踪数据/控制流
- 修改已确认的根因能修复问题且无副作用

→ 进入 Phase 2A（直接修复）。

### 路径 B：未确认根因

**只有在以下所有条件都满足时**才能得出"未找到根因"的结论：
- 已穷尽 Phase 0 所有调查手段（完整调用栈、组件边界、Git 历史、稳定复现、外部调研）
- 已确认问题属于环境层面、已知的第三方依赖限制（无升级路径）或无法修复的外部因素
- 已记录所调查的内容以及每条路径为何行不通

**未满足条件 → 返回 Phase 0。** 不要过早进入路径 B。

→ 进入 Phase 2B（预防性措施）。

## Phase 2A：直接修复（已知根因）

1. **创建失败测试用例** — 优先使用自动化测试（参考 `test-driven-development` 技能），没有则用一次性脚本
2. **设计修复方案** — 在根因源头修复，一次只改**一处**，不要"顺手"做额外改进
3. **检查同类问题** — 代码库中是否还有其他地方存在相同根因模式？
4. **添加验证日志** — 记录修复点的进入/退出、数据转换前后值、错误路径、修复依赖的假设
5. **[进度] 更新进度文件** — 记录根因、修复方案和发现的同类问题
6. **进入 Phase 3**

### 修复无效时

| 失败次数 | 操作 |
|---------|------|
| 第 1 次 | 返回 Phase 0 重新分析，或触发外部调研 |
| 第 2 次 | 返回 Phase 0 或触发外部调研；记录失败尝试 |
| 第 3 次及以上 | **停止。** 触发外部调研 + 质疑架构（见下方） |

### 3 次以上修复失败：质疑架构

**表明架构问题的模式：**
- 每次修复在不同位置暴露新问题
- 修复需要"大规模重构"
- 每次修复在其他地方产生新症状

**停止并质疑：** 这个模式是否从根本上不合理？是否应该重构架构而非修修补补？在尝试更多修复前与用户讨论，可配合 `refactoring-insight` 技能评估架构健康度。同时触发外部调研。

---

## Phase 2B：预防性措施（无根因）

### 第 1 步：设计候选方案

对每个候选方案按以下框架评估：

| 维度 | 评估问题 |
|------|---------|
| 覆盖范围 | 能处理哪些场景？遗漏了哪些？ |
| 复杂度 | 需要多少代码？新依赖？新概念？ |
| 副作用风险 | 可能破坏什么？性能影响？ |
| 可维护性 | 后续开发者能理解吗？易于调试吗？ |
| 误判风险 | 会不会阻止正常行为？ |
| 可逆性 | 如果引发问题，撤销的难度如何？ |

### 第 2 步：向用户展示选项

当存在多个可行方案时（外部调研结论直接复用 Phase 0 第 8 步产出格式），使用 `AskUserQuestion`（OpenCode：`question`）：
- 先给对比总表，再逐套展开
- 每套固定结构：专业讲述 + 通俗解释（一句话类比）+ 优点 / 缺点 / 注意事项（不得省略或美化）+ 来源链接
- 推荐选项标记为"(推荐)"并说明理由
- 等待用户决策后再实施

### 第 3 步：实施并继续

方案确定后实施。**[进度] 更新进度文件** — 记录预防性方案及其理由。进入 Phase 3。

## Phase 3：验证

### 第 1 步：确认验证日志

Phase 2A 中已添加日志则跳过此步。若未添加，按以下格式在关键位置补充：

**日志格式：**
```
[时间戳] [级别] [组件::函数] 消息 — 键=值, 键=值
```

**日志级别：** `DEBUG`（追踪执行/验证路径）、`INFO`（状态转换）、`WARN`（预期异常）、`ERROR`（意外失败）

**需要记录：** 修复点的进入/退出及状态、数据转换前后的值、错误路径、修复所依赖的假设

### 第 2 步：用户测试

1. 告知用户需要测试什么以及注意观察什么
2. 等待用户确认测试完成
3. **不要事先宣布成功**
4. **[进度] 更新进度文件** — 标注用户测试已完成

### 第 3 步：日志分析

用户确认测试完成后，分析日志文件。注意 `.adl-logs/` 位于 `.gitignore` 中：

**只分析最新日志：** 目录中可能存在多个日志文件，其中大部分是历史旧日志。必须按 `LastWriteTime` 找到**最新**的一个日志文件进行分析，忽略其余旧文件。`.adl-logs/`、`debug-logs.txt`、`debug-logs-browser.txt` 均为同名覆盖式文件时直接分析；存在多个按时间命名/生成的日志时，先 `LS` 列出并按最后写入时间取最新。

| 工具 | 可用？ | 说明 |
|------|--------|------|
| `LS` / `Read`（绝对路径） | 是 | 绕过 `.gitignore` |
| `RunCommand` | 是 | Shell 不遵守 `.gitignore` |
| `Glob` / `Grep` / `SearchCodebase` | **否** | 遵守 `.gitignore`，会遗漏日志 |

**也检查运行时调试日志：** `debug-logs.txt`（Tauri）和 `debug-logs-browser.txt`（浏览器）— 同样只取最新（与当前测试环境匹配的那一份）

**检查要点：** 预期日志条目 → 确认修复生效；错误条目 → 边界情况；缺失条目 → 代码路径未触发；意外模式 → 与假设不符

### 第 4 步：处理结果

| 结果 | 操作 |
|------|------|
| 日志确认有效，用户确认解决 | **[进度] 标记已完成**，记录验证摘要 → 进入过渡阶段 |
| 修复部分有效但存在缺口 | 识别缺口，记录分析，返回 Phase 2A/2B 完善 |
| 修复完全无效 | 记录失败尝试，重新检查方案/代码/方法/架构 |
| 引入回归 | 回滚或调整修复；记录回归；重新评估副作用 |
| 用户说"问题还是没有解决" | 记录"用户报告修复无效"，进入失败迭代 |

### 失败迭代

当用户报告问题仍然存在，按以下顺序逐层排查：
1. **方案层** → 假设错了？修复的是表象而非根因？
2. **代码层** → 实现是否正确？边界情况？
3. **方法层** → 技术策略是否合理？
4. **架构层** → 是否是系统性问题？（可配合 `refactoring-insight` 技能）
5. 仍然卡住 → 触发外部调研

**经过 3 次失败的迭代后，停止。** 向用户升级报告每轮尝试、学到什么、未解决的架构问题。不要尝试第 4 轮。

## Phase 3→4 过渡：触发检测

进入 Phase 4 的触发条件是用户表示问题已解决的任何消息。检测模式：

| 中文 | 英文 |
|------|------|
| "问题已解决"、"已解决"、"搞定了"、"没问题了"、"可以了"、"好了"、"解决了" | "it's fixed"、"problem resolved"、"solved"、"done"、"works now"、"resolved"、"fixed" |

**第 1 步 — 更新进度文件：** 将对应事项标记为 `已完成`，记录确认时间戳。

**第 2 步 — 进度关卡：** 读取进度文件，检查未确认事项：
- 全部已完成 → 进入 Phase 4
- 有未完成事项 → 询问用户每个未确认事项，更新后进入 Phase 4

**模糊触发：** 如果消息可能另有含义（如"好了"可能只是示意停止），询问一次："确认问题已解决，可以开始收尾归档了吗？"

## Phase 4：收尾归档

### 入口关卡

读取 `docs/root-cause-resolution/` 下最新月份子目录中最新的进度文件：
- 所有事项已完成 → 进入第 1 步
- 存在未完成事项 → 返回[过渡阶段 — 第 2 步](#phase-34-过渡触发检测)先解决

### 第 1 步：根因验证与代码清理（子代理工作流）

**只读报告循环：** 子代理只生成报告，主代理验证后实施修复。循环直到报告无问题。

```
子代理 A（根因验证）→ 主代理问题验证 → 主代理修复 → 子代理 A 复审 → 通过
                                                              ↓
                                                       子代理 B（死代码清理）→ 主代理问题验证 → 主代理修复 → 子代理 B 复审 → 通过
```

**规则：**

| 规则 | 说明 |
|------|------|
| 子代理类型 | 使用**可写文件**的子代理（`subagent_type: "general_purpose_task"`），因需写报告文件；禁止其修改任何源代码/配置/文档文件 |
| 仅允许写入报告文件 | 子代理唯一允许的写操作是写入指定报告文件 `.review-diffs/review-issue-N-revM.md`；源码一律只读 |
| 主代理问题验证 | 每个被报告的问题（含预存/低程度问题）修复前，主代理必须先验证真实存在性并判断是否特殊情况（见下方"主代理问题验证"）；确认真实且应修复才修 |
| 强制重新审查 | 主代理修复后，必须重新调度子代理审查，且每次都按最新完整 diff **全量重看**（不得只看增量） |
| 预存问题必须修复 | 包括此前已存在的代码问题；同样须先经主代理问题验证 |
| 逐问题循环 | 每个问题使用独立子代理循环 |
| A 通过后才执行 B | 子代理 B 仅在根因验证通过后启动 |

#### 主代理问题验证（修复前置）

所有被报告的问题（包括预存问题、低程度问题）默认都要修复，但修复前主代理必须逐项验证，结果记录到进度文件：

**1. 真实性验证** — 问题是否真实存在？
- 重新阅读相关代码、复现、核对调用链与逻辑，排除子代理误报、过期快照导致的假阳性
- 核对 diff 快照与实际代码一致（快照是否过期）

**2. 特殊情况判断** — 逐项判定每个被报告问题是否应修复。**默认都要修复**，仅以下真正有正当理由的情形不修复（并记录理由）：

| 情形 | 判定 | 处理 |
|------|------|------|
| **用户特殊设计** | 刻意为之的行为/命名/结构或已知取舍（有注释/文档/历史提交佐证） | **仍需检查是否有优化/调整/改进空间**；确认无任何可改进之处后才不修复并记录理由；无法确认时询问用户 |
| **正当防御性代码** | 系统边界验证、生产调试用的错误处理/日志、有意的性能取舍 | **仍需检查是否有优化/调整/改进空间**；确认无任何可改进之处后才保留并记录理由 |
| **无用/不必要的防御性代码** | 根因修复后不再需要、冗余守卫、多重检查、不必要的预防措施 | **修复并清理删除** |
| **合理兼容处理** | 合理、符合有利于**长期演进**收益、非偷懒性兼容 | **仍需检查是否有优化/调整/改进空间**；确认无任何可改进之处后才保留并记录理由 |
| **不合理兼容处理** | 不合理、不利于长期演进收益、**偷懒性兼容**（为省事绕开重构） | **修复** |
| **非本次变更引入** | 只要在审查范围内发现，无论是否本次变更引入 | **同样修复解决** |

**整体原则：** 保证代码的**准确性、一致性**，所有相关代码**高度吻合、完美契合**。**尽量不引入兼容性代码**，反对"A 兼容 B、B 兼容 C"式的相互兼容层；发现此类兼容一律按上述规则修复为统一、一致的正确实现。**对于所有审查范围内的代码（包括预存代码、用户特殊设计、正当防御性代码、合理兼容处理），即使判定为"不修复"，也必须逐项检查是否存在可优化、调整、改进的内容，确认无任何可改进之处后才不修复。不得偷懒跳过优化检查。**

**3. 判定处理：**

| 判定 | 操作 |
|------|------|
| 真实存在且应修复 | 修复（含预存/低程度问题、非本次变更引入的问题） |
| 误报 | **不修复**，记录理由（子代理误报/过期快照假阳性） |
| 用户特殊设计 / 正当防御性代码 / 合理兼容处理 | **仍需检查优化/改进空间**；确认无任何可改进之处后才不修复，记录理由到进度文件；有可改进之处则优化 |

**4. 复审联动：** "不修复"的判定及理由写入进度文件，并随下一轮复审 prompt 提供给子代理；子代理可提出异议，异议成立则重新评估，循环直到一致。

#### Diff 快照预生成（审查前置）

调度任何子代理之前，先按文件生成独立的 diff 快照文件，子代理直接读取文件，**不在终端重复执行 git 命令**：

1. 在仓库根创建临时目录 `.review-diffs/`（加入 `.gitignore`，Phase 4 完成后删除）
2. **按变更文件拆分快照**（每个变更文件一个独立快照）：
   - 先获取变更文件列表：`git diff --name-only > .review-diffs/changed-files-rev<N>.txt`
   - 为每个变更文件生成独立快照：`git diff -- <文件路径> > .review-diffs/<文件名>-rev<N>.diff`
   - 文件名中的路径分隔符替换为下划线（如 `src/main.rs` → `src_main.rs-rev1.diff`）
3. 子代理 prompt 中给出相关文件的快照路径列表，令其按需 Read 各文件快照，而非自行 `git diff`
4. 每轮主代理修复后，**重新生成所有快照**（rev 递增，如 `rev2`），供下一轮复审使用
5. 子代理将审查报告写入 `.review-diffs/review-issue-<序号>-rev<轮次>.md`；主代理读取该文件并转写索引到进度文件

#### 子代理 A：根因验证

对每个问题，调度子代理审查变更（源码只读，仅允许写报告文件）：

```
分析为修复 [问题描述] 所做的变更。进行全面审查：

1. 根因与正确性：是否识别并修复了真正的根因？遗漏了边界情况？
2. 技术方案与设计质量：方案是否合适？命名、职责、耦合、架构一致性
3. 副作用与安全性：是否引入回归？性能影响？影响共享状态？
4. 预存问题：审查范围内是否存在此前已存在的代码问题？（包括预存警告、报错、问题）
5. 优化与改进机会：审查范围内的代码（含用户特殊设计、预存代码）是否存在可优化、调整、改进的内容？即使判定为"不修复"的项，也必须逐项检查是否有改进空间，不得偷懒跳过

使用 Read 读取 diff 快照文件：.review-diffs/issue-N-revM.diff（禁止在终端自行执行 git 命令）。对每个问题包含严重性（严重/高/中/低）和建议修复方案。

将完整审查报告写入独立报告文件：.review-diffs/review-issue-N-revM.md（含：输入快照路径、逐问题结论、严重性、建议方案）。禁止修改任何源代码文件。返回消息只需给出报告文件路径 + 关键摘要。
```

#### 子代理 B：死代码与冗余清理

**仅在子代理 A 通过后执行。** 对每个通过根因验证的问题，调度子代理（源码只读，仅允许写报告文件）：

```
审查为 [问题描述] 所做的所有变更。识别并报告：

1. 死代码 — 不可达的代码（未使用的导入、函数、变量、永不执行的条件分支）
2. 冗余检查 — 同一条件的多重守卫、重复验证
3. 不必要的预防措施 — 根因修复后不再需要的防御性代码
4. 诊断日志 — 应删除或降级为 trace 级别的调试日志
5. 优化与改进机会 — 审查范围内是否存在可优化、调整、改进的内容（含用户特殊设计、预存代码）？即使判定为"不修复"的项，也必须逐项检查是否有改进空间，不得偷懒跳过

不要标记：有正当用途的错误处理、系统边界验证、生产调试用的 warn/error 日志

使用 Read 读取 diff 快照文件：.review-diffs/issue-N-revM.diff（禁止在终端自行执行 git 命令）。对每个项目指定：文件路径、行号、要删除的内容、为何可安全删除。

将完整报告写入独立报告文件：.review-diffs/review-issue-N-revM.md（含：输入快照路径、逐项结论、文件路径、行号、删除内容）。禁止修改任何源代码文件。返回消息只需给出报告文件路径 + 关键摘要。
```

#### 并行派发与轮次控制

- 多个问题同轮审查时，**在同一条消息中并行派发**多个子代理（每个问题一个），等待全部返回后合并报告
- 每轮循环结束后重新生成快照（rev 递增），下一轮复审按**最新完整 diff 全量重看**
- 复审必须针对最新快照，禁止基于过期快照或上一轮报告直接判断"无问题"

#### 最终验证

所有清理完成后：
1. 运行 `mandatory-testing` 验收流程（ESLint/Prettier/Clippy/rustfmt + 类型检查 + 测试）
2. 验证所有修复在清理后仍然完整

**测试范围遵循全局[测试策略（分级执行）](#测试策略分级执行)：** 所有阶段只跑受影响部分，不执行全量测试。

### 第 2 步：标记所有事项为已完成

确认进度文件中所有事项已标记 `已完成`。保留全部过程记录，不得删除或修改。

### 第 3 步：更新 README.md

更新所在月份的归档 README `docs/root-cause-resolution/YYYY-MM/README.md`（不存在则创建）：
1. 读取当前内容
2. 追加记录（如尚未存在）：
   ```
   - [progress-YYYY-MM-DD-HHmmss.md](./progress-YYYY-MM-DD-HHmmss.md) — 事项1标题, 事项2标题, 事项3标题
   ```
3. 确保链接按时间顺序排列（最新在最后）

## 决策树

```
用户内容
  │
  ├─ 第 0 步：内容类型分类
  │     ├─ 需求相关类型 → 记录进度文件 → 使用 brainstorming（space 与实施计划阶段
  │     │                  须同时覆盖任务中附带的解决/优化/调整问题）→ 衔接实施
  │     └─ 解决/优化/调整类型 → 预检探索 → 向用户复述理解 → 等待确认
  │           ├─ 确认一致 → 创建进度文件 → 进入 Phase 0
  │           └─ 纠正/补充 → 调整理解，重新确认（禁止跳过）
  │
  ├─ [进度] 创建进度文件，列出所有事项
  │
  ├─ Phase 0：根因调查（8 步，含外部调研）
  │     ├─ 根因已确认 → Phase 1 → Phase 2A → Phase 3
  │     └─ 未确认 → 已穷尽手段？ 是 → Phase 2B
  │                             否 → 返回 Phase 0
  │
  ├─ Phase 2A 修复无效？
  │     ├─ 第 1-2 次失败 → 返回 Phase 0 / 外部调研
  │     └─ 第 3 次以上 → 外部调研 + 质疑架构
  │
  ├─ Phase 3 → 已修复？ → 标记已完成 → 进度关卡 → Phase 4
  │     └─ 否 → 失败迭代（方案→代码→方法→架构，最多 3 轮）→ 仍卡住 → 外部调研
  │
  ├─ [记录] 每阶段完成立即写入进度文件（主/子 Agent 均自动记录，防上下文丢失）
  │
  ├─ [测试] 所有阶段只测受影响部分，不执行全量测试
  │
  └─ 任何阶段：用户新任务 → 立即追加进度文件
```

## 红旗警示

| 如果发现自己… | 应该… |
|-------------|------|
| 用户还没确认意图就开始调查/修复 | 停止，先完成预检并等待用户确认 |
| 未分类用户内容就直接处理 | 先做内容类型分类（需求 vs 解决/优化/调整）再选择流程 |
| 需求相关类型未用 `brainstorming` 或未记录进度文件 | 两者都要：进 brainstorming，同时记录进度文件 |
| brainstorming 只设计需求部分，漏掉解决/优化/调整问题 | space 阶段与实施计划阶段必须同时覆盖解决/优化/调整问题 |
| 未探索代码就凭提示词直接下结论 | 先探索相关代码，再形成判断 |
| 探索后跳过确认直接进入 Phase 0 | 必须先向用户复述理解并确认 |
| "先快速修复，以后再调查" / "试试改 X 看看能不能行" | 从一开始就做对；返回 Phase 0，不要猜测 |
| "我没完全理解，但可能有效" | 停止，理解清楚再修复 |
| 一次性做多处改动 | 一次只改一个变量 |
| 跳过验证日志 / 失败测试 | 没有证据就是盲人摸象 |
| 在追踪数据流之前就提出方案 | 你不知道根因 |
| 再试一次修复（2 次以上失败后） | 3 次以上失败 = 架构问题，停止并质疑 |
| 未穷尽根因调查就添加预防性措施 | 返回 Phase 0 |
| 使用 `Glob`/`Grep` 读取 `.gitignore` 保护的日志 | 使用 `LS` + `Read` 绝对路径 |
| 跳过创建/更新进度文件、想"稍后一起记"、依赖记忆 | 进度文件是唯一真实来源；每阶段完成即写入，上下文压缩会丢信息 |
| 子 Agent 未写独立报告文件、只靠返回消息 | 子 Agent 必须写 `.review-diffs/review-issue-N-revM.md`（已实测主 Agent 读不到子 Agent 上下文） |
| 主 Agent 未把子 Agent 报告转写进进度文件 | 收到报告后立即转写/索引到进度文件 |
| 未通过进度关卡就进入 Phase 4 | 必须先检查未确认事项 |
| 没有头绪 / 多次修复失败后仍硬试而不触发外部调研 | 无方案或卡住时必须触发外部调研（最新资料、官方文档、社区、同类产品对标），多方案须给专业+通俗双层解释与优缺点+注意事项 |
| 子代理修改源代码 | 使用可写子代理，仅允许写指定报告文件，源码一律只读 |
| 子代理自行 `git diff` / 复审基于过期快照或只看增量 | 使用预生成快照，每轮修复后重新生成（rev 递增），按最新完整 diff 全量重看 |
| 多个问题串行派发子代理 | 同轮并行派发（一条消息派发多个子代理） |
| 非收尾阶段（含子代理循环内）跑全量测试 | 所有阶段只测受影响部分，不执行全量测试 |
| Phase 3 分析旧日志文件 | 只按 `LastWriteTime` 取最新日志分析 |
| 子代理 B 在 A 未通过时启动 | 根因验证通过后才执行死代码清理 |
| 忽略预存问题 / 非本次变更引入的问题 | 审查范围内的问题无论何时引入都必须修复（先经主代理问题验证） |
| 未验证问题真实性就直接修复 | 先由主代理验证真实存在性（排除子代理误报、过期快照假阳性）再修 |
| 未判断防御性代码/兼容处理是否正当就保留 | 无用防御性代码、不合理/偷懒性兼容须修复；仅正当用途/合理兼容保留并记录理由 |
| 判定"不修复"后未检查优化/改进空间 | 即使判定为用户特殊设计/正当防御性代码/合理兼容处理，也必须逐项检查是否有可优化、调整、改进的内容，确认无任何可改进之处后才不修复 |
| Phase 4 完成后忘记更新 README.md | 每次收尾后必须追加记录 |

**上述任何情况意味着：停止；意图未确认则回到预检阶段，其余返回 Phase 0 重新执行。**

## 速查表

| 阶段 | 关键活动 | 成功标准 |
|------|---------|---------|
| **预检** | 内容分类（需求→brainstorming+进度文件；解决/优化/调整→本流程），探索相关代码，复述问题/方向，等待用户确认 | 用户确认理解与意图一致 |
| **进度** | 创建进度文件，列出事项，每次事件后更新 | 所有事项已追踪且状态准确 |
| **记录** | 每阶段完成立即写入进度文件；子 Agent 写独立报告文件，主 Agent 转写索引 | 关键信息全部落盘，不依赖记忆 |
| **测试** | 所有阶段只测受影响部分，不执行全量测试 | 只运行受影响的测试且全部通过 |
| **0. 调查** | 阅读错误，稳定复现，检查变更，收集证据，追踪数据，模式分析，假设验证，外部调研（最新资料+官方文档+社区+同类产品对标，结合技术栈取舍） | 理解是什么和为什么 |
| **1. 路径** | 确定根因是否已知 | 明确选择路径 A 或 B |
| **2A. 直接修复** | 失败测试，设计方案，检查同类，添加日志 | 修复针对根因 |
| **2B. 预防性** | 设计方案，多方案对比（专业+通俗+优缺点+注意事项），请用户讨论选择 | 方案已确定并实施 |
| **3. 验证** | 确认日志，用户测试，日志分析（只取最新） | 问题已确认解决 |
| **过渡** | 触发检测，标记已完成，进度关卡 | 所有事项已确认，进入 Phase 4 |
| **4. 收尾归档** | 生成 diff 快照 → 子代理 A（根因验证，写报告文件）→ 主代理问题验证 → 子代理 B（死代码清理，写报告文件）→ 分级验证 → 标记已完成 → 更新 README | 代码已清理，报告已归档，进度已标记，README 已更新 |

## 相关技能

- **`systematic-debugging`** — 系统性调试方法论，与 Phase 0 调查配合使用
- **`brainstorming`** — 预检第 0 步判定为"需求相关类型"时使用；其 space 与实施计划阶段须同时覆盖附带的解决/优化/调整问题
- **`codegraph-knowledge-graph`** — 查询代码知识图谱，加速 Phase 0 代码探索
- **`test-driven-development`** — 在 Phase 2A 修复前创建失败测试
- **`refactoring-insight`** — 质疑架构时评估代码质量与重构风险
- **`verification-before-completion`** — 在宣布成功前验证修复
- **`mandatory-testing`** — Phase 4 收尾时的全量验收流程
- **`using-superpowers`** — 技能系统入口
