### 定位到的三个根因

| 现象 | 根因 |
|---|---|
| 分隔符日期显示成「下次启动日期」 | `archivedAt: Date.now()` 只在「会话已死需重建」时调用（即下次启动），记录的是启动时刻 |
| 历史逐渐消失 | `MAX_HISTORY_SEGMENTS = 5`，超出部分连快照一起删 |
| 分隔符无法整行/不跟随宽度 | 分隔符是写进只读 xterm 缓冲区的 ANSI 文本，宽度由写入瞬间的 `cols` 固定 |

### 关键架构决策（含被否方案的理由，后续改动勿重蹈）

1. **不能用一个 xterm 装全部历史**：内存随历史线性增长，宽度变化必须全量重放。
2. **不能用「每段一个只读 xterm」**：`serialize({scrollback:1000})` 单段千行，xterm 按 `rows` 预分配行缓冲与画布（`TerminalHistoryView.tsx` 注释已写明），单挂载段位图即百 MB 量级。
3. **选定：行模型 + DOM 文本 + 行级虚拟化**。历史是「已渲染完的静态屏幕内容」，不需要终端仿真器。

### 顺带挖出的既有坑（已写入 spec §5.3）

**服务端单段保存有 200 KiB 硬上限**（`crates/server/src/handlers/terminal_output.rs` 的 `MAX_OUTPUT_BYTES`），超限返回 `InvalidInput`，而前端 `terminalOutputStore.save()` 只 `console.warn` → 表现为**历史静默丢失**。行模型 JSON 约为 ANSI 文本的 2–3 倍，必须：服务端抬到 2 MiB + 前端加 512 KiB 单段软上限（超限丢最旧屏幕行，保证必定可存）。

### 写入模型定为「追加式行块」（commit `0f24d40f`）

用户追问「三条措施能否彻底解决内容残缺」后复盘确认：**不能**。三条措施只修掉「失败不可见」，没修掉「内容不完整」。据此又挖出**两个比 200 KiB 更靠前的漏点**：

- **漏点 A：采集源本身是有损环**。数据取自 `terminal.buffer.active`，超出 xterm `scrollback` 的行**在内存里就被丢了**，持久化层看不到。VS Code 同病（`terminal.integrated.scrollback` 默认 1000，官方解法只是"让你调大"）→ 归为物理边界，措施是调大采集侧 scrollback（5000）。
- **漏点 B：采集时机是尾去抖而非节流**。原实现每个输出事件 `clearTimeout` + `setTimeout(500)`，持续输出时定时器永不触发，只能靠 30 秒周期兜底 → **最多 30 秒输出未落盘**；这 30 秒若超出环容量即源头丢失。必须改**节流**。

**最终选型：② 追加式行块**（否决 ① 覆盖式快照 + 调阈值、③ 旁路采集 PTY 原始流）。理由是它**结构性消除**「单次写入体积无界」这个根因，而不是把阈值调大。要点：

- 单次写入 = 一个行块（≤ 64 KiB），由「两次采集之间新增的行数」决定 → **撞不到任何体积上限**，所以服务端 `MAX_OUTPUT_BYTES`（200 KiB）**不用改**。
- 键为合成键 `${sessionId}#${seq}`，**复用既有 `terminalOutput` 的 `sessionId: string` 契约 → 零 IPC 改动、零桥接层改动**。
- 段结构：`{ sessionId, endedAt, live, chunks: [{lines, size}] }`（每块元信息都存，供虚拟列表精确落位与二级淘汰计算）。
- 淘汰两级：常规**按段**最旧优先（跳过最近 20 段）；最后手段**按块**丢最旧段的头部块（至少留 1 块）。
- 环回兜底：scrollback 溢出会裁掉最旧行、绝对行号失效 → 检测到位失效则**重建整段**，否则写出错位历史（比丢失更难排查）。
- 无法消除的三类丢失（已写入 spec §2.3）：环外内容、`\x1b[3J` 清掉的 scrollback、强杀时最后一个未落盘的块。

**外部调研结论（可复用）**：xterm 序列化实测——5000 行普通内容 ≈ 0.31 MB 原始 / 0.02–0.04 MB gzip；病态「每格 truecolor」5000 行可达 13 MB 原始，**gzip 后仍超 2 MB**；社区结论是「**必须按字节预算裁剪，行数上限不足以保证体积**」。tmux-resurrect 用 `capture-pane` 抓**渲染后的行文本**、打包 gz、恢复时重新注入 —— 与追加式行块同源思路。VS Code / Windows Terminal 都只是「有界 + 可调」，不承诺无损。
