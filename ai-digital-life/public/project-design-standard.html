设计哲学与核心原则

以下原则中，Agent 体系相关借鉴已随自研 Agent 剥离退役；仅保留对宿主仍有指导意义的部分。

轻量内核 轻量高效内核
仍有效的
  • 分层清晰、内核轻量：宿主只做工作区/终端/编辑器/浏览器/存储，不背 Agent 包袱
  • 纯 SQLite 存储（JSONL 仅作调试日志）
已退役的（随 Agent 体系剥离）
  • 状态驱动 Agent、事件订阅扩展（33 个生命周期事件）
  • 工具注册中心（ToolRegistry）、原生 Fork、自动阈值压缩
我们刻意不选的
  • TUI 优先的极简 UI（不符合桌面用户预期）
  • 纯 JSONL 存储（项目采用 SQLite，JSONL 仅作调试日志）
完整功能 完整功能体系
仍有效的
  • 类型化错误分类：fromError() 归一化思路
  • 精致 UI：审美与交互范式（非组件复用）
已退役的（随 Agent 体系剥离）
  • 动态 Provider 注册（Provider.Service）、自动阈值压缩
  • Ruleset 权限、配置热重载
我们刻意不选的
  • Effect-TS 函数式编程（学习曲线陡）
  • 代码级热重载（不承诺）
  • 单一 Error Channel 总线（实际为多通道类型化错误）

Section 03

架构蓝图

四层宿主：UI 层 → 桥接层 → 后端命令层 → 存储层，每层职责明确；第三方 harness 作为外部进程由宿主拉起与渲染，不在层内。

👨‍💻 专业视角
采用分层宿主架构。严格遵循层间单向依赖原则： UI → Bridge → Backend Commands → Storage。 前端经三桥接调用统一 IPC，经 #[tauri::command]（桌面）或 HTTP（浏览器预览）到达 Rust domain crates。 关键契约（IPC 接口、共享类型）使用 TypeScript 类型作为单一真源（Rust→TS 自动生成）。
🧑 通俗视角
把系统想象成一家餐厅 + 外请主厨：
① 顾客（用户）在前台（UI）点餐
② 服务员（Bridge）把订单传给后厨
③ 后厨（Backend 命令 + domain crates）备菜、存档、记账
④ 冷库（Storage）存着食材和历史订单
⑤ 主厨（第三方 harness，外请）只管做"智能菜"，上菜口（中心渲染）由餐厅提供
想换主厨？不用装修餐厅，换个外请团队就行。
⬇️ 依赖方向：上层依赖下层，下层不得依赖上层
🎨 UI 表现层
React 组件 设计系统 Token 工作区/终端/编辑器/浏览器面板 设置（含存储组/dsh 设置） i18n
🌉 桥接层
Tauri Bridge (桌面) Preview Bridge (浏览器) Mock Bridge (测试) IPC 契约统一
⚙️ 后端命令层
Tauri Commands / HTTP handlers Domain Crates（workspace/pty/browser/clipboard/…） 结构化错误 (AppError) capabilities 白名单
💾 存储层
SQLite 状态（工作区/快照索引/站点元数据/剪贴板…） 文件（日志/dsh bundle） storage-locator 指针 启动期迁移

宿主数据模型

locator 指针 + SQLite 状态 + 文件归档的组合。原"事件流 + Epoch + 会话树"模型已随 Agent 会话体系退役（见决策 03/07/09 存档）。

👨‍💻 专业视角
所有应用数据路径由 adl-kernel::storage 的 StoragePaths 统一解析， locator 文件记录指针，默认统一根为 app_data_dir()。 SQLite 存结构化状态，文件存大体量内容；路径变更登记为 pendingMigration， 在下次启动、任何 DB/日志句柄打开前执行迁移。
🧑 通俗视角
想象搬家公司 + 档案室：
• locator 是"新家地址卡"，所有东西按卡上的地址放
• SQLite 是档案柜：工作区清单、补丁快照索引、网站元数据、剪贴板各就各位
• 文件是仓库：日志、dsh 安装包放架子上
• 搬家（迁移）只在开门前进行：先复印、再验货、再换地址卡，最后清理旧家；验货失败就不换卡

Section 05

关键风险与应对

宿主 + 外部 harness 形态下的主要风险。原 Agent 体系风险已随退役失效，不再列出。

风险 01 · dsh 宿主进程托管可靠性
dsh 为外部进程：拉起失败、端口占用、版本不匹配、进程意外退出 都会让中心无内容可渲染。
✅ 应对策略
① webapp-host 拉起后做就绪探测，失败重试；Windows 下先直调、失败回退 .cmd
② 系统 dsh 与内嵌 bundle 双源：优先可用源，检测经缓存避免重复探测
③ 版本管理支持查最新 / 升级 / 回退 / 卸载，升级失败保留旧版可用
④ 浏览器模式 iframe 加载被拒（X-Frame-Options / CSP）时退化为"外部打开"按钮
风险 02 · 结构化错误 vs 现有 captureTypedError
现有前端已实现 captureTypedError 体系（Zustand slice 中显式捕获）， Rust 侧已有 Result 结构化错误。双端如何归类对齐？
✅ 应对策略
① 不引入"统一 Error Channel 总线"，对齐现有双端体系
② Rust 侧：Result 结构化传播，ErrorKind 全覆盖分类
③ 前端：captureTypedError 统一归类 + 结构化 JSONL 日志
④ 新增模块沿用现有模式，不做"大爆炸"式重构
风险 03 · 存储迁移丢数据
路径变更涉及搬运 SQLite 与大文件：中途失败、句柄占用、 目标不可写都可能丢数据或留双份。
✅ 应对策略
① 只在启动期、任何 DB/日志句柄打开前迁移，不做运行中热迁移
② 按分类复制 → 校验（尺寸 + PRAGMA quick_check）→ 切换指针 → 清理旧源
③ 失败不切换指针、不删源文件、不自动重试，等用户在设置中重试或取消
④ 清理用 base-aware 白名单，外部文件永不删除；预检用 .adl-write-probe 探测目标可写性
风险 04 · 设计感 UI + Tauri 双端一致性
浏览器预览（Chromium）和 Tauri 桌面（WebView2）的渲染引擎差异、 系统字体差异、DPI 缩放差异，可能导致精致 UI 在 WebView2 中"看起来不精致" （字体发虚、动画掉帧、颜色偏差）。WebView2 为 OS 级渲染表面，CSS z-index 无法覆盖。
✅ 应对策略
① 设计 Token 必须抽象：颜色、字号、间距全部用 CSS 变量，平台层覆盖
② 字体栈优先用 Web Font（Inter / HarmonyOS Sans），不依赖系统字体
③ 关键组件建立"双端验证清单"，每次修改后人工确认两端表现一致
④ 浮动层出现时经 browser_set_bounds 移出 WebView（State + MutationObserver 双路检测）； 面板 Resize Handle 用"区域逃逸"（向左扩展 8px 进无 WebView 区）
⑤ 启用 CSS will-change + transform 动画，避免重排导致的掉帧
风险 05 · 凭据管理 + 权限门禁误放
WebView 若绕过 Tauri Command 直接触达系统能力，或 capabilities 使用通配权限， 将破坏安全边界；凭据若落入普通配置或日志，会造成泄露。
✅ 应对策略
① 凭据只经 crates/credential 存储（keyring + 加密文件降级）
② capabilities 白名单禁止 "all" / "**" 通配，新增命令必须登记
③ 敏感操作走审批确认（ApprovalRequired）
④ 日志中凭据脱敏，禁止明文打印
