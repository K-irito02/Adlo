🔭 项目概览

两个项目同为 AI 编码代理领域的前沿开源实现，但理念与侧重点各有不同。

Pi 极简主义 · 终端优先

由 Mario Zechner（badlogic）创建，定位为"极简终端编码工具"。核心理念：适应你的工作流，而不是反过来。Pi 通过 TypeScript 扩展系统、技能系统和包管理机制，让用户可以按需构建自己的 IDE 体验，而不需要 fork 源码。

  • 语言：TypeScript（纯前端，无后端）
  • 运行模式：交互式 TUI、打印模式、JSON 模式、RPC 模式、SDK 嵌入
  • 包管理：npm/git 安装扩展包（Pi Packages）
  • 架构：单体仓库 + 多包发布

OpenCode 企业级 · 架构先行

定位为企业级 AI 编码平台，目前正在进行 V2 架构重写。核心理念：插件化、可热重载、类型安全。OpenCode 使用 Effect-TS 函数式编程框架构建，注重可测试性、可观察性和可维护性。

  • 语言：TypeScript + Effect-TS（函数式）
  • 运行模式：CLI + TUI + 桌面应用 + Web 前端
  • 架构：微服务 + 包化 + 插件系统
  • 特点：V2 重写中，强调小核心 + 插件架构
💡 通俗理解

Pi 像一个"乐高积木盒"——给你几个基本工具，你可以自由拼装出自己想要的东西，轻巧灵活。OpenCode 更像一个"装配工厂"——它定义了一套完整的生产流程和接口标准，各个模块各司其职，适合团队协作和规模化扩展。

🎯 设计哲学对比

理解两个项目的核心理念，就抓住了它们的灵魂。

Pi 的哲学 进攻性可扩展

Pi 明确拒绝内置很多功能，因为"你应该自己决定怎么工作"：

  • No MCP —— 用 CLI 工具 + README（Skills）就够了
  • No Sub-agents —— 用 tmux 或扩展自己实现
  • No Permission Popups —— 放容器里跑，或写扩展自己控制
  • No Plan Mode —— 写计划到文件，或用扩展实现
  • No Background Bash —— 用 tmux，完全可观察、可交互

这种"减法哲学"让 Pi 核心极轻，但扩展能力极强。

OpenCode 的哲学 小核心 + 插件化

OpenCode V2 正在进行的重构核心思路：

  • 核心只做状态容器 —— 核心服务如 Catalog、Account、Agent 只管理状态，暴露简单操作接口
  • 行为外移到插件 —— Provider 注册、配置加载、认证、模型发现等全部由插件实现
  • 热重载设计 —— 更新是细粒度的、可观察的，不需要重启整个进程
  • 插件钩子系统 —— 通过 Immer draft 让插件可以安全地修改配置，通过 cancel 机制控制变更
  • 策略与配置分离 —— Provider 配置和 Provider 策略是两回事，配置控制"能不能连"，策略控制"允不允许用"

这种"分离关注点"的哲学让系统可维护性极高。

💡 通俗理解

Pi 的理念是"给你一把瑞士军刀，剩下的你自己发挥"；OpenCode 的理念是"我给你设计好工厂流水线，每个工位都有标准接口"。两者没有优劣，只是适用场景不同：Pi 适合个人开发者快速迭代，OpenCode 适合团队协作的企业级场景。

🏗️ 架构设计

两个项目在架构层面展现了截然不同的设计思路。

Pi 分层架构

Pi 采用经典的四层架构，层次清晰：

  • @pi-ai —— 底层 AI 库，封装 LLM API、Provider 管理、模型目录、流式传输、OAuth 认证等
  • @pi-agent-core —— Agent 运行时，有状态 Agent、工具执行、事件流、会话管理、上下文压缩
  • @pi-coding-agent —— 编码代理应用层，CLI/TUI/RPC 接口、扩展/技能/主题系统
  • @pi-tui —— 终端 UI 组件库，Box、Text、编辑器等渲染组件

OpenCode 插件化微内核架构

OpenCode V2 采用"小核心 + 插件"架构：

  • packages/core —— 领域 Schema、类型化错误、状态容器、事件、插件钩子合约
  • packages/opencode —— 应用层，CLI/TUI/服务器路由/存储胶水/遗留兼容
  • plugins —— Provider 插件、配置插件、认证插件、模型发现插件等
  • EventV2 —— 自包含的持久化事件系统，支持事务性排序、发布订阅、回放

💡 通俗理解

Pi 的架构像一栋四层楼房——每层有自己的职责，上层依赖下层，结构清晰但相对固定。OpenCode 的架构像一个可插拔的服务器机箱——核心只提供总线供电和通信协议，真正的功能由插上去的板卡（插件）提供，可以随时更换升级。

📦 模块设计

深入两个项目的模块划分，了解如何组织代码。

💡 通俗理解

Pi 的模块是垂直分层的：AI 底层 → Agent 运行时 → 应用层，每层解决一个抽象级别的问题。OpenCode 的模块是水平分割的：核心只做领域建模，应用层只做界面和路由，Schema 包作为所有模块的"共同语言"。

🤖 Agent 设计

这是两个项目最核心、最值得深入学习的部分。

Pi Agent 有状态 · 事件驱动

Pi 的 Agent 设计围绕"有状态的事件循环"展开：

  • Agent 类 —— 封装了完整的 Agent 状态（systemPrompt、model、tools、messages、thinkingLevel）
  • 消息流 —— AgentMessage → transformContext() → convertToLlm() → LLM，支持自定义消息类型（通过 declaration merging）
  • 事件序列 —— 每个 prompt() 调用产生 10+ 种事件：agent_start → turn_start → message_start/update/end → tool_execution_start/update/end → turn_end → agent_end
  • 工具执行模式 —— 支持并行（默认）和串行，并行模式下 preflight 串行验证 + 执行并发执行，按 LLM 请求顺序持久化
  • Steering & Follow-up —— 允许用户在 Agent 运行时"插队"发送消息，steer 在工具执行后立即处理，follow-up 在 Agent 全部完成后处理
// 核心 API 示例 const agent = new Agent({ initialState: { systemPrompt, model }, streamFn: models.streamSimple.bind(models), }); agent.subscribe(async (event) => { if (event.type === "message_update") { /* 流式渲染 */ } }); await agent.prompt("Hello!");

OpenCode Agent 策略驱动 · 热重载

OpenCode 的 Agent 设计围绕"配置化 + 策略化"展开：

  • Agent 定义 —— 通过配置文件定义 Agent（model、variant、system prompt、permissions、steps、color、mode）
  • 多 Agent 系统 —— 支持 primary/subagent 角色，可定义多个命名 Agent（如 reviewer、build、plan）
  • 权限系统 —— 每个 Agent 有自己的权限规则（permissions），控制 tool 访问
  • V2 Runner —— Effect-native 的本地运行器，逐 turn 执行，支持 durable 投影、上下文压缩、并发的 Session 执行
  • Context Epoch —— 保存不可变的 Provider 缓存基线 + 可观察的上下文源，上下文变更时以时间顺序插入 System 消息
// V2 配置式 Agent 定义 { "agents": { "reviewer": { model: "openrouter/openai/gpt-5", variant: "high", system: "Find regressions and missing tests.", mode: "subagent", steps: 12, permissions: [ { action: "edit", resource: "*", effect: "deny" } ] } } }

💡 通俗理解

Pi 的 Agent 像一个"对话机器人"——你告诉它你是谁、用什么模型、有什么工具，然后开始对话，它通过事件告诉你每一步的进展。OpenCode 的 Agent 更像一个"可配置的智能体"——你可以在配置文件中定义多个不同角色的 Agent（审查员、构建员、规划员），每个都有自己的权限和模型，系统按需调度。

🔧 工具系统

工具是 Agent 与外部世界交互的桥梁，两个项目都设计了精密的工具系统。

Pi 灵活的工具注册

  • AgentTool 接口 —— 包含 name、label、description、parameters（Typebox schema）、execute、renderCall、renderResult
  • executionMode —— 每个工具可单独配置并行/串行执行模式
  • 流式进度 —— execute 中通过 onUpdate 回调流式输出进度
  • 终止信号 —— 返回 terminate: true 可跳过自动后续 LLM 调用
  • 文件突变队列 —— withFileMutationQueue() 确保并行工具调用时文件读写一致性
  • 输出截断 —— 内置 truncateHead/truncateTail 工具，50KB/2000行限制
  • 动态工具加载 —— 支持运行时按需加载工具（如搜索工具），利用 Anthropic/OpenAI 的原生延迟加载机制
  • 远程执行 —— 支持通过 ReadOperations/BashOperations 等接口将工具操作委托给远程系统
pi.registerTool({ name: "my_tool", description: "What this tool does", parameters: Type.Object({ action: Type.String() }), async execute(toolCallId, params, signal, onUpdate, ctx) { onUpdate?.({ content: [{ type: "text", text: "Working..." }] }); return { content: [{ type: "text", text: "Done" }], details: {} }; }, });

OpenCode 类型安全的工具定义

  • Tool.make() —— 使用 Effect Schema 定义 input/output 编解码器，类型安全
  • 执行上下文 —— 每个工具接收 sessionID、agent、assistantMessageID、toolCallID
  • 名称注册 —— 工具名在注册时确定，与工具值本身分离
  • 作用域注册 —— 支持 Location 级和进程级注册，Location 优先
  • 输出边界 —— 工具返回完整域输出，系统层做 Provider 输出边界处理
  • 失败语义 —— ToolFailure（模型可见）、中断（非工具结果）、缺陷（操作失败策略）三者严格区分
  • Permit 集成 —— 工具执行前调用 PermissionV2 进行权限检查
const grep = Tool.make({ description: "Search file contents", input: Input, output: Output, execute: (input, context) => Effect.gen(function* () { yield* permission.assert({ sessionID: context.sessionID, ... }); return yield* filesystem.grep(input, root); }), });
💡 通俗理解

Pi 的工具系统像"工具箱"——每个工具都有独立的说明书（description）、参数清单（parameters）和操作手册（execute），你可以随时增加新工具，也可以替换内置工具。OpenCode 的工具系统像"工厂流水线的工位"——每个工位都有严格的输入输出规范（Schema），有安全检查（Permission），有标准操作流程，确保整个生产线稳定可靠。

💬 会话管理

会话管理是编码代理的核心基础设施，直接影响到用户体验和系统可靠性。

Pi JSONL 树形会话

  • 存储格式 —— JSONL 文件，每行一个事件条目，附带 id 和 parentId 形成树形结构
  • 分支管理 —— 通过 /tree 导航会话树，/fork 从历史点创建新会话，/clone 复制当前分支
  • 上下文压缩 —— 支持手动（/compact）和自动压缩，溢出时自动触发并重试
  • 会话持久化 —— 自动保存到 ~/.pi/agent/sessions/，按工作目录组织
  • 外部编辑 —— 支持 Ctrl+G 打开外部编辑器，支持 piped stdin

OpenCode 持久化事件流

  • Durable Inbox —— session_input 是持久化收件箱，PromptAdmitted 事件记录已接受的输入
  • Context Epoch —— 保存不可变的 Provider 缓存基线，上下文变更时自动插入 System 消息
  • 自动压缩 —— 每次 Provider 调用前估计上下文大小，超预算时自动触发压缩
  • 事件回放 —— EventV2 支持事务性排序、发布订阅、回放，客户端可通过 sessions.events() 订阅
  • Steer/Queue 投递 —— steer 输入在下一个安全边界投递，queue 输入按 FIFO 顺序投递
💡 通俗理解

Pi 的会话系统像"笔记本"——每页记录一次对话，你可以翻到之前任何一页继续写，也可以用分支记录不同的思路。OpenCode 的会话系统像"录音+文字记录"——所有对话都有录音（持久化事件），可以随时回放，还能自动压缩优化存储空间，适合长时间的复杂对话。

🔌 扩展机制

扩展能力是两个项目最显著的区别之一，也是最具学习价值的部分。

Pi 四层扩展体系

Pi 提供了四个层次的扩展点，从简单到复杂：

  • Prompt Templates —— 最简单的扩展，就是 Markdown 文件，写一段提示词模板，通过 /name 调用
  • Skills —— 能力包，包含 SKILL.md + 辅助脚本，遵循 Agent Skills 标准，通过 /skill:name 调用
  • Extensions —— 最强大的扩展，TypeScript 模块，可以注册工具、命令、事件监听器、UI 组件
  • Pi Packages —— 将扩展/技能/提示词/主题打包成 npm 包或 git 仓库，通过 pi install 安装
// Extension 能做几乎所有事情 export default function (pi: ExtensionAPI) { pi.registerTool({ name: "deploy", ... }); pi.registerCommand("stats", { ... }); pi.on("tool_call", async (event, ctx) => { /* 拦截工具调用 */ }); pi.on("session_before_compact", async (event, ctx) => { /* 自定义压缩 */ }); pi.registerShortcut("ctrl+shift+p", { ... }); pi.registerFlag("plan", { type: "boolean" }); pi.registerProvider("my-proxy", { ... }); };

OpenCode 插件钩子系统

OpenCode V2 正在构建一个更严谨的插件系统：

  • 插件定义 —— 返回 { order, hooks } 的 Effect，通过 order 控制加载顺序
  • 钩子类型 —— 定义在 PluginV2.HookSpec 中，当前包括：init、provider.update、model.update、account.update、account.remove、account.activate、account.activated
  • Immer Draft —— 回调接收 Immer draft，可以安全修改配置，坏变更可丢弃
  • Cancel 机制 —— 通过 cancel: boolean 让插件可以阻止变更
  • 热重载 —— 插件更新时不需要重启进程，只需重新注册
// 内置插件示例 export const EnvPlugin: Definition = Effect.gen(function* () { return { order: PluginOrder.env, // 加载顺序 10 hooks: { "provider.update": (draft) => { // 根据环境变量自动启用 Provider }, }, }; });

🧠 模型与 Provider

模型接入是编码代理的核心能力，两个项目都支持大量 Provider。

Pi 30+ Provider 全面覆盖

  • 官方 Provider —— Anthropic、OpenAI、Google、Azure、Amazon Bedrock、Mistral 等
  • 社区 Provider —— DeepSeek、Kimi、MiniMax、小米 MiMo、OpenRouter、Together AI 等
  • 本地模型 —— 支持 llama.cpp router 服务器，通过 /llama 管理模型下载和加载
  • 自定义 Provider —— 通过 ~/.pi/agent/models.json 或扩展注册自定义 Provider
  • OAuth 认证 —— 支持 Anthropic、GitHub Copilot、OpenAI Codex 等 OAuth 登录
  • 思考级别 —— 7 级思考水平（off/minimal/low/medium/high/xhigh/max），可精细控制

OpenCode 插件化 Provider 架构

  • Provider 插件 —— 每个 Provider 是一个插件，可独立注册/注销
  • 类型化 Schema —— ProviderV2.Info 包含 id、name、enabled、endpoint、options
  • 策略控制 —— 通过 experimental.policies 控制 Provider 可用性，与配置分离
  • 模型变体 —— 支持模型变体（Variants），如不同推理级别
  • 自动发现 —— models.dev 服务自动发现模型，EnvPlugin 根据环境变量自动启用 Provider

💡 通俗理解

Pi 的 Provider 系统像"万能遥控器"——预置了 30+ 个"频道"（Provider），你只需要按几个键就能切换。OpenCode 的 Provider 系统像"可编程的电视信号接收器"——每个 Provider 是一个可插拔的模块，你可以通过配置策略决定哪些频道可见，哪些频道禁用。

⚙️ 配置系统

配置系统是编码代理的"控制面板"，直接影响用户体验。

Pi 分层配置

  • 层级 —— 全局（~/.pi/agent/settings.json）→ 项目（.pi/settings.json）
  • 交互式配置 —— 通过 /settings 命令在 TUI 中修改
  • 上下文文件 —— 自动加载 AGENTS.md/CLAUDE.md 作为系统提示
  • 项目信任 —— 首次运行项目时询问是否信任，信任后加载项目本地配置和扩展
  • 环境变量 —— 20+ 环境变量控制运行时行为（API Key、离线模式、缓存策略等）

OpenCode V2 配置重构

  • 配置发现 —— opencode.json/opencode.jsonc 在全局、项目父目录、.opencode 目录中查找
  • V2 配置组 —— 11 个配置组，每个组经过详细评审（keep/remove/redesign）
  • 策略与配置分离 —— Provider 配置和 Provider 策略是两个独立的概念
  • 引用系统 —— 通过 references 配置本地目录或 Git 仓库的引用，用 @alias 访问

💡 通俗理解

Pi 的配置像"手机设置"——有全局设置和每个 App 的设置，通过图形界面修改，简单直观。OpenCode 的配置像"企业级配置文件"——每个配置项都经过严格评审，有明确的版本迁移路径，适合团队标准化管理。

💎 总结与借鉴

从 Pi 可以学到什么

  • 极简主义设计 —— 核心功能做到极致，其他留给扩展。拒绝不必要的复杂功能，每个功能都有明确的理由
  • 完整的事件系统 —— 10+ 种事件类型覆盖 Agent 完整生命周期，让 UI 层可以精确响应每个状态变化
  • 灵活的扩展体系 —— 四层扩展（模板/技能/扩展/包）满足不同复杂度需求，降低扩展门槛
  • 进程式工具执行 —— 并行/串行灵活切换，流式进度反馈，文件突变队列确保一致性
  • 动态工具加载 —— 利用 Provider 原生延迟加载机制，按需加载工具，优化缓存命中率
  • Steering/Follow-up 机制 —— 用户可以在 Agent 运行时"插队"发送消息，提供更好的交互体验

从 OpenCode 可以学到什么

  • 插件化架构 —— 小核心 + 插件，通过钩子系统实现热重载，状态和行为分离
  • 类型安全的设计 —— 使用 Effect Schema 做类型化编解码，Schema.TaggedErrorClass 做类型化错误，Branded ID 做类型安全标识
  • 策略与配置分离 —— 配置描述"能不能连"，策略决定"允不允许用"，两者独立演化
  • Context Epoch —— 不可变的 Provider 缓存基线 + 可观察的上下文源，上下文变更时自动插入 System 消息
  • Durable Inbox —— 持久化收件箱模式，确保消息不丢失，支持回放和恢复
  • 配置评审流程 —— 每个配置项都经过 keep/remove/redesign 评审，避免遗留负担

💡 最终思考

Pi 和 OpenCode 代表了编码代理领域的两种典型设计思路：Pi 追求"极致的灵活性和用户体验"，OpenCode 追求"极致的可维护性和扩展性"。对于我们自己的项目来说，最理想的方案是吸取两者的精髓——在架构上借鉴 OpenCode 的插件化和类型安全，在用户体验上借鉴 Pi 的简洁和灵活，打造一个既有坚实基础又有上佳体验的 AI 编码代理平台。
